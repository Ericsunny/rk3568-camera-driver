## ① 任务目标(做完这个,你应该能白板讲清)

1. **i2c_driver 模型**:probe(client)/remove、of_match_table、id_table、`module_i2c_driver`——与你写过的 platform_driver 只差三处(见 §1.1 对照表)

> 你板上正在运行的内核,就是**你自己 VM 编出来的那一颗**:
> `Linux version 4.19.232 (rk3568@rk3568-vm) ... #8 SMP Mon Oct 12 14:35:54 UTC 2026`
> 说明 `~/rk3568/RK_SDK/kernel` **就是运行内核的源码树**——用它编的模块,vermagic 与符号表天然一致,不会出现"版本魔术不匹配"。

> **三条实测教训**:
> ① 原任务书的 `CROSS_COMPILE=aarch64-linux-gnu-` 在你这台 VM 上**不存在**;写成裸前缀(`aarch64-rockchip-linux-gnu-`)则要求 PATH 里有工具链,忘了 export 就报 `aarch64-rockchip-linux-gnu-gcc: No such file or directory / Is your PATH set correctly?`
> ② **手打工具链目录名极易出错,而且报错会骗人**(2026-10-19 实测):目录名敲成 `gcc-builtroot-9.3.0-2020.03-x86_64-aarch64-linux-gnu`(少 d、下划线变横线、结尾不对)或把两段前缀拼在一起时,命令行变成 `.../bin/aarch64-linux-gnu-/bin/aarch64-rockchip-linux-gnu-gcc`,报错却仍说 `Is your PATH set correctly?` —— **真凶是路径拼错,不是 PATH**。用自动查找版后,目录名一个字母都不用打;找不到时会直接报 `Cannot find toolchain under ...`。
> ③ **Makefile 里写中文注释会出事**:注释行会与下一行并成一行(实测),导致变量赋值变成注释的一部分、变量为空,而报错仍表现为"找不到编译器"。**Makefile 一律 ASCII。**

自查:`cat ~/rk3568/RK_SDK/kernel/include/config/kernel.release` 应输出 `4.19.232`(这个字符串就是 vermagic 的来源,已实测)。

#### 事实 2:★ 你的 .ko 会 insmod 成功,但 probe 可能永远不打印

这是模块四最容易卡死的地方。机制:**驱动和设备靠 compatible 匹配,先注册的先赢。**

你板上的实际情况(实测):

- ov8858 的驱动是**内建**的(配置成 =y,不是模块):
  `grep -i ov8858 /lib/modules/4.19.232/modules.builtin` → `kernel/drivers/media/i2c/ov8858_camera.ko`
  (ov5647 / imx415 / sc530ai / dw9714 同样都是内建)
- 设备树节点 `cam1_ov8858@36` 的 `compatible = "ovti,ov8858"`,当前 `status = "disabled"`(我逐节点核过 i2c5 下 10 个节点全是 disabled)

于是你会遇到三种现象,**全都不是 bug**:

| 你的做法 | 现象 | 原因 |
|---|---|---|
| 驱动写 `ovti,ov8858`,节点仍 disabled | insmod 成功,毫无打印 | 没有设备 → probe 根本不会被调用(模块活着但没活干) |
| 驱动写 `ovti,ov8858`,节点改 okay | insmod 成功,**还是没有你的打印** | 内建驱动开机就已注册,把设备抢走了 |
| 驱动写**独特** compatible(如 `ovti,ov8858-sm`)+ 节点 compatible 改成同一个 | **你的 probe 打印出现** | 只有你匹配 |

**结论:骨架想验证到"probe 级",必须动一次 dtb**(改节点 compatible 或 status → 重编 dtb → 重部署,这套你在 L1-A 已经会)。这本来就是 L1-B 的前置动作,不算额外工作。

#### 事实 3:骨架阶段"不插模组"也能验证,但有前提

- 骨架**不读 chip id**(那是 L1-B 的活)→ I2C 通信失败**不影响** probe 成功
- 但三路电源必须拿得到:`cam1_ov8858@36` 里有 `avdd-supply / dovdd-supply / dvdd-supply`,若它们引用的 regulator 没使能,`devm_regulator_bulk_get` 会返回 `-EPROBE_DEFER` → probe 反复重试,你只看到 deferred 日志
- 自查命令:`cat /sys/kernel/debug/regulator/regulator_summary | head -30`

### 阶段 B:加载级(目标:probe 打印出来、remove 干净)· 约 1 天

**手术点 3 · power_on/power_off 函数**:power_on = `regulator_bulk_enable` → `clk_prepare_enable` → (PWDN 拉高,`gpiod_set_value`);power_off = 逆序。**全部返回 int 把错误往上传**。

**手术点 4 · probe 开头**:`devm_kzalloc` 私有结构体 → `v4l2_i2c_subdev_init(&priv->subdev, client, &ov8858_sm_subdev_ops)`(一行完成 sd↔client 双向绑定,你在图上画过的那根线)→ 存 client。

**手术点 5 · 五件套之 regulator**:supplies 数组三名字(`"dovdd"/"avdd"/"dvdd"`,**必须与 dts 的 `*-supply` 属性名后缀一致**,就是你 05 文档里 ov8858 节点的三个 supply)→ `devm_regulator_bulk_get` → 返回值检查,**`-EPROBE_DEFER` 原样上抛**。

**手术点 6 · 五件套之 clk**:`devm_clk_get(dev, "xvclk")` → 检查。enable 放 power_on(手术点 3),不放 probe——**为什么?**(自查题 2)。

**手术点 7 · runtime PM**:填 `ov8858_sm_pm_ops`(`.runtime_suspend = power_off`,`.runtime_resume = power_on`),`SET_RUNTIME_PM_OPS`;probe 尾部 `pm_runtime_enable`。**铁律**:power_on/off 会被 PM 框架和 s_stream **双路径**调用,必须可重入。

**手术点 10 · media pad**:`priv->pad.flags = MEDIA_PAD_FL_SOURCE` → `media_entity_pads_init(&sd->entity, 1, &priv->pad)`(图上"把 pads 登记给 entity")。

**手术点 11 · 注册**:`pm_runtime_enable` → `v4l2_async_register_subdev(&priv->subdev)` → `dev_info(client->dev, "ov8858_sm probe done\n")`。

**手术点 12 · remove(对称性自查)**:`async_unregister` → `pm_runtime_disable` → `ctrl_handler_cleanup` → 返回 0。**对称性纪律:probe 里每一步成功,remove 里都要有对应撤销;devm 管的除外**。

**probe 的调用顺序**(照着排,别跳):

```
ov8858_sm_probe(client)
  ① devm_kzalloc 私有结构体
  ② v4l2_i2c_subdev_init(&priv->subdev, client, &ops)     ← sd↔client 双向绑定
  ③ 五件套取资源:devm_regulator_bulk_get → devm_clk_get → devm_gpiod_get(pwdn/reset)
  ④ ctrl handler:init → new_std / new_int_menu → 查 handler->error → sd.ctrl_handler = &handler
  ⑤ media entity:media_entity_pads_init(&sd->entity, 1, &priv->pad)
  ⑥ v4l2_subdev_ops 填表(.core / .pad / .video,先占位)
  ⑦ pm_runtime_enable + SET_RUNTIME_PM_OPS
  ⑧ v4l2_async_register_subdev(&priv->subdev)             ← 之后 subdev 已"活"在系统里
  ⑨ dev_info(client->dev, "ov8858_sm probe done\n")
remove:按 ⑧ ⑦ ⑤ ④ 逆序撤销(devm 管的不用管)
```

✅ **本阶段验收**(需要一次 dtb 改动,见 ②C 事实 2):`insmod` 后 `dmesg` 出现你的 `ov8858_sm probe done`;`rmmod` 无 warning 无 oops;`lsmod` 里出现又消失。

**顺手一件事**:这份骨架 + 你 L1-B 的 dts 改动,正好是 GitHub 仓库 `rk3568-camera-driver` 里 `driver/` 目录的第一份内容(仓库现在只有 `mini3a/` + `docs/`,没有驱动代码)。

#### 1.3 `container_of`(本模块最重要的一条)

```c
#define to_ov8858_sm(sd) container_of(sd, struct ov8858_sm, subdev)
```

- **问题**:框架回调给你的只有 `struct v4l2_subdev *`(框架只知道自己的对象);你要拿自己的私有大数据,怎么办?
- **原理**:私有结构体里 `subdev` 是**内嵌成员**——用"成员地址 − 成员在结构体中的偏移"反推大结构体首地址。`offsetof(type, member)` 编译期算偏移,宏展开就是一次指针减法,**零运行时开销**;
- **IMX6ULL 对照**:`file->private_data` 是"存指针";`container_of` 是"不存指针也能找回",因为**内嵌位置本身编码了信息**;
- **动手验证(10 分钟)**:VM 里写 10 行小程序打印 `&big`、`&big.subdev`、`container_of(&big.subdev)` 三个地址——前两个相减 = offsetof。

#### 1.4 `devm_*` 与 `-EPROBE_DEFER`

- **`devm_*` 家族**(`devm_kzalloc/devm_clk_get/devm_regulator_bulk_get/devm_gpiod_get`):资源挂在 `struct device` 上,驱动 detach 时**自动释放**——IMX6ULL 时代你 probe 里手动 kfree/err 跳标签的写法,devm 全包了。**铁律:probe 里一切能 devm 的都 devm**;
- **`-EPROBE_DEFER`**:regulator/clk 的提供者可能在消费者**之后**注册(内核初始化顺序不保证)。拿不到时返回 `-EPROBE_DEFER`,probe **原样返回这个值**,核心稍后自动重试 probe——你什么都不用做,但**不能吞掉这个错误**。这就是 probe 里错误处理的第一要义。
