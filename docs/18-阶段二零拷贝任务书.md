# 18 - 阶段二:V4L2 零拷贝(EXPBUF → dmabuf → RGA → NPU)

> **一句话**:把相机帧从"采集→memcpy→CPU 缩放→喂 NPU"改成"**VB2 缓冲直接导出 dmabuf → RGA 硬件缩放 → NPU 零拷贝消费**",并用可复现的数字证明省掉了多少拷贝、多少延迟、多少 CPU。
>
> 载体:**IMX415 的 NV12 流**(`/dev/video5`,3840×2160,media1 链路现成)。OV8858 的 RAW10 留作 RAW 域加餐(见 §7)。

## 1. 环境事实(2026-10-21 已逐条验证)

| 项 | 事实 | 验证方式 |
|---|---|---|
| 相机 | `imx415 1-001a → rkisp_mainpath = /dev/video5`,`NV12 3840×2160`,stride 3840 | `v4l2-ctl -d /dev/video5 --get-fmt-video` |
| RGA | `/dev/rga`;`/lib/aarch64-linux-gnu/librga.so`;头文件 `/usr/include/rga/{im2d.hpp,im2d.h,rga.h,...}` | `ls` + `ldconfig -p` |
| NPU | 驱动已绑定;**以 DRM 节点暴露**:`/dev/dri/card1`、`/dev/dri/renderD129`(`DRIVER=RKNPU`) | `cat /sys/class/drm/card1/device/uevent` |
| rknn | `librknnrt 2.3.2`(支持 `rknn_create_mem_from_fd` / `rknn_set_io_mem`) | `strings librknnrt.so` |
| 模型 | `yolov8n_rk3568_i8.rknn`(输入 640×640) | `ls /root/npu/examples/yolov8/model/` |
| 编译 | 板载 `gcc/g++ 9.4.0`、`make` | `gcc --version` |
| **没有**的东西 | 无 `/dev/dma_heap`、无 `/dev/ion` | `ls /dev` |

**推论**:dmabuf **不靠 heap 申请**,而是**直接从 V4L2 的 VB2 缓冲导出**(`VIDIOC_EXPBUF`);RGA 输出缓冲用 `RGA` 自己的 mmap 或第二路 VB2;NPU 输入用 `rknn_create_mem_from_fd(dmabuf_fd)`。

## 2. 三条链路(要对比的就是它们)

```
A. 基线(今天的做法)
   rkisp ──mmap──> 用户态 buf1 ──memcpy──> buf2 ──CPU 双线性缩放──> 640×640 RGB ──rknn_inputs_set──> NPU
   每帧拷贝: 3840*2160*1.5 (NV12 = 12.4 MB) + 640*640*3 (1.2 MB) ≈ 13.6 MB,且全在 CPU 上

B. RGA 硬件缩放(半零拷贝)
   rkisp ──mmap──> 用户态 buf ──memcpy──> RGA 输入 ──RGA 硬件缩放/色彩转换──> RGA 输出 ──rknn_inputs_set──> NPU
   每帧拷贝: 仍是 12.4 MB(只是缩放从 CPU 挪到了硬件)

C. 全零拷贝(目标)
   rkisp ──VIDIOC_EXPBUF──> dmabuf fd ──RGA import(fd)──> 硬件缩放 ──> dmabuf out ──rknn_create_mem_from_fd──> NPU
   每帧 CPU 拷贝: 0 B
```

## 3. 指标定义(必须可复现,不许拍脑袋)

| 指标 | 定义 | 怎么测 |
|---|---|---|
| 帧均拷贝字节数 | 每帧 `memcpy/memmove` 的总字节数 | 工具里把所有 `memcpy` 包成 `cpy_track()`,累加 `len` 并计数 |
| 端到端延迟 | `DQBUF` 拿到帧(用 vb2 timestamp)→ 处理完成(时间戳差) | `clock_gettime(CLOCK_MONOTONIC)`;跑 100 帧取 **中位数/P95** |
| RGA 单次耗时 | 一次 `im2d` 缩放调用的墙钟 | 循环 200 次取中位数 |
| NPU 单次推理耗时 | `rknn_run` 墙钟 | 同上 |
| CPU 占用 | 处理线程的 `utime+stime` / 墙钟 | 读 `/proc/self/stat` 前后差值 |
| 帧率 | 实际 DQBUF 帧数 / 墙钟 | 跑 5 秒 |

> 对比表要求:A/B/C 三行 × 六个指标,并列出"理论拷贝字节数 vs 实测",差值要能解释。

## 4. 手术点(代码往哪写)

建议单文件 `zerocopy/zc_bench.c`(板载 gcc 直接编),内部四个模式:

| 模式 | 开关 | 做什么 |
|---|---|---|
| `--mode=copy` | A | mmap + memcpy + CPU 缩放(NV12→RGB 640×640)+ `rknn_inputs_set` |
| `--mode=rga` | B | mmap + memcpy + RGA(fd 无关,普通 buffer)+ rknn |
| `--mode=zc` | C | EXPBUF + RGA import dmabuf + rknn_create_mem_from_fd |
| `--mode=zc-nonpu` | C′ | 同 C,但只做 EXPBUF + RGA,用于隔离 NPU 因素 |

关键 API:

```c
/* 1. 导出 dmabuf */
struct v4l2_exportbuffer exp = { .type = V4L2_BUF_TYPE_VIDEO_CAPTURE_MPLANE, .index = idx, .plane = 0 };
ioctl(fd, VIDIOC_EXPBUF, &exp);            /* exp.fd 就是 dmabuf fd */

/* 2. RGA 以 dmabuf 导入并缩放 */
rga_buffer_handle_t h = importbuffer_fd(exp.fd, src_size);
rga_buffer_t src = wrapbuffer_handle(h, W, H, RK_FORMAT_YCbCr_420_SP);
rga_buffer_t dst = wrapbuffer_handle(hout, 640, 640, RK_FORMAT_RGB_888);
imresize(src, dst);                         /* 硬件缩放 + NV12→RGB */

/* 3. NPU 零拷贝输入 */
rknn_tensor_mem *mem = rknn_create_mem_from_fd(ctx, out_fd, virt, size, 0);
rknn_set_io_mem(ctx, mem, &input_attrs[0]);
```

**注意**:`rkisp` 的 mainpath 在 4.19 上给的是**单 plane MP(MPLANE)**,`num_planes=1`;EXPBUF 时 `plane=0`。

### 5.3 曝光太暗的真因:模拟增益是 0(2026-10-21 定位并修好)

一开始 640×640 输出均值只有 0.6,肉眼全黑。查下来的顺序:

1. 先以为是 RGA 坏了 → 自检:输入 Y=100 的合成灰面,RGA 输出 **97.3** = `(100−16)×255/219` → RGA 正常,而且暴露了**色彩范围是 limited range** 这个坑
2. 再以为是暗场景 → `ystat` 一量:Y mean 30.2 / p50 25 / **max 255**(其实是场景里有高光)
3. 查 sensor 控制项:

```

  exposure       : min=4 max=2242 value=2242     ← 已经在最大
  analogue_gain  : min=0 max=240  value=0        ← 最小!这才是黑的真因
```

**增益扫描**(每次设完抓一帧统计 Y):

| gain | 0 | 32 | **64** | 96 | 160 |
|---|---|---|---|---|---|
| Y 均值 | 30.2 | 53.8 | **117.3** | 194.0 | 240.8 |
| Y 中位 | 25 | 49 | **123** | 239(接近削顶) | 255(削顶) |

**取 gain = 64**(中位 123,高光 p99 才到 255,没有整体削顶)。

另有偏色:没有 AWB,画面整体偏绿。要好看得跑 `mini3a`(手写 3A)或 rkaiq;零拷贝/perf 表不受影响。

### 5.4 踩到的坑:limited range vs full range

RGA 的 YUV→RGB 走的是 **limited range(16–235)**,而 `rkisp` mainpath 报的 `Quantization: Full Range`。第一版 CPU 参考按 full range 写,同一帧 PSNR 只有 25 dB、看起来"RGA 输出全黑"——实际是暗部被限幅压到 0。判据就是自检那个 97.3 对上了 `(100−16)×255/219`。

> 给 S4 的提醒:NPU 模型输入也是 RGB,如果训练数据是 full-range,这里要在 RGA 之后补一次范围拉伸。

**三模式对比(各 30 帧,最终版 —— 含 EXPBUF 缓存与 int8 位运算优化)**

| 模式 | capture | preproc | rknn_run | postproc | **合计** | 等效帧率 | 每帧拷贝 | **CPU 时间** | CPU 占墙钟 |
|---|---|---|---|---|---|---|---|---|---|
| **A** 拷贝基线 | 5.01 | 34.39 | 39.34 | 13.73 | **92.5 ms** | 10.8 fps | **13,670,400 B**(2 次) | 38.28 ms | 38.8% |
| **B** RGA | 5.01 | 24.18 | 39.80 | 14.40 | **83.4 ms** | 12.0 fps | **1,228,800 B**(1 次) | 29.58 ms | 32.9% |
| **C** 全零拷贝 | 5.01 | **23.51** | 40.94 | **0.42** | **69.9 ms** | **14.3 fps** | **0 B**(0 次) | **12.97 ms** | **17.4%** |

理论 vs 实测拷贝:A = 3840×2160×1.5 + 640×640×3 = 12,441,600 + 1,228,800 = **13,670,400** ✓ 实测一致;B = 1,228,800 ✓;C = 0 ✓。

**结论**

| 指标 | A → C 的变化 |
|---|---|
| 每帧拷贝 | 13,670,400 B → **0 B**(−100%) |
| 端到端延迟 | 92.5 ms → **69.9 ms**(−24%) |
| CPU 时间 | 38.28 ms/帧 → **12.97 ms/帧**(−66%) |
| CPU 占墙钟 | 38.8% → **17.4%** |
| 等效帧率 | 10.8 → **14.3 fps** |

**收益从哪来**
1. `postproc` 13.73 ms → **0.42 ms**:输出直接在 NPU 内存里读,省掉 `rknn_outputs_get` 的拷贝
2. `preproc` 34.39 → 23.51 ms:省掉 12.4 MB 的 NV12 拷贝
3. CPU 大降:除了省拷贝,还因为把 int8 偏置从逐字节改成 8 字节位运算(见下)

**三个非预期发现(本次最有价值的部分)**

**① `rknn_set_io_mem()` 必须用 `RKNN_QUERY_NATIVE_INPUT_ATTR` + `pass_through = 1`**

用普通 `INPUT_ATTR`(pass_through=0)时,runtime 每帧还要做一次内部转换:

| set_io_mem 用的属性 | rknn_run | CPU/帧 |
|---|---|---|
| 普通 `INPUT_ATTR`(pass_through=0) | 75.59 ms | 49.90 ms |
| **`NATIVE_INPUT_ATTR` + pass_through=1** | **41.16 ms** | **23.15 ms** |

不查这一项,就会得出"零拷贝没用"的错误结论。

**② "减 128" 要写成 8 字节异或,不要逐字节**

模型输入是 int8(zp=−128),RGA2 没有 NN 单元,只能自己补这个偏置。第一版逐字节 `t[k] = t[k]-128`,**12.15 ms/帧**(uncached 内存,~100 MB/s)。因为 `(v−128) mod 256 == v ^ 0x80`,改成 8 字节一次异或后:

| 写法 | 耗时 |
|---|---|
| 逐字节 `-128` | 12.15 ms |
| **8 字节 `^= 0x8080808080808080`** | **1.97 ms**(6 倍) |

这一项直接把 C 的 CPU 从 23.2 ms 压到 **12.97 ms**。

**③ EXPBUF 缓存化收益极小(但做了就该做)**

原来每帧 `VIDIOC_EXPBUF` + `close`,改到 setup 阶段导出 4 个 fd 并缓存:

```
预先导出 4 个 dmabuf(耗时 0.12 ms,一次性)
```

preproc 没有明显变化(33.99 → 33.83)→ **说明每帧 EXPBUF 本来就不是瓶颈**,真正的 9 ms 缺口是上面第 ② 条。这次优化本身价值在于"消掉一个每帧系统调用",不是性能来源。

**还留着的优化点**

- 输出侧同样可以 `set_io_mem` 直读(已做);NMS/解码还能向量化
- 若要支持高帧率,应把"降 CPU"变成"跑更多路"(多相机并行),这是零拷贝在该平台真正的价值

### 5.6 多路并行:验证"降 CPU"到底值多少钱(2026-10-21)

**前提**:一个 `/dev/videoN` 只能被一个进程打开,所以"多路"用**同一份输入驱动 N 条独立处理流水线**来模拟(N 个进程,各自持有 rknn context,同时跑 50 次推理)。这样测的是"CPU 能撑几条流水线",正好是零拷贝要回答的问题。

工具:`zc_npu f|g <次数> x /root/out_640.rgb`(f = 拷贝路径,g = 零拷贝路径,均带 `getrusage` 统计)

**原始数据**

| 并发 N | 模式 | 聚合吞吐 | 单路吞吐 | 每路延迟 | 每次推理 CPU | **总 CPU(占单核)** |
|---|---|---|---|---|---|---|
| 1 | f 拷贝 | 16.5 inf/s | 16.5 | 60.6 ms | 17.1 ms | 28.2% |
| 1 | **g 零拷贝** | **20.1 inf/s** | 20.1 | 49.8 ms | **6.2 ms** | **12.5%** |
| 2 | f | 20.5 | 10.2 | 98 ms | 20.2 | 41.4% |
| 2 | **g** | **22.8** | 11.4 | 88 ms | **7.1** | **16.2%** |
| 3 | f | 21.9 | 7.3 | 137 ms | 21.7 | 47.6% |
| 3 | **g** | **23.3** | 7.8 | 128 ms | **9.3** | **21.7%** |
| 4 | f | 22.7 | 5.7 | 175 ms | 24.4 | 55.3% |
| 4 | **g** | **23.5** | 5.9 | 169 ms | **11.7** | **27.5%** |

**结论(和"能跑更多路"的直觉不一样,但更真实)**

1. **聚合吞吐会被 NPU 卡死在 ~23.5 inf/s**(单次推理 41–43 ms),N 从 1 加到 4 只从 20.1 涨到 23.5,再增加并发没有意义。所以零拷贝**不能**换来"更多路推理"。
2. **它换来的是"同样吞吐下的一半 CPU"**:N=4 时两条路径吞吐几乎相同(23.5 vs 22.7 inf/s),但 CPU 是 **27.5% vs 55.3%,正好差一倍**。
3. **每路 CPU 成本也差一倍**(6.2 vs 17.1 ms/次),而且**并发越高差距越稳定**(N=4 时 11.7 vs 24.4)。
4. 省下来的那 ~0.27 个核,在这块板子上是给 **ISP 3A、编码器、网络**用的——这才是零拷贝的实际卖点,而不是"多跑几路检测"。
5. 每路延迟随 N 线性变差(60 → 175 ms),因为只有一颗 NPU;要降延迟得**流水线化**(采集/前处理/推理分线程重叠),而不是加并发。

> 这组数据的口径:输入是同一张 640×640 图,不含采集,所以纯粹是"处理链"的 CPU 成本;真实多路还要加上每路 3840×2160 的采集与 RGA,CPU 会更高,零拷贝的优势只会更明显。

### 5.7 流水线化:采集 / 前处理 / 推理三线程重叠(2026-10-21)

工具:`zerocopy/zc_pipe.cpp`(3 线程 + 3 槽位,**每个槽位一套独立 rknn context + 输入/输出 tensor 内存**)

```
cap 线程 :DQBUF -> 抢空槽
pre 线程 :EXPBUF(已预导出) -> RGA 缩放 -> 8 字节异或补 int8
inf 线程 :rknn_run -> 解码 -> QBUF 还回 V4L2 -> 释放槽位
```

**先说一个前提发现:相机本身只有 12–15 fps**

```
v4l2-ctl --stream-count=30 --stream-to=/dev/null  3840x2160 → 12.3 fps
                                                  1920x1080 → 12.7 fps
```

分辨率和帧率无关(sensor 模式固定,ISP 只是缩放),所以**串行版 69.9 ms/帧其实已经贴着相机上限**。

**负载 1×(相机是瓶颈,两者一样)**

| 版本 | 墙钟 | 吞吐 |
|---|---|---|
| 串行 mode C | 69.9 ms/帧 | 14.3 fps |
| **流水线** | **69.2 ms/帧** | **14.4 fps** |

两边都是采集受限,看不出差别——**这正是"流水线已经没拖后腿"的证据**,不是流水线没用。

**负载 2×(每帧推理两次,把相机上限顶开)**

| 版本 | 每帧耗时 | 吞吐 | 说明 |
|---|---|---|---|
| 串行 mode C | 5 + 23.5 + **81.2** + 0.4 = **110.2 ms** | **9.1 fps** | 前处理与推理串行相加 |
| **流水线** | **88.0 ms** | **11.4 fps** | 关键路径 = max(前处理, 推理) |

**→ 流水线比串行快 25%(11.4 vs 9.1 fps)**,这就是阶段重叠的真实收益。

**结论**

1. 相机 12–15 fps 时,两种实现都是采集受限(14.4 fps),流水线不会凭空变快。
2. 一旦**计算量超过采集周期**(加模型、加路数、加编码),流水线立刻体现价值:2× 负载下 +25%。
3. 流水线的关键路径是 `max(前处理, 推理×次数)`,而不是两者相加——所以要把最慢的那一段优化好(RGA 15.7 ms vs 推理 29 ms,推理是大头)。
4. 每帧延迟随并发线性变差的问题依旧存在(一颗 NPU),真正的解法是**多 NPU 或降模型开销**,不是加线程。

**顺带记一个工具 bug(也是性能教训)**

写 `ystat` 时逐字节扫 Y 平面统计亮度,结果 4K 一帧要 **3.5 秒**——因为 vb2 的 mmap 是 **uncached**,逐字节访问等于每字节一次内存事务(≈2 MB/s)。同一块内存用 `memcpy` 是 **1 GB/s**(mode A 里 12.9 ms 拷 12.4 MB)。**结论:uncached 内存上一定要用宽字长/memcpy,不要逐字节。** 这也解释了为什么 int8 偏置那条改成 8 字节异或能从 12.15 ms 降到 1.97 ms。

## 6. 风险与备选

| 风险 | 备选 |
|---|---|
| rkisp mainpath 的 buffer 可能不允许 EXPBUF(vb2 不总是支持) | 换 `rkisp_mainpath` 的其他 video 节点,或退到 `rkcif`+OV8858 的 RAW 路径测 dmabuf 导出 |
| RGA 不认 rkisp 的 dma-buf 属性(cache/IOMMU) | `importbuffer_fd` 前先 `dma_buf_begin_cpu_access`;或改用 `RgaApi.h` 的老接口 |
| NPU 输入要求 RGB888 且 640×640,色彩空间转换要在 RGA 里做 | `imresize` 支持 `RK_FORMAT_YCbCr_420_SP → RK_FORMAT_RGB_888`,一次搞定 |
| NPU 走 DRM_GEM,`rknn_create_mem_from_fd` 可能要求特定 fd 类型 | 备选:`rknn_create_mem` 由 rknn 自己分配,再用 RGA 直接写进去(仍是零 CPU 拷贝) |

## 7. RAW 域加餐(OV8858)

OV8858 链路是 `rkcif`(RAW10 compact,不是 NV12),拿它做零拷贝的看点是:

- `rkcif` 的 VB2 buffer 直接导出 dmabuf,交给 RGA 做 **RAW10 → RGB** 转换(RGA 不支持 RAW10,需要在 CPU 上解包,或者交给 NPU/ISP)→ 这一步大概率**做不成零拷贝**,正好用来说明"格式不友好时零拷贝的边界在哪"
- 更有价值的做法:OV8858 走 `rkisp`(而不是 rkcif)形成 `RAW10 → ISP → NV12`,再套用本任务书的链路 C
