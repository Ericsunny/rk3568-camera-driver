# 20 - L4 电源管理:ov8858_sm 补 pm_runtime + suspend/resume 验证(2026-10-21)

> 对应诚实清单第 2 条("无 pm_runtime")。**runtime PM 与系统 suspend/resume 都已验证通过**;
> 但"**带着流直接 suspend**"会把整块板子挂死(需断电),这条已记入已知限制。

---

## 1. 改了什么(4 处)

| 位置 | 改动 |
|---|---|
| `s_stream` | 上电不再直接调 `power_on/off`,改成 `pm_runtime_get_sync()` / `mark_last_busy + put_autosuspend()` |
| 新增回调 | `runtime_suspend/resume`(映射到 `power_off/on`)、`system_suspend/resume` |
| `i2c_driver.driver` | 加 `.pm = &ov8858_sm_pm_ops` |
| `probe` / `remove` | probe 末尾 `set_autosuspend_delay(2000) + use_autosuspend + set_active + enable + put_autosuspend`;remove 里 `pm_runtime_disable` |

关键点:`power_on/off` 在 L1-B 已经做成**幂等**(`powered` 标志),所以 runtime PM 反复 resume/suspend 不会把 clk/regulator 引用计数弄乱。

## 3. 系统 suspend/resume(pm_test 模拟,相机空闲时)

> ⚠️ **口径说明(2026-10-22 更正)**:本节用的是 `pm_test=devices` —— **内核自测模式**,跑到设备挂起阶段后由内核自己等 5 秒恢复,**不是真实 suspend**。
> 真实 suspend(`pm_test=none`)在本板**无法验证退出**:板子没有 RTC(`/dev/rtc*` 不存在)、也没有电源键(只有硬开关),不存在任何"人能触发"的唤醒源,`echo mem` 之后只能断电。
> 详见 [`docs/27`](27-稳定性回归.md) §7。所以本节结论只能表述为"**挂起/恢复回调链路正确**",不能表述为"真实 suspend 可用"。

用 `pm_test=devices` 做安全的设备级挂起(5 秒后自动恢复,**不会真的断电**):

```bash
echo devices > /sys/power/pm_test
echo mem > /sys/power/state
```

dmesg:

```
[126.615389] PM: suspend entry (deep)
[126.661363] Freezing user space processes ... (elapsed 0.001 seconds) done.
[126.694188] ov8858-sm 5-0036: system_suspend        ← 我们的回调被调用
[127.148814] PM: suspend debug: Waiting for 5 second(s).
[135.675709] ov8858-sm 5-0036: system_resume         ← 恢复
[135.829324] PM: suspend exit
```

恢复后:**uptime 连续(没重启)**、`v4l2-ctl` 抓帧 **OK**、`runtime_status` 正常回到 active。

> 注意:SSH 会在这个过程里断一次(网卡也被挂起),**不代表板子挂了**,重连即可。

### 3.1 完整业务流验证:开流 → 关流 → 挂起 → 恢复 → 再开流(2026-10-21 通过)

| 阶段 | 动作 | 结果 |
|---|---|---|
| A | 开流 5 帧 | 抓帧 OK,`runtime_status = active` |
| B | 等 3 秒(autosuspend 2s) | `runtime_status = suspended` |
| C | `echo mem > /sys/power/state`(pm_test=devices) | 见下面 dmesg,5 秒后自动恢复 |
| D | 恢复后再开流 5 帧 | **抓帧 OK**,`runtime_status` 回到 active |

```
[53.532066] PM: suspend entry (deep)
[53.607717] ov8858-sm 5-0036: system_suspend
[54.056952] PM: suspend debug: Waiting for 5 second(s).
[62.583893] ov8858-sm 5-0036: system_resume
[62.739184] PM: suspend exit
```

恢复后:**uptime 连续(没有重启)**、抓 5 帧 OK、双路回归也正常(OV8858 30.02 fps / 71.8 MB/s,IMX415 15.00 fps / 178.0 MB/s,与挂起前完全一致)。

→ **"suspend/resume 链路恢复"这条验收通过**(前提是符合 §4 的正确用法:挂起前停流)。

## 4. 已知限制:**带着流 suspend 会把板子挂死**

```bash
v4l2-ctl -d /dev/video0 --stream-mmap --stream-count=300 --stream-to=/dev/null &
echo devices > /sys/power/pm_test
echo mem > /sys/power/state        # ← 这一步之后板子无响应
```

现象:ping 不通、SSH 不通、串口无输出,**看门狗也没有把它拉回来**,只能断电重启。

原因(推断):`rkcif`/`csi2-dphy` 这条链在**流还在跑**的时候被 suspend,设备侧没有正确的 quiesce,in-flight 的 DMA 与 MIPI 接收状态无法恢复,最终卡死在整个系统挂起流程里。

**正确用法(应用层):**

```bash
# 挂起前:先关流
v4l2-ctl -d /dev/video0 --stream-mmap --stream-count=0 2>/dev/null   # 或直接结束采集进程
# 然后才允许 suspend
```

这也符合我们的驱动设计:每次 `s_stream(1)` 都从 `power_on` + 全量寄存器表重来,不依赖 suspend 期间保留状态。

**如果要把"带流 suspend"做对**,需要:
1. `system_suspend` 里先 `ov8858_sm_stop_stream()`(我们已经这么写了),**但不够**——rkcif/CSI 侧也要能 quiesce,那不在 sensor 驱动职责内
2. 或者让上层(应用/框架)保证 suspend 前停流,这是 RK 平台上相机应用的常规做法

## 6. 结论

| 项 | 状态 |
|---|---|
| 驱动补 pm_runtime | ✅ |
| runtime PM 三态迁移 | ✅ 实测 |
| 系统 suspend/resume(相机空闲) | ⚠️ **仅 `pm_test=devices` 模拟**通过(回调被调用、恢复后可用);真实 suspend 无唤醒源,退出无法验证(见 docs/27 §7) |
| 系统 suspend(带流) | ❌ 挂死,需断电;已记为已知限制,给出正确用法 |
| 诚实清单第 2 条("无 pm_runtime") | ✅ 已关闭 |

**工程要点**:runtime PM 不是"加上就完事"——真正的价值在于 `power_on/off` 必须幂等,否则挂起/恢复几次就把 clk/regulator 引用计数弄乱(L1-B 踩过这个坑);另外"能挂起"和"能带着业务负载挂起"是两件事,后者需要整条链路协同。
