# M3 高光与动态范围：能不能把过曝的窗户救回来

> 日期：2026-10-22
> 设备：RK3568 + IMX415（10-bit linear RAW10）+ rkisp（ISP21）+ rkaiq 2022 三件套
> 结论一句话：**高光没有饱和，能救；但这套 2022 组合里 DRC 下发不下去，只能靠 AE 侧牺牲整幅亮度来换。**

---

## 1. 现象

同场景（暗房间 + 中间一扇朝外的窗）下：窗户整片 255、室内偏暗。目视"窗外一片白，什么都看不见"。

## 2. 先回答一个问题：传感器饱和了吗？

如果不饱和，理论上可以靠 tone mapping 把高光压回来；如果饱和了，任何 ISP 处理都救不回来（只有 HDR 多曝光或 ND 滤镜）。

**方法**：不开 3A，用手动曝光做阶梯（gain 固定 4），看高光能不能掉下来。

| 曝光(行) | 平均 Y | ≥250 占比 | ≥240 占比 | p99 | ≤16 占比 |
|---|---|---|---|---|---|
| 600 | 49.03 | 4.66% | 5.22% | 255 | 11.6% |
| 300 | 36.25 | 2.46% | 2.74% | 255 | 23.1% |
| 150 | 28.07 | 1.70% | 1.78% | 255 | 41.6% |
| 75 | 22.09 | **0.00%** | 0.01% | 221 | 74.6% |
| 37 | 17.82 | 0.00% | 0.00% | 145 | 86.9% |

**结论：曝光降到 1/8 时高光完全不裁** → 传感器没饱和，高光可以救。

再算一下高光超出饱和多少：把 exp600 下 ≥250 的像素在 exp75 图上取样，读数为 145/255。考虑 gamma（实测中间调 8 倍曝光只对应 3.31 倍码值，符合 ~2.2 gamma）：

```
线性光强 = (145/255)^2.2 × 8 ≈ 2.4 倍满量程  →  超出约 1.3 档
```

也就是说：**只要压 1.3 档左右，窗户就能保住，但整幅会暗 1.3 档**。这正是"要么亮要么过曝"的两难来源。

## 3. 试 DRC：硬件支持，但这套组合里下发不下去

ISP21 有 DRC（局部色调映射），IQ 里有 `adrc_calib`，但**默认 `Enable = 0`**，而且 `DrcGain` 全是 `0.00390625`（=1/256，等于"不放大"）。

于是做了对照：把 `Enable` 置 1、`DrcGain` 放大 4 倍（0.015625），其余不动，跑 3A 采一帧：

| 配置 | 平均 Y | ≥250 占比 | p50 | ≤16 占比 |
|---|---|---|---|---|
| 默认（DRC 关） | 63.53 | 2.90% | 57.0 | 17.75% |
| DRC 开（gain ×4） | 63.58 | 2.90% | 57.0 | 17.83% |

**逐项一致到小数点后两位 —— DRC 没有任何效果。** 日志给出了原因：

```
[ATMO]:XCAM ERROR rk_aiq_algo_adrc_itf.cpp:160: processing: Ae Proc result is null!!!
[ATMO]:XCAM ERROR rk_aiq_algo_adrc_itf.cpp:176: processing: ae Pre result is null!!!
[CAMHW]:XCAM ERROR CamHwIsp21.cpp:364: get drc params from 3a result failed!
[CAMHW]:XCAM ERROR CamHwIsp21.cpp:429: get drc params from 3a result failed!
```

3A 侧拿不到 DRC 参数（adrc 算法没算出结果），`rkisp` 自然收不到 DRC 配置。**IQ 里那个 `adrc_calib` 字段名/结构与 2022 库的解析器对不上**，属于又一处版本代差（和 §21 的 IQ/库不配套同源）。要修就得改库或改 IQ schema，代价高、收益不确定，本轮不做。

> ⚠️ 这里踩过一个自己挖的坑：第一次对比时拿"上一次会话"的基线帧当参照，得出"DRC 把过曝面积 3.97%→2.90%、暗部 22.9%→17.8%"的结论。后来用同一协议重跑基线，发现基线本身就是 2.90%/17.8% —— 差异来自 AE 收敛状态，不是 DRC。**跨会话的数字不能当对照。**

## 4. 能落地的只有 AE 侧：三档权衡

既然局部色调映射走不通，就只剩"整体曝光换高光"：

| 配置 | 平均 Y | ≥250 占比 | p50 | ≤16(死黑) | 观感 |
|---|---|---|---|---|---|
| 默认（AE setpoint 45） | 63.53 | 2.90% | 57.0 | 17.8% | 亮，窗户过曝 |
| `DySetpoint ×0.85`（setpoint 38） | 38.92 | **1.82%** | 27.0 | 36.6% | 暗，窗户保住 |
| `OverExpCtrl.Enable=1` | 40.27 | **1.84%** | 28.0 | 34.4% | 暗，窗户保住 |

- 两种"高光优先"方案结果几乎一样，但 **`OverExpCtrl` 是自适应的**：只有画面里高光占比超过阈值（`HighLightTh=150`）时才压曝光，普通场景不受影响；直接改 setpoint 是"永远压暗"。
- 所以推荐：**白天逆光场景用 `OverExpCtrl=1`；普通场景保持默认。**

## 5. 结论与后续

| 项 | 结论 |
|---|---|
| 高光是否饱和 | **否**，约超饱和 1.3 档 |
| DRC 能否用 | **不能**，2022 库取不到 adrc 参数（日志 4 条 error，实测零差异） |
| 可用手段 | AE 侧压制（`OverExpCtrl`），代价是整幅暗 1.3 档 |
| 真解 | **IMX415 DOL-HDR（长短曝光 + amerge）**，需 sensor 双曝光模式 + ISP HDR 合成，属下一阶段 |

## 6. 复现

```bash
# 1) 曝光阶梯（不开 3A），判断高光是否可救
sh /root/m3_ladder.sh
# 2) 三条 AE/DRC 臂，各起一次 rkaiq 采一帧
python3 /root/mk_variant.py /root/iq_oe.json overexp
sh /root/m3_arm.sh /root/iq_oe.json overexp
# 3) 切到"高光优先"模式（可逆）
python3 /root/iq_highlight_mode.py status
python3 /root/iq_highlight_mode.py on     # 打开 OverExpCtrl
python3 /root/iq_highlight_mode.py off    # 关回去
```

`tools/iq_highlight_mode.py` 的两个实现细节（都是踩过的坑）：

1. **原地改一个字符，不重排版 JSON**。第一版用 `json.load` + `json.dump` 重写，文件从 331401 → 331402 B，md5 从 `0666ba18` 变成 `57b0188b`，直接把 `tools/install_rkaiq_2022.sh` 的 md5 闸门踩红了。改成"定位 `OverExpCtrl` 块里第一行 `"Enable": N` 做正则替换"后，开关往返 md5 精确回到 `0666ba18ce1e4db30cddc92810587fb1`。
2. **改完立刻 `json.load` 自校验**，值不对就删除临时文件、不替换原文件。
