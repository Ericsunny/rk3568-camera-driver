# 28 · 内核问题闭环：TRY_FMT 污染 ACTIVE 模式 + 停流错误可见性

> 起因（用户 m02956）：固定当前提交 / 内核配置 / 相机模式，复现并修掉两件事：
> ① 任何程序发一次 `VIDIOC_TRY_FMT`，实际采集模式会被改掉；
> ② 停流（`VIDIOC_STREAMOFF` / 异常停流）出错时用户态看不到任何错误。
>
> 验收标准：全部支持格式/分辨率的 TRY_FMT 不改变 `G_FMT` 与实际采集模式；异常停流能拿到**可定位**的错误码。

涉及提交：`driver/ov8858_sm/ov8858_sm.c`（本次修改）
内核：`4.19.232`，#40（修复前）→ **#42**（修复后）
设备：OV8858 @ `/dev/video0`（rkcif），1632×1224 BG10 RAW10

---

## 1. 问题①：TRY_FMT 改掉 ACTIVE

### 1.1 复现（修复前，#40）

`tools/tryfmt_check.sh` 对 pad0 / code `0x3007` 依次 TRY 8 种分辨率，每次 TRY 后立刻 `G_FMT(ACTIVE)`：

```
[ 1] try 1632x1224 -> TRY 1632x1224 | ACTIVE 1632x1224 ok
[ 2] try 1920x1080 -> TRY 1920x1080 | ACTIVE 1920x1080 **CHANGED** (baseline 1632x1224)
[ 3] try 1280x720  -> TRY 1632x1224 | ACTIVE 1632x1224 ok
...
[ 8] try  800x600  -> TRY 1632x1224 | ACTIVE 1632x1224 ok
RESULT=FAIL changed=1/8
```

单次 TRY 也一样，并且**实际采集真的变成了 1080p**：

```
saved_bytes=2211840   (1632x1224 应为 2048*1224=2506752；2211840=2048*1080)
```

注意 1920×1080 恰好是驱动支持的第二模式（`mode_1080p`），其它不在模式表里的分辨率会被回退成 1632×1224，所以只有第 2 项翻车——**这个 bug 只在“TRY 一个真正合法的另一个模式”时触发**，很容易漏测。

### 1.2 根因

`ov8858_sm_set_fmt()` 早期版本不区分 `which`，先把 `fmt->format` 填成模式表里的值，然后**无条件**把驱动内部状态改成该模式：

```c
/* 修复前（示意） */
ov8858_sm_fill_fmt(ov8858, &fmt->format);   /* 无论 TRY 还是 ACTIVE */
ov8858->cur_mode = ...;                     /* ← TRY 也改，污染 ACTIVE */
```

`VIDIOC_SUBDEV_S_FMT(which=TRY)` 的语义是“试算，不改变现状”，rkcif/rkisp 在 `S_FMT(ACTIVE)` 之前普遍会先 `TRY` 一次做校验。于是：**应用只是探一下能不能用 1080p，sensor 就被切到 1080p 了**，而 `G_FMT(ACTIVE)` 走的还是驱动填的 `cur_mode`，两者一起错，看起来“G_FMT 也是对的，但采到的数据大小不对”。

### 1.3 修复

`driver/ov8858_sm/ov8858_sm.c`：

```c
/* ov8858_sm_get_fmt(): TRY 只读 try_format，ACTIVE 才回 cur_mode */
if (fmt->which == V4L2_SUBDEV_FORMAT_TRY) {
#ifdef CONFIG_VIDEO_V4L2_SUBDEV_API
	fmt->format = *v4l2_subdev_get_try_format(sd, cfg, fmt->pad);
#else
	return -ENOTTY;
#endif
} else {
	ov8858_sm_fill_fmt(ov8858, &fmt->format);
}

/* ov8858_sm_set_fmt(): TRY 写完立刻返回，绝不碰 cur_mode */
if (fmt->which == V4L2_SUBDEV_FORMAT_TRY) {
#ifdef CONFIG_VIDEO_V4L2_SUBDEV_API
	*v4l2_subdev_get_try_format(sd, cfg, fmt->pad) = fmt->format;
	return 0;
#else
	return -ENOTTY;
#endif
}

if (ov8858->streaming) {
	dev_err(sd->dev, "set_fmt(ACTIVE) refused while streaming\n");
	return -EBUSY;          /* 出流中改模式一律拒绝 */
}
```

关键就三条：**TRY 早退**、**TRY 只写 try_format**、**出流中拒绝 ACTIVE 改模式**。

### 1.4 验证（修复后，#41 / #42 复测一致）

```
[ 1] try 1632x1224 -> TRY 1632x1224 | ACTIVE 1632x1224 ok
[ 2] try 1920x1080 -> TRY 1920x1080 | ACTIVE 1632x1224 ok    ← 不再被改
[ 3..8] ...                          | ACTIVE 1632x1224 ok
RESULT=PASS changed=0/8

单次 TRY(1920x1080) -> TRY 1920x1080 | ACTIVE 1632x1224 ok   RESULT=PASS

实际采集：saved_bytes=2506752  (2048*1224，确实是 1632x1224 的 10bit RAW)
         抓 10 帧 0.37 s ≈ 27.0 fps
```

`RESULT=PASS` 的判定包含四项：sweep 全绿、单次 TRY 不改 ACTIVE、`v4l2-ctl --get-fmt-video` 仍是 1632×1224、**实际读出的 buffer 字节数**对得上。

## 2. 问题②：停流错误看不到

### 2.1 驱动侧：错误原本被直接丢弃

```c
/* 修复前 */
ov8858_sm_stop_stream(ov8858);        /* 返回值没人看，I2C 写失败也当成功 */
```

改成返回并记录：

```c
static int ov8858_sm_stop_stream(struct ov8858_sm *ov8858)
{
	int ret;

	if (inject_stop_err > 0) {          /* 故障注入，仅用于验证 */
		ret = -inject_stop_err;
	} else {
		ret = ov8858_sm_write_reg(ov8858->client, 0x0100, 0x00);
	}

	if (ret < 0) {
		last_stop_err = ret;            /* 供用户态读取 */
		stop_err_cnt++;
		dev_err(&ov8858->client->dev,
			"stop_stream failed: %d (sensor 可能仍在出流)\n", ret);
	}

	return ret;
}
```

注入后内核日志：

```
ov8858-sm 5-0036: [fault-inject] stop_stream 人为返回 -5
ov8858-sm 5-0036: stop_stream failed: -5 (sensor 可能仍在出流)
```

### 2.2 为什么 `VIDIOC_STREAMOFF` 自己拿不到错误码（V4L2 设计）

- `include/media/videobuf2-core.h:404`：`void (*stop_streaming)(struct vb2_queue *q);` —— **回调是 void**。
- `videobuf2-core.c:1695`：`call_void_qop(q, stop_streaming, q);` —— vb2 用 `call_void` 调它，`vb2_core_streamoff()` 恒返回 0。

也就是说 **`VIDIOC_STREAMOFF` 在 V4L2 里就没有错误返回通道**，任何驱动都不可能让它把 `-EIO` 交给用户态。这是规范限制，不是 rkcif 的锅。

### 2.3 上层还会再吞一次（rkcif）

即使驱动返回了错误，rkcif 也有两处丢弃：

```c
/* drivers/media/platform/rockchip/cif/dev.c:516 / :562 */
ret = v4l2_subdev_call(p->subdevs[i], video, s_stream, on);
if (on && ret < 0 && ret != -ENOIOCTLCMD && ret != -ENODEV)   /* ← 只有 on 才判错 */
	goto err_stream_off;
```

```c
/* capture.c:5432 起：terminal sensor 在停流路径上根本不收 s_stream(0) */
if (p->subdevs[i] == terminal_sensor->sd) {
	if (reset_src == RKCIF_RESET_SRC_ERR_CSI2 || ...) {
		ret = v4l2_subdev_call(..., core, ioctl,
				       RKMODULE_SET_QUICK_STREAM, &on);
	}
} else {
	ret = v4l2_subdev_call(p->subdevs[i], video, s_stream, on);
}
```

所以“停流时 sensor 出错”在整条链路上只能靠**日志**发现，用户态无从判断。

### 2.4 因此提供一个可查询的错误通道（只读 module parameter）

```c
static int last_stop_err;      /* 最近一次停流错误码，0 = 正常 */
static int stop_err_cnt;       /* 累计失败次数 */
module_param(last_stop_err, int, 0444);
module_param(stop_err_cnt, int, 0444);
```

实测（`tools/stop_status_check.sh`，#42）：

```
--- A) 正常停流 ---
STREAMOFF: ret=0 errno=0 (ok)   RESULT=OK_NO_ERROR
  参数: last_stop_err=0   stop_err_cnt=0

--- B) 注入停流失败 -EIO ---
STREAMOFF: ret=0 errno=0 (ok)   RESULT=OK_NO_ERROR      ← 符合 V4L2 语义，必然为 0
  参数: last_stop_err=-5  stop_err_cnt=1                 ← 可定位的错误码
  dmesg: 2 条 'stop_stream failed'

--- C) 恢复注入后 ---
  参数: last_stop_err=-5  stop_err_cnt=1                 ← 保留，便于事后取证
```

用户态用法：

```sh
cat /sys/module/ov8858_sm/parameters/last_stop_err
cat /sys/module/ov8858_sm/parameters/stop_err_cnt
```

## 4. 诚实清单

| 项 | 状态 | 说明 |
|---|---|---|
| TRY_FMT 不污染 ACTIVE | ✅ 已修已验 | 8 例 sweep + 单次 TRY + 实际字节数三重校验 |
| 出流中 ACTIVE 改模式 | ✅ 返回 `-EBUSY` | 驱动侧拦截；应用若绕过 rkcif 直接调 subdev 也会被拒 |
| 停流出错驱动层可见 | ✅ | 返回 `-5` + `dev_err` |
| 停流出错用户态可见 | ⚠️ 部分 | `STREAMOFF` 按 V4L2 规范恒返回 0；通过只读参数 `last_stop_err` / `stop_err_cnt` 暴露 |
| rkcif 向上传播 | ❌ 未改 | 属厂商层，改动面大且 `stop_streaming` 是 void，改了也到不了用户态；已在 §2.3 记录证据 |
| 开流失败传播 | 未改动 | `dev.c` 对 `on` 的错误本来就会 `goto err_stream_off`，无需改 |
