# 29 · 可靠性工程：双消费者、有界队列、buffer 生命周期与零拷贝消费者

> 项目定位的落地主线：把现有 RK3568 相机链路做成 **可诊断、能承受消费者故障、可控恢复** 的可靠性工程。
> 本文记录 **阶段性成果与真实进度**，未完成项单独列在 §8，不把没测过的场景写成已支持。
>
> 当前状态（2026-10-23）：内核闭环已完成并验证（docs/28，内核 #42）；用户态服务 `camd` 已有
> 双消费者 + 有界队列 + 引用计数归还 + RGA 零拷贝消费者，队列深度/buffer 数的边界已实测出公式；
> 自动回归脚本 `tools/regress.sh` 已写好待跑；故障注入只覆盖到"消费者内部故障"一类。

---

## 1. 整体链路

```
OV8858/V4L2 采集(/dev/video0, BG10, multiplanar)    RKISP 主流(/dev/video5, NV12)
        │  每个 buffer 带引用计数 + DMA-BUF fd(VIDIOC_EXPBUF)
        ├──► 实时分析消费者(RT 队列: 满则丢最旧，保新帧)
        │        └── 可选:RGA 直接吃 dmabuf fd 做缩放/降采样(零拷贝)
        └──► 取证/保存消费者(EV 队列: 限速，默认丢最旧)
                              │
        所有消费者都 release → refcount 归零 → QBUF 还给内核
```

三条硬约束：

1. **采集端不能被慢消费者拖死** —— 队列有固定深度且默认丢最旧，任何一条都不可能无限堆内存。
2. **每个 buffer 的所有权清楚** —— 只有"所有消费者 + 硬件"都结束才归还 V4L2。
3. **DMA-BUF 共享 fd ≠ 访问已完成** —— 能否 QBUF 由引用计数决定，不由"fd 还在""分析函数返回了"决定。

## 2. 用户态状态机（camd）

```
INIT ──► RUNNING ──► DRAINING ──► STOPPED(rc=0)
           │
           └──► FAULT ──► RECOVERING ──(成功)──► RUNNING
                            └──(失败)──► STOPPED(rc≠0) + 诊断包
```

- **停止标志不是 `volatile`**：用 `atomic_bool g_run / g_draining` + `pthread_mutex/cond` 广播唤醒；
  消费者在 `q_pop()` 里阻塞在条件变量上，drain 时立即被唤醒并退出，不会漏掉最后一帧。
- **有界恢复**：`--recover-attempts N`（默认 1）。第一次失败后重开会话一次，再失败就
  **干净退出 + 打诊断包**（`/root/camd_diag_<时间>/`：metrics.json、dmesg 尾部、meminfo、fd 列表、
  `last_stop_err`、线程/RSS），不无限重启、不把故障藏掉。
- **错误传播**：`fatal(code, fmt, ...)` 统一入口 —— 记录错误码/消息、置 `g_run=false`、唤醒所有队列，
  线程 join 后由 session 决定是否恢复。

## 3. buffer 生命周期（当前实现）

```c
n->seq = 帧序号; n->ts_us = DQBUF 时刻; refs = 1;   /* capture 自己一份 */
node_get(n); q_push(Q_RT, n);      /* 实时消费者一份 */
node_get(n); q_push(Q_EV, n);      /* 取证消费者一份 */
node_release(n);                   /* capture 释放自己那份 */
...
node_release(n);  /* 消费者处理完；refs 归零才 QBUF */
```

关键点：

- `refs` 用 `atomic_int`，`node_release()` 里 `fetch_sub` 到 1 的那个线程负责 `QBUF`；
- 队列**丢弃**（丢最旧 / 背压超时）同样走 `node_release()`，所以"丢帧"不会漏还 buffer；
- 指标里 `frames` 与 `frames_returned` 必须相等（差值为在途帧），这是"没有泄漏"的直接证据；
- 每个 buffer 在 `VIDIOC_EXPBUF` 时导出一个 **DMA-BUF fd**，消费者可直接交给 RGA/NPU，不需要 CPU 拷贝。

## 4. 两条队列的策略差异

| 队列 | 深度(默认) | 满了怎么办 | 适用 |
|---|---|---|---|
| `Q_RT` 实时分析 | 4 | **丢最旧**（保新帧），计 `dropped` | 检测/预览，新鲜度优先 |
| `Q_EV` 取证保存 | 2 | **丢最旧**（`--ev-policy block` 改为有界阻塞 200 ms） | 存图/取证，宁可丢也不无限堆 |

`--ev-fps` 对取证分支限速（默认 5 fps）。**默认 `drop` 是这次改的**：第一版用"有界阻塞"，
结果取证消费者一旦跟不上，背压直接反压到采集，帧率从 30 掉到 5（见 §5.2 的 B 臂）。
现在取证队列满时丢最旧，采集永不被它拖住。

## 5. 板上实测

测试设备与格式：`/dev/video0` = OV8858 BG10 1632×1224（30.3 fps 上限）；
`/dev/video5` = RKISP NV12 3840×2160（15.2 fps 上限）。全部为板上实测。

### 5.1 buffer 数与队列深度的边界（决定性实验）

慢消费者 = 每帧 200 ms（`--fault slow`），目的就是让它跟不上；此时看采集帧率会不会塌。

| `-b` buffer | `--rt-depth` | `--ev-depth` | 深度和+2 | 实测 fps | RT 丢帧 | 结论 |
|---|---|---|---|---|---|---|
| 4 | 4 | 2 | 8 | **5.07** | 0 | 采集被饿死 |
| 8 | 2 | 2 | 6 | 30.22 | 123 | 正常 |
| 8 | 3 | 2 | 7 | 30.22 | 122 | 正常 |
| 8 | 4 | 2 | **8** | 30.22 | 121 | 正常（刚好卡线） |
| 8 | 5 | 2 | **9** | **20.47** | 108 | 开始饿死 |
| 8 | 6 | 2 | 10 | **12.77** | 116 | 明显饿死 |

分界线正好在 `nbufs = rt_depth + ev_depth + 2`：等号成立时正常，超出 1 就开始掉。
`+2` 是两处不可省的占用：**采集侧 1 帧在途** + **每个消费者各 1 帧正在处理**。

### 5.2 取证队列策略对照（300 帧，正常消费者）

| 臂 | 策略 | fps | RT 丢帧 | EV 处理/丢 |
|---|---|---|---|---|
| A | `--ev-policy drop`（默认） | **20.19** | 0 | 76 / 224 |
| B | `--ev-policy block`（第一版行为） | **5.05** | 0 | 300 / 0 |

B 臂 5 fps 就是"取证背压反压采集"的直接后果；A 臂虽然也只有 20 fps（`-b 4` 且 RT 队列深度 4，
本身就在边界上），但已经不受取证消费者牵连。**这就是把 EV 默认改成丢最旧的原因。**

### 5.3 慢消费者不拖死采集（`-b 8`）

| 臂 | 消费者 | fps | RT 处理/丢 | RT p99 |
|---|---|---|---|---|
| C1 | 200 ms/帧 | **30.17** | 100/162 | 0 µs |
| C2 | 正常 | 30.17 | 100/0 | 1 µs |

慢消费者只是让 RT **丢帧变多**，采集帧率一点没掉 —— 这是设计要求的行为：
"消费者慢"应该体现为丢帧率上升，而不是整条链路降速。

### 5.4 RGA 零拷贝消费者 vs CPU 拷贝

实时消费者做同一件事：把整帧缩到小图（4K→640×360、BG10→408×306）。

**4K NV12 3840×2160 → 640×360（100 帧）**

| 臂 | 单帧耗时 avg | p99 | CPU user | CPU sys | CPU 合计 |
|---|---|---|---|---|---|
| nop（只取帧） | — | 1 µs | 0.014 s | 0.195 s | 0.209 s |
| CPU 拷贝 + 4×4 降采样 | 24.21 ms | 27.48 ms | 2.524 s | 0.121 s | **2.645 s** |
| **RGA 零拷贝（dmabuf fd）** | **6.34 ms** | **6.40 ms** | 0.007 s | 0.354 s | **0.361 s** |

→ 单帧耗时 **3.8× 更短**，CPU **7.3× 更少**（每帧 26.5 ms → 3.6 ms）。

**OV8858 BG10 1632×1224 → 408×306（100 帧）**

| 臂 | 单帧耗时 avg | p99 | CPU user | CPU sys | CPU 合计 |
|---|---|---|---|---|---|
| nop | — | 1 µs | 0.008 s | 0.142 s | 0.150 s |
| CPU 拷贝 + 降采样 | 19.32 ms | 24.33 ms | 1.923 s | 0.130 s | **2.053 s** |
| **RGA 零拷贝** | **5.43 ms** | **5.50 ms** | 0.021 s | 0.234 s | **0.255 s** |

→ 单帧 **3.6× 更短**，CPU **8.0× 更少**（每帧 20.5 ms → 2.55 ms）。

两条臂的 fps 都没变（15.15 / 30.32），因为消费者耗时（6 ms / 5 ms）远小于帧间隔（66 ms / 33 ms）——
**说明瓶颈仍在采集，不在消费者**；零拷贝的收益体现在 CPU 与余量上，不是帧率上。这点必须写清楚，不能吹成"提帧率"。

RGA 用法要点（本板 librga 1.9.2 / 头文件 `/usr/include/rga`）：

```c
src = wrapbuffer_fd_t(dmabuf_fd, w, h, stride, h, RK_FORMAT_YCbCr_420_SP); /* NV12 */
src = wrapbuffer_fd_t(dmabuf_fd, w, h, stride, h, RK_FORMAT_YCbCr_400);    /* 8bit 数据(如 BG10 按灰度搬) */
st  = imresize_t(src, dst, 0, 0, 0, 1);   /* dst 用 wrapbuffer_virtualaddr_t 建 */
```

- 编译：`gcc -O2 -pthread -DHAVE_RGA -I/usr/include/rga -o camd_rga camd.c -lrga -ldl`
  （不带 `-DHAVE_RGA` 也能编，RGA 代码整段被 `#ifdef` 排除）；
- 本内核 `struct v4l2_plane` **没有** `bytesperline` 字段，stride 要从 `S_FMT` 回填的
  `fmt.pix_mp.plane_fmt[0].bytesperline` 取（1632×1224 BG10 实测 2048）。

### 5.5 配置自洽性检查（写进程序，不只写在文档）

`camd` 启动时算 `need = rt_depth + ev_depth + 2`，超过 `nbufs` 直接告警：

```
WARN: 配置不自洽 —— buffer=4, 但 rt_depth(4)+ev_depth(2)+2=8
      ⥀ 采集可能被饿死(帧率断崖)。建议 -b 8 或降低队列深度。
```

实测：`-b 4` + 慢消费者触发告警并掉到 5 fps；`-b 8` + 同样参数不告警、保持 30 fps。

## 6. 队列与 buffer 怎么定（结论）

**buffer 数不是"排队长度"，是"在途资产"**：采集在途 1 + 每个消费者处理中 1 + 每个队列里排队的 N。

```
nbufs ≥ rt_depth + ev_depth + 2
```

**队列深度决定延迟，不决定吞吐**：30 fps 下深度 d ⇒ 最大额外排队延迟 d×33 ms。
由单帧耗时反推：

```
理想深度 d = ⌈单帧耗时 × 帧率⌉
```

- 单帧 10 ms @30 fps → d=1（排队只加延迟）
- 单帧 50 ms @30 fps → d=2（33–66 ms，可接受）
- 单帧 200 ms @30 fps → 理论 d=6，但延迟 200 ms 且需要 10 个 buffer；**此时应丢帧保实时，而不是加大队列**

**本项目取值**：`-b 8 --rt-depth 3 --ev-depth 2 --ev-fps 10`（8 ≥ 3+2+2 留 1 帧余量，
最大排队延迟 100 ms）。实测：`30.27 fps`、RT 丢 0 帧、EV 按 10 fps 限速丢 78 帧（符合设计意图）。
