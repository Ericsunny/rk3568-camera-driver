# 29 · 可靠性工程：双消费者、有界队列、buffer 生命周期与零拷贝消费者

> 项目定位的落地主线：把现有 RK3568 相机链路做成 **可诊断、能承受消费者故障、可控恢复** 的可靠性工程。
> 本文记录 **阶段性成果与真实进度**，未完成项单独列在 §8，不把没测过的场景写成已支持。
>

> **自动回归 `tools/regress.sh` 已跑通（10/10 启停、1800 帧零泄漏、背压对照、一次性故障恢复、持续故障放弃）**；

## 1. 整体链路

```
OV8858/V4L2 采集(/dev/video0, BG10, multiplanar)    RKISP 主流(/dev/video5, NV12)
        │  每个 buffer 带引用计数 + DMA-BUF fd(VIDIOC_EXPBUF)
        ├──► 实时分析消费者(RT 队列: 满则丢最旧，保新帧)
        │        └── 可选:RGA 直接吃 dmabuf fd 做缩放/降采样(零拷贝)
        └──► 取证/保存消费者(EV 队列: 限速，默认丢最旧)
                              │
        所有消费者都 release → refcount 归零 → QBUF 还给内核
```

三条硬约束：

1. **采集端不能被慢消费者拖死** —— 队列有固定深度且默认丢最旧，任何一条都不可能无限堆内存。
2. **每个 buffer 的所有权清楚** —— 只有"所有消费者 + 硬件"都结束才归还 V4L2。
3. **DMA-BUF 共享 fd ≠ 访问已完成** —— 能否 QBUF 由引用计数决定，不由"fd 还在""分析函数返回了"决定。

## 2. 用户态状态机（camd）

```
INIT ──► RUNNING ──► DRAINING ──► STOPPED(rc=0)
           │
           └──► FAULT ──► RECOVERING ──(成功)──► RUNNING
                            └──(失败)──► STOPPED(rc≠0) + 诊断包
```

- **停止标志不是 `volatile`**：用 `atomic_bool g_run / g_draining` + `pthread_mutex/cond` 广播唤醒；
  消费者在 `q_pop()` 里阻塞在条件变量上，drain 时立即被唤醒并退出，不会漏掉最后一帧。
- **有界恢复**：`--recover-attempts N`（默认 1）。第一次失败后重开会话一次，再失败就
  **干净退出 + 打诊断包**（`/root/camd_diag_<时间>/`：metrics.json、dmesg 尾部、meminfo、fd 列表、
  `last_stop_err`、线程/RSS），不无限重启、不把故障藏掉。
- **错误传播**：`fatal(code, fmt, ...)` 统一入口 —— 记录错误码/消息、置 `g_run=false`、唤醒所有队列，
  线程 join 后由 session 决定是否恢复。

## 3. buffer 生命周期（当前实现）

```c
n->seq = 帧序号; n->ts_us = DQBUF 时刻; refs = 1;   /* capture 自己一份 */
node_get(n); q_push(Q_RT, n);      /* 实时消费者一份 */
node_get(n); q_push(Q_EV, n);      /* 取证消费者一份 */
node_release(n);                   /* capture 释放自己那份 */
...
node_release(n);  /* 消费者处理完；refs 归零才 QBUF */
```

关键点：

- `refs` 用 `atomic_int`，`node_release()` 里 `fetch_sub` 到 1 的那个线程负责 `QBUF`；
- 队列**丢弃**（丢最旧 / 背压超时）同样走 `node_release()`，所以"丢帧"不会漏还 buffer；
- 指标里 `frames` 与 `frames_returned` 必须相等（差值为在途帧），这是"没有泄漏"的直接证据；
- 每个 buffer 在 `VIDIOC_EXPBUF` 时导出一个 **DMA-BUF fd**，消费者可直接交给 RGA/NPU，不需要 CPU 拷贝。

## 4. 两条队列的策略差异

| 队列 | 深度(默认) | 满了怎么办 | 适用 |
|---|---|---|---|
| `Q_RT` 实时分析 | 4 | **丢最旧**（保新帧），计 `dropped` | 检测/预览，新鲜度优先 |
| `Q_EV` 取证保存 | 2 | **丢最旧**（`--ev-policy block` 改为有界阻塞 200 ms） | 存图/取证，宁可丢也不无限堆 |

`--ev-fps` 对取证分支限速（默认 5 fps）。**默认 `drop` 是这次改的**：第一版用"有界阻塞"，
结果取证消费者一旦跟不上，背压直接反压到采集，帧率从 30 掉到 5（见 §5.2 的 B 臂）。
现在取证队列满时丢最旧，采集永不被它拖住。

## 5. 板上实测

测试设备与格式：`/dev/video0` = OV8858 BG10 1632×1224（30.3 fps 上限）；
`/dev/video5` = RKISP NV12 3840×2160（15.2 fps 上限）。全部为板上实测。

### 5.1 buffer 数与队列深度的边界（决定性实验）

慢消费者 = 每帧 200 ms（`--fault slow`），目的就是让它跟不上；此时看采集帧率会不会塌。

| `-b` buffer | `--rt-depth` | `--ev-depth` | 深度和+2 | 实测 fps | RT 丢帧 | 结论 |
|---|---|---|---|---|---|---|
| 4 | 4 | 2 | 8 | **5.07** | 0 | 采集被饿死 |
| 8 | 2 | 2 | 6 | 30.22 | 123 | 正常 |
| 8 | 3 | 2 | 7 | 30.22 | 122 | 正常 |
| 8 | 4 | 2 | **8** | 30.22 | 121 | 正常（刚好卡线） |
| 8 | 5 | 2 | **9** | **20.47** | 108 | 开始饿死 |
| 8 | 6 | 2 | 10 | **12.77** | 116 | 明显饿死 |

分界线正好在 `nbufs = rt_depth + ev_depth + 2`：等号成立时正常，超出 1 就开始掉。
`+2` 是两处不可省的占用：**采集侧 1 帧在途** + **每个消费者各 1 帧正在处理**。

### 5.2 取证队列策略对照（300 帧，正常消费者）

| 臂 | 策略 | fps | RT 丢帧 | EV 处理/丢 |
|---|---|---|---|---|
| A | `--ev-policy drop`（默认） | **20.19** | 0 | 76 / 224 |
| B | `--ev-policy block`（第一版行为） | **5.05** | 0 | 300 / 0 |

B 臂 5 fps 就是"取证背压反压采集"的直接后果；A 臂虽然也只有 20 fps（`-b 4` 且 RT 队列深度 4，
本身就在边界上），但已经不受取证消费者牵连。**这就是把 EV 默认改成丢最旧的原因。**

### 5.3 慢消费者不拖死采集（`-b 8`）

| 臂 | 消费者 | fps | RT 处理/丢 | RT p99 |
|---|---|---|---|---|
| C1 | 200 ms/帧 | **30.17** | 100/162 | 0 µs |
| C2 | 正常 | 30.17 | 100/0 | 1 µs |

慢消费者只是让 RT **丢帧变多**，采集帧率一点没掉 —— 这是设计要求的行为：
"消费者慢"应该体现为丢帧率上升，而不是整条链路降速。

### 5.4 RGA 零拷贝消费者 vs CPU 拷贝

实时消费者做同一件事：把整帧缩到小图（4K→640×360、BG10→408×306）。

**4K NV12 3840×2160 → 640×360（100 帧）**

| 臂 | 单帧耗时 avg | p99 | CPU user | CPU sys | CPU 合计 |
|---|---|---|---|---|---|
| nop（只取帧） | — | 1 µs | 0.014 s | 0.195 s | 0.209 s |
| CPU 拷贝 + 4×4 降采样 | 24.21 ms | 27.48 ms | 2.524 s | 0.121 s | **2.645 s** |
| **RGA 零拷贝（dmabuf fd）** | **6.34 ms** | **6.40 ms** | 0.007 s | 0.354 s | **0.361 s** |

→ 单帧耗时 **3.8× 更短**，CPU **7.3× 更少**（每帧 26.5 ms → 3.6 ms）。

**OV8858 BG10 1632×1224 → 408×306（100 帧）**

| 臂 | 单帧耗时 avg | p99 | CPU user | CPU sys | CPU 合计 |
|---|---|---|---|---|---|
| nop | — | 1 µs | 0.008 s | 0.142 s | 0.150 s |
| CPU 拷贝 + 降采样 | 19.32 ms | 24.33 ms | 1.923 s | 0.130 s | **2.053 s** |
| **RGA 零拷贝** | **5.43 ms** | **5.50 ms** | 0.021 s | 0.234 s | **0.255 s** |

→ 单帧 **3.6× 更短**，CPU **8.0× 更少**（每帧 20.5 ms → 2.55 ms）。

两条臂的 fps 都没变（15.15 / 30.32），因为消费者耗时（6 ms / 5 ms）远小于帧间隔（66 ms / 33 ms）——
**说明瓶颈仍在采集，不在消费者**；零拷贝的收益体现在 CPU 与余量上，不是帧率上。这点必须写清楚，不能吹成"提帧率"。

RGA 用法要点（本板 librga 1.9.2 / 头文件 `/usr/include/rga`）：

```c
src = wrapbuffer_fd_t(dmabuf_fd, w, h, stride, h, RK_FORMAT_YCbCr_420_SP); /* NV12 */
src = wrapbuffer_fd_t(dmabuf_fd, w, h, stride, h, RK_FORMAT_YCbCr_400);    /* 8bit 数据(如 BG10 按灰度搬) */
st  = imresize_t(src, dst, 0, 0, 0, 1);   /* dst 用 wrapbuffer_virtualaddr_t 建 */
```

- 编译：`gcc -O2 -pthread -DHAVE_RGA -I/usr/include/rga -o camd_rga camd.c -lrga -ldl`
  （不带 `-DHAVE_RGA` 也能编，RGA 代码整段被 `#ifdef` 排除）；
- 本内核 `struct v4l2_plane` **没有** `bytesperline` 字段，stride 要从 `S_FMT` 回填的
  `fmt.pix_mp.plane_fmt[0].bytesperline` 取（1632×1224 BG10 实测 2048）。

### 5.7 恢复路径踩到的真问题:同一进程重开设备 EBUSY

第一次跑故障注入时，"有界恢复"的重开 **必然失败**：

```
FATAL[2]: 实时分析消费者故障(注入)
>>> 有界恢复 第 1/1 次
FATAL[1]: S_FMT 1632x1224 失败: Device or resource busy
```

排查过程（都是实测排除）：

1. 不是 fd 泄漏 —— 加 `ls /proc/self/fd` 打印，重开时进程只剩 stdin/stdout/stderr；
2. 不是时序太急 —— 在 S_FMT 上做了 1 s 的 EBUSY 重试，仍然一直 busy；
3. **是 vb2 队列没被释放** —— rkcif 的 `rkcif_s_fmt_vid_cap_mplane()` 用
   `vb2_is_busy(&stream->vnode.buf_queue)` 判忙，而只 `close(fd)` 不会立刻把 `num_buffers` 清零。

修法（规范拆除顺序）：`dev_close()` 里先 `munmap()`，再 `VIDIOC_REQBUFS(count=0)`，最后才 `close()`。
改完立即复测：恢复后 60 帧全部跑满（§5.6 第 5 行）。

**这条值得记下来**：它正好说明"有界恢复"不能只在应用层重试，还要把设备侧状态（vb2 队列）
显式拆干净——否则恢复逻辑看着写了、实际从没成功过。

### 5.8 RKNN 消费者（NPU 零拷贝，`--rknn MODEL`）

> ⚠️ **阶段说明(2026-10-23)**:本节描述的是**实验阶段的 native IO 尝试**,不是当前服务路径。
> 当前 `camd --rknn` 走的是 `RGA 缩放到本地 RGB → rknn_inputs_set`,**不是零拷贝**;见 [docs/31 程序与证据对照表](31-程序与证据对照表.md)。

**动机**：L3 双摄、任务书要求"实时分析"；前面 §5.4 只做到 RGA 缩放，还没把 NPU 接进来。
本节把"采集 buffer → RGA → NPU 输入 tensor"整条链做成零拷贝，CPU 一次都不搬。

**实现要点**（`tools/camd.c`，`-DHAVE_RKNN`）：

1. `rknn_init` 后取 `RKNN_QUERY_NATIVE_INPUT_ATTR`（不是普通 `INPUT_ATTR`），
   `rknn_create_mem(size_with_stride)` 拿到带 fd 的 tensor 内存，**`pass_through = 1`** 后
   `rknn_set_io_mem`——不设 `pass_through` 的话 runtime 每帧还要再做一次格式转换（41 ms → 75 ms 的坑，见 docs/18）。
2. 同一个 fd 交给 RGA：`wrapbuffer_fd_t(in_mem->fd, 640, 640, 640*3, 640, RK_FORMAT_RGB_888)`，
   `imresize_t(采集 dmabuf, npu 内存)` 直接把缩放结果写进 NPU 输入。
3. **输出也必须用 native 属性**（`RKNN_QUERY_NATIVE_OUTPUT_ATTR` + `rknn_create_mem` + `rknn_set_io_mem`）。
   第一版混用了「native 输入 + 普通输出属性」，`rknn_set_io_mem` 阶段直接 **SIGBUS**。
4. 加了阶段心跳 `/root/camd_stage.log`（`cap seq=N` / `rga in fd=` / `rga out st=` / `npu run in|out`），
   每次 `fsync`——卡死重启后能直接看出死在哪一步，不用猜。

**板上实测**（kernel `#42`，`librknnrt 2.3.2`，模型 `yolov8n_rk3568_i8.rknn`，输入 `[1,640,640,3]` INT8 zp=-128）：

| 通道 | 规模 | 帧数 | rc | 端到端帧率 | 消费者耗时 | 拆分 |
|---|---|---|---|---|---|---|
| `/dev/video0`（OV8858，rkcif） | 1632×1224 BG10 | 50 | 0 | 21.44 fps | 48.11 ms/帧 | RGA 7.11 ms + `rknn_run` 41.0 ms |
| `/dev/video5`（IMX415，ISP） | 1920×1080 NV12 | 100 | 0 | 15.00 fps | 66.46 ms/帧 | RGA 11.92 ms + `rknn_run` 54.54 ms |
| `/dev/video5`（IMX415，ISP） | 3840×2160 NV12 | 20 | 0 | 13.64 fps | 78.85 ms/帧 | RGA 25.78 ms + `rknn_run` 53.07 ms |

- 三组的 `npu ok` 都等于帧数、`err=0`、`dropped=0`；心跳日志逐帧完整（`rga out st=1`、`npu run out ret=0`）。
- **NPU 单次推理在这块板上是 41–55 ms**（同模型同输入 640×640）：单独循环跑 41 ms，和真实采集并发时 53–55 ms——差的 12 ms 是 RGA/DDR 抢带宽。写性能必须写这个区间，不能只挑 41 ms。
- RGA 从采集 dmabuf 缩放的耗时随源分辨率线性增长：1632×1224 → 7.1 ms，1080p → 11.9 ms，4K → 25.8 ms。这条也决定了 4K 全流程不可能快。
- 三组端到端帧率都被 NPU 卡住（15.0 / 13.6 fps），采集本身是 26–30 fps，所以**这条链路现在的瓶颈明确是 NPU，不是采集、不是 RGA、不是队列**。

**诚实的边界**：

- 只有 `rknn_run` + 触摸一个输出字节，**没有做 YOLOv8 解码/NMS**；所以现在报的是"推理跑通 + 时延"，不是"检测到几个目标"。完整解码在 `zerocopy/zc_npu.cpp`（L2 阶段的工具）里，接进 camd 是下一步。
- OV8858 通道是 BG10 原始 Bayer，RGA 只是当 8 bit 数据搬，NPU 看到的不是正常图像 → **该通道的检测结果无意义，只能用来验证零拷贝链路**。要出真检测必须走 ISP 的 NV12 通道。

### 5.9 又一次踩同一个坑：`kill -9` 打正在出流的进程

跑 1080p 前发现板上有两个 camd（前一条命令被 PowerShell 的 `|` 拆坏，重复启动），清理时用了
`kill -9 $(pidof camd)`，结果整机卡死（`rkisp_stream_stop id:0 timeout`），只能断电重启。

**规则（第二次写进文档，说明它真的容易犯）**：

- 停采集**只能** `kill -TERM`（camd / grab / st_burn 都装了 SIGINT/SIGTERM 处理，会走正常 STREAMOFF）；
- 清理残留用 `pidof <名字>` 逐个 TERM，等 2 s 再检查，**不要** `pkill -f`（会匹配到 ssh 自己的命令行）；
- 4K 采集 + NPU/RGA 同跑时，buffer 保持 `-b 4`（已验证 20 帧稳定）；要加 buffer 先做小规模验证。


## 6. 队列与 buffer 怎么定（结论）

**buffer 数不是"排队长度"，是"在途资产"**：采集在途 1 + 每个消费者处理中 1 + 每个队列里排队的 N。

```
nbufs ≥ rt_depth + ev_depth + 2
```

**队列深度决定延迟，不决定吞吐**：30 fps 下深度 d ⇒ 最大额外排队延迟 d×33 ms。
由单帧耗时反推：

```
理想深度 d = ⌈单帧耗时 × 帧率⌉
```

- 单帧 10 ms @30 fps → d=1（排队只加延迟）
- 单帧 50 ms @30 fps → d=2（33–66 ms，可接受）
- 单帧 200 ms @30 fps → 理论 d=6，但延迟 200 ms 且需要 10 个 buffer；**此时应丢帧保实时，而不是加大队列**

**本项目取值**：`-b 8 --rt-depth 3 --ev-depth 2 --ev-fps 10`（8 ≥ 3+2+2 留 1 帧余量，
最大排队延迟 100 ms）。实测：`30.27 fps`、RT 丢 0 帧、EV 按 10 fps 限速丢 78 帧（符合设计意图）。

### 5.10 RKNN 消费链路验收:实现正确,但受成像质量限制不可用

这一节回答一个问题:**`--rknn` 消费者到底能不能用?** 结论是**通道打通、后处理正确、真实场景不可用**,三件事都有证据。

#### 用标准图证明实现正确(对照组)

用 YOLO 官方 `bus.jpg`(137 419 B)转成 640x640 RGB,走 `--image` 离线模式:

```
IMAGE /root/bus640.rgb -> det=4 max_score=0.760
  box 0: cls=0 score=0.76  [108,286,169,486]   person
  box 1: cls=0 score=0.75  [451,352,504,532]   person
  box 2: cls=0 score=0.73  [  8,364,154,558]   person
  box 3: cls=5 score=0.71  [214,229,560,819]   bus
```

类别、分数、位置全部正确。**模型加载、native 输入属性、RGA 缩放、DFL 解码、NMS 整条链路是对的。**

#### 实拍:框出来了,但框的内容是错的

四轮实拍(4K NV12,`/dev/video5`,每次 20~30 帧,`ok == 帧数`、`err=0`,管道本身零异常):

| 轮次 | 关键设置 | `score_max` | 检出 | 框落在哪 |
|---|---|---|---|---|
| 1 | 判据 `obj x cls`(原始) | 0.29~0.39 | 0 | 无 |
| 2 | `--no-obj-mul`(官方判据) | 0.627 | 21/21 帧 | **整个画面**,`cls=6 train` 0.50 |
| 3 | +退化框过滤 + `--rot90` | 0.449 | 13 | 画面上半幅,`cls=62 chair` 0.36 |
| 4 | 调整机位后 | **0.851** | 1~2/帧 | **空白桌板**,`cls=9 traffic light` 0.76~0.85 |

第 2 轮的判据修正是有价值的:它把 `det` 从恒 0 变成每帧有框,并证明之前 `obj x cls` 会把分数系统性压低约 40%。但修好之后暴露出的真问题是**框的内容不对**。

![整帧被判成 train](evidence/2026-10-23-detection/det_fullframe_train.png)

![上半幅被判成 chair](evidence/2026-10-23-detection/det_half_chair.png)

![重新调整机位后的全景](evidence/2026-10-23-detection/det_reposition_overview.png)

第 4 轮最值得看:置信度 0.85 的 `traffic light` 框,放大后里面是一片**没有任何细节的绿色桌板**:

![框内特写](evidence/2026-10-23-detection/det_blank_desk_zoom.png)

#### 为什么不可用(三个原因叠加)

1. **失焦**:P0 的对焦是在 1.5 m 对着对焦图做的,换机位后景深不匹配,桌面整体是糊的;
2. **白平衡偏色**:`--wb` 的灰度世界在室内暖光 + 大片高光下把画面压成橄榄绿;
3. **高光过曝**:曝光 1200 时窗户整块爆成紫色,占画面约 1/3。

在这样的输入上,yolov8n 的纹理特征不成立——它会给"什么都没有"的区域一个 0.85 的置信度,这比"检测不到"更难堪,也更能说明问题不在阈值。

#### 诚实结论与边界

- **能验的**:RTSP 前置的这条消费链路(队列、buffer 生命周期、RGA 零拷贝、NPU 绑定、后处理)全部正确,可用 `bus.jpg` 稳定复现;
- **不能验的**:本板在无 3A 直采条件下的真实场景检测。要让它可用,必须先解决成像质量(对焦/白平衡/曝光),或让 camd 从 3A 已经拉起的流里取帧(架构改动);
- **不要做的事**:降阈值凑框。实测降到 0.10 只会得到更多同类误检,并且当次直接把板子跑挂。

#### 5.10.1 更正(2026-10-23,M7 第 1/2 步):去掉 `--wb` 后检测恢复正确

上文的结论建立在两个**错误的默认设置**上,现已定位并推翻:

1. `--wb` 灰度世界白平衡本身是**破坏性**的:室内暖光 + 大面积高光下它把画面压成橄榄绿,再乘以偏绿的白平衡,模型看到的颜色彻底失真;
2. 曝光 1200/增益 96 使窗户过曝、整体发白。

**同一场景,只把 `--wb` 去掉、曝光回 300/增益 64**,`camd --no-obj-mul` 100% 帧命中:

```
rt seq=19 det=2 max=0.57 [0]cls=77 s=0.57 234,134,386,486
                        [1]cls=56 s=0.41 554,269,639,449
```

`cls=77` 正是 COCO 的 **teddy bear**,框精确落在毛绒玩偶上(见 `evidence/2026-10-23-m7-detection/m7_teddy_bear_0.57.png`),`cls=56` 是画面右缘的一把椅子。

**因此上文的"真实场景不可用"结论作废**,准确表述是:

> 消费链路正确;检测在**固定成像参数(曝光 300/增益 64、不加白平衡、不加旋转)** 下对毛绒玩偶给出 0.57 的 `teddy bear` 框,判定正确。此前的失败来自软件侧的破坏性白平衡与过曝,不是传感器本身。

**仍然成立的部分:** 不能靠降阈值凑框;`obj x cls` 判据确实会系统性压低分数;`bus.jpg` 对照仍是最快的冒烟验证。


## 9. 故障注入全覆盖与资源曲线（收尾）

### 9.1 新增注入点

| 注入 | 开关 | 做法 | 期望 |
|---|---|---|---|
| 慢消费者 | `--fault slow` | 消费者每帧 sleep | 采集不被拖死，RT 丢帧上升 |
| 消费者故障 | `--fault fail` | 消费者内 fatal | 一次有界恢复 |
| **DQBUF 超时** | `--fault dqbuf --fault-at N` | **故意不归还 buffer**，空闲队列见底 | 连续 3 次超时 → 触发恢复 |
| **停流失败** | `--fault stopfail --stopfail-n 5` | 写驱动参数 `inject_stop_err=5` | JSON 里 `stop_err_param=-5` |

DQBUF 超时不是"假装超时"：它真的把 buffer 扣住不还，让 `vb2` 的可用队列耗尽，poll 必然等到超时。
停流失败也不是模拟——驱动里 `ov8858_sm_stop_stream()` 真的返回 `-EIO`，只是 V4L2 的 `stop_streaming` 是 `void` 回调，
错误回不到用户态，所以落在只读参数 `last_stop_err` 里（见 docs/28）。

### 9.2 资源曲线

新增采样线程：每 500 ms 读一次 `/proc/self/statm`（RSS）与 `times()`（CPU tick），结束时折算成百分比写入 metrics JSON。

### 9.3 实测（`/dev/video0` 1632×1224，`-b 8 --rt-depth 3 --ev-depth 2 --ev-fps 10`）

| 用例 | 结果 |
|---|---|
| T1 正常 300 帧 | `frames=300 returned=300 fps=30.12 rss_max=24.7 MB cpu=3.02% dq_timeouts=0` |
| T2 DQBUF 超时（持续坏） | `rc=3`，扣留 8 个 buffer → 3 次超时 → `FATAL[3]` → 恢复 1 次后放弃 |
| T2b 同故障但 `--fault-once` | `rc=0`，`frames=200 returned=200 fps=30.17 dq_timeouts=3` —— **坏一次 → 恢复 → 跑满** |
| T3 停流失败注入 | `stop_err_param=-5`，`frames_returned=60`，进程正常退出 |
| T4 慢消费者 200 ms/帧 | 采集仍 30.1 fps（RT 丢帧上升） |

### 9.4 一个必须写清楚的边界

故障期间 `frames_returned < frames`（T2 里 45 帧只还了 37 帧）：那 8 个 buffer 是被**注入逻辑扣住**的，
设备关闭时由内核统一回收，不是泄漏。判据仍然是**故障窗口之外**的 `frames == frames_returned`。

### 9.5 覆盖情况

| 故障 | 覆盖 |
|---|---|
| 慢消费者 | ✅ |
| 消费者内部故障 | ✅ |
| DQBUF 超时 | ✅（新增） |
| 停流失败 | ✅（驱动侧注入 + 只读参数取证） |
| RGA 失败 | ⚠️ 未单独注入（走消费者故障路径） |
| RKNN 失败 | ⚠️ 未单独注入（同上） |

## 10. ISP 生命周期矩阵（rkaiq_3A × 采集，2026-10-26 实测）

> 背景：docs/35 旧版写"3A 独占 /dev/video5，必须 stop+disable+重启"；docs/31 §8
> 又实测"3A active 时 cam_rtsp 可直接采集"。两套说法并存说明 ISP mainpath /
> params / stats 的生命周期没有统一模型。本节用一组对照实验把它钉死。
> 全部结论在 #47 内核实测；实验原始输出见 `evidence/2026-10-26-ISP生命周期矩阵/`。

### 10.1 矩阵

| 格 | 起始状态 | 动作 | 实测结果 | 结论 |
|---|---|---|---|---|
| A4 | 3A 停(空闲) | evrec 直采 60s+3 触发 | 3 事件全落盘,14.9fps | **停 3A 后无需重启**（旧 docs/35 的"必须重启"作废） |
| M2 | 3A 停(空闲) | `systemctl start rkaiq_3A` | active,无 rkisp 报错 | 空闲态 start 安全（即开机自启同路径） |
| A1 | 3A active | evrec 全链(--detect+rtsp+触发) | 3 事件,det 分 0.745~0.814(对比固定曝光 0.61~0.75 **不降反升**),10.3fps(带检测已知负载),RTSP 实拉 68 帧 | **共存成立**（与 docs/31 §8 一致,主链从 cam_rtsp 扩展到 evrec） |
| A6 | 3A active | `--fault-sim` 触发 evrec 链路恢复 | 重开 video5 成功,30 帧稳定复位 | **有界恢复与 3A 并存** |
| A2 | 3A active,采流中 | `systemctl stop rkaiq_3A` | 在跑的流**暂时无恙**;evrec 退出 STREAMOFF 时 `rkisp_stream_stop id:0 timeout` | wedge 不发生在 stop 3A 瞬间,而在之后任何一次 STREAMOFF |
| A5 | A2 之后 | 新开 video5(st_burn) | 3/3 fail,无首帧;复测仍 fail | **新打开者全灭**,唯一恢复=重启 |

### 10.2 错误归因表

| 症状 | 谁造成 | 恢复路径 |
|---|---|---|
| `S_FMT: EBUSY` | video5 被其他采流进程持有（`ls -l /proc/*/fd \| grep video5` 找真凶）；**不是 3A 本身**（A1 已证 3A active 可开） | 结束持有进程 |
| `rkisp_stream_stop id:0 timeout` + 之后 DQBUF 全阻塞 | 3A 在采流中被 stop/kill（ISP params/stats 通路随 3A 消失,mainpath 停不下来） | **重启**（唯一已验证恢复） |
| params buffer 尺寸/提交错误 | librkaiq 与 IQ 版本错配（docs/21/28 的历史问题,与生命周期无关） | 三件套回滚方案,见 docs/21 §9 |

### 10.3 params / stats 节点归属（#52 实测）

| 节点 | Card type | 能力 | 角色 |
|---|---|---|---|
| `/dev/video12` | `rkisp-statistics` | META_CAPTURE(`0x84a00000`) | **stats**:3A 读取的硬件统计 |
| `/dev/video13` | `rkisp-input-params` | META_OUTPUT(`0x8c200000`) | **params**:3A 写回的参数 |
| `/dev/video7` / `/dev/video8` | `rkisp_rawwr0` / `rawwr2` | 视频捕获(`0x84201000`) | **不是** params/stats(历史文档里"video7 stats / video8 params"的说法已作废) |

- **3A 常驻时**:`params`/`stats` 由 `rkaiq_3A_server` 独占,采集程序只碰 `/dev/video5`,**不要打开 video12/13**;
- **自写 3A 时**(mini3a 路线):由用户程序接管 video12(读 stats)/ video13(写 params),此时不要同时跑 `rkaiq_3A`;
- 节点号随内核/`status` 变化:换内核后用 `v4l2-ctl --list-devices` + `--info` 的 Card type 复核,不要硬编码。

### 10.4 操作规则（由此矩阵导出）

1. **常规使用：3A 常驻,采集程序直接开流**——AE/AWB 生效,检测分数还更好（A1）；
2. 需要独占压测时：干净停 3A 后**直接采,不必重启**（A4/M2）；
3. **红线：任何时候不要在采流中 stop/kill 3A**（A2/A5）；
4. 链路抖动交给 evrec `--recover`（A6）,它与 3A 并存；
5. 一键栈：`tools/run_3a_stack.sh`（断言 3A active→evrec+RTSP+周期触发→指标）。
