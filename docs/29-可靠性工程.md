# 29 · 可靠性工程(进行中)：双消费者、有界队列与 buffer 生命周期

> 项目定位的落地主线：把现有 RK3568 相机链路做成 **可诊断、能承受消费者故障、可控恢复** 的可靠性工程。
> 本文记录 **阶段性成果与真实进度**，未完成项单独列在 §7，不把没测过的场景写成已支持。
>
> 当前状态（2026-10-22 收工）：内核闭环已完成并验证（docs/28）；用户态服务 `camd` 第一版已在板上跑通，
> 双消费者 + 有界队列 + 引用计数归还可运行；故障注入与自动回归脚本、P95/P99 验收数据 **尚未完成**。

---

## 1. 整体链路

```
OV8858/V4L2 采集(/dev/video0, multiplanar)
        │  每个 buffer 带引用计数
        ├──► 实时分析消费者(RT 队列: 满则丢最旧，保新帧)
        └──► 取证/保存消费者(EV 队列: 限速 + 有界阻塞/超时丢)
                              │
        所有消费者都 release → refcount 归零 → QBUF 还给内核
```

三条硬约束：

1. **采集端不能被慢消费者拖死** —— 两条队列都有固定深度，任何一条都不可能无限堆内存。
2. **每个 buffer 的所有权清楚** —— 只有“所有消费者 + 硬件”都结束才归还 V4L2。
3. **DMA-BUF 共享 fd ≠ 访问已完成** —— 能否 QBUF 由引用计数决定，不由“fd 还在”“分析函数返回了”决定。

## 2. 用户态状态机（camd）

```
INIT ──► RUNNING ──► DRAINING ──► STOPPED(rc=0)
           │
           └──► FAULT ──► RECOVERING ──(成功)──► RUNNING
                            └──(失败)──► STOPPED(rc≠0) + 诊断包
```

- **停止标志不是 `volatile`**：用 `atomic_bool g_run / g_draining` + `pthread_mutex/cond` 广播唤醒；
  消费者在 `q_pop()` 里阻塞在条件变量上，drain 时立即被唤醒并退出，不会漏掉最后一帧。
- **有界恢复**：`--recover-attempts N`（默认 1）。第一次失败后重开会话一次，再失败就
  **干净退出 + 打诊断包**（`/root/camd_diag_<时间>/`：metrics.json、dmesg 尾部、meminfo、fd 列表、
  `last_stop_err`、线程/RSS），不无限重启、不把故障藏掉。
- **错误传播**：`fatal(code, fmt, ...)` 统一入口 —— 记录错误码/消息、置 `g_run=false`、唤醒所有队列，
  线程 join 后由 session 决定是否恢复。

## 3. buffer 生命周期（当前实现）

```c
n->seq = 帧序号; n->ts_us = DQBUF 时刻; refs = 1;   /* capture 自己一份 */
node_get(n); q_push(Q_RT, n);      /* 实时消费者一份 */
node_get(n); q_push(Q_EV, n);      /* 取证消费者一份 */
node_release(n);                   /* capture 释放自己那份 */
...
node_release(n);  /* 消费者处理完；refs 归零才 QBUF */
```

关键点：

- `refs` 用 `atomic_int`，`node_release()` 里 `fetch_sub` 到 1 的那个线程负责 `QBUF`；
- 队列**丢弃**（丢最旧 / 背压超时）同样走 `node_release()`，所以“丢帧”不会漏还 buffer；
- 指标里 `frames` 与 `frames_returned` 必须相等（差值为在途帧），这是“没有泄漏”的直接证据。

## 4. 两条队列的策略差异

| 队列 | 深度(默认) | 满了怎么办 | 适用 |
|---|---|---|---|
| `Q_RT` 实时分析 | 4 | **丢最旧**（保新帧），计 `dropped` | 检测/预览，新鲜度优先 |
| `Q_EV` 取证保存 | 2 | **有界阻塞 200 ms**，超时丢并计数 | 存图/取证，宁可丢也不无限堆 |

`--ev-fps` 对取证分支限速（默认 5 fps），避免写盘把整条链路拖慢。

## 5. 板上实测（第一版，200 帧）

```json
{ "rc": 0, "device": "/dev/video0", "size": "1632x1224",
  "frames": 200, "frames_returned": 200, "qbuf_errors": 0, "fatal": 0,
  "first_frame_ms": 58.41, "elapsed_ms": 39445.91, "fps": 5.08,
  "rt": {"processed": 200, "dropped": 0, "p95_us": 0, "p99_us": 1},
  "ev": {"processed": 200, "dropped": 0, "p95_us": 0, "p99_us": 1} }
```

读数说明（**都是实测，不美化**）：

- `frames == frames_returned == 200`、`qbuf_errors=0` → 200 帧全部按引用计数归还，无泄漏。
- `fps` 只有 **5.08** —— 因为这次用了 `--ev-fps 5`，取证分支限速后 `Q_EV` 满了走**有界阻塞**，
  把采集线程也压到了 5 fps。**这不是 bug，是当前策略的直接后果**，也说明“取证背压会反压到采集”。
  待办：把 EV 改为“限速 + 超时立即丢”（不阻塞采集），或给 EV 单独一个拷贝线程，让采集永远不等消费者。

## 6. 复现

```sh
# 板上（camd 已编译为 /root/camd）
./camd -n 200 --analyze-ms 5 --ev-fps 5 --json /root/camd_smoke.json
./camd -d /dev/video0 -w 1632 -h 1224 -f BG10 -n 0            # 一直跑
./camd --fault fail --recover-attempts 1 --json /root/f.json   # 故障注入(见 §7)
```

源码：[`tools/camd.c`](../tools/camd.c)（单文件，板上 `gcc -O2 -pthread -o camd camd.c -ldl`）。
证据：[`evidence/2026-10-22-camd/`](../evidence/2026-10-22-camd/)。
