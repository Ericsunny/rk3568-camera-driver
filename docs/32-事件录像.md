## 事件前后录像（evrec）—— 设计、实测与判据

### 1. 为什么不用 camd 直接写

采集/检测（camd）与录像的失败模式不同：检测关心“每帧处理完没”，录像关心“事件前后 N 秒不被丢”。
混在一个进程里，任一环卡住都会同时毁掉两者。所以独立成 `tools/evrec.c`。

### 2. 结构

```
V4L2 采集 → MPP H.264 编码 → 环形缓冲(字节上限) → 触发 → 从最近 IDR 起 → .h264 + .json
```

- `--pre N` / `--post N`：事件前后秒数；
- `--ring-mb M`：内存硬上限，满了丢最旧（**冲突时以字节为准**）；
- `--trigger FILE` 或 `SIGUSR1`：两种触发源，文件方式供 camd 后续接入；
- `MPP_ENC_SET_HEADER_MODE = EACH_IDR`：**每个 IDR 自带 SPS/PPS**，保证任意切片自包含。

### 3. 两个真 bug（都已修）

| 现象 | 根因 | 修法 |
|---|---|---|
| 码流解出 0 帧 | 录到的片段里**没有 SPS/PPS**（MPP 默认只在首帧输出头） | `SET_HEADER_MODE=EACH_IDR` |
| 2 个 IDR 却有 2 组重复参数集 | 早期手工注入头 + 编码器自带头，重复 | 关闭手工注入 |

`ev1.h264`（坏）：`NAL {1:62, 5:2, 6:4}`，首字节是 SEI。
`ev6.h264`（好）：`NAL {1:40, 5:2, 6:4, 7:2, 8:2}`，`first_nal = 7`。

### 4. 判据：解码帧数 = JSON 帧数 **− 1**

实测对照（关键）：

| 码流 | 编码帧数 | 解码帧数 |
|---|---|---|
| `ref30.h264`（`mpp_enc_probe` 生成，已知 30 帧） | 30 | **29** |
| `ev6.h264`（evrec 切片） | 42 | **41** |

**`mpp_dec_probe` 固定少解一帧**，与本项目录像逻辑无关（已知帧数的对照流同样少一帧）。
因此判据写成 `decoded == frames - 1`；`41/42` 属**通过**。

早期误判为“末帧未 flush”，加空包 EOS 后仍是 41 —— 假设被推翻，记在此处避免重复走。

### 5. 实测数据

```
>>> 触发 seq=71 ts=5015.6ms -> pre_i=44 (丢弃到 IDR)
>>> 写出 /root/ev/ev6.h264 (42 帧) + ev6.json
FILE ev6.h264 bytes 1528472
NAL 50 {1:40, 5:2, 6:4, 7:2, 8:2} first_nal 7
解出 41 帧
```

JSON 逐帧记录 `seq / ts_ms / abs_ms / bytes / key`，可反查每一帧。
