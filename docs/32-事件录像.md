## 事件前后录像（evrec）—— 设计、实测与判据

### 1. 为什么不用 camd 直接写

采集/检测（camd）与录像的失败模式不同：检测关心“每帧处理完没”，录像关心“事件前后 N 秒不被丢”。
混在一个进程里，任一环卡住都会同时毁掉两者。所以独立成 `tools/evrec.c`。

### 2. 结构

```
V4L2 采集 → MPP H.264 编码 → 环形缓冲(字节上限) → 触发 → 从最近 IDR 起 → .h264 + .json
```

- `--pre N` / `--post N`：事件前后秒数；
- `--ring-mb M`：内存硬上限，满了丢最旧（**冲突时以字节为准**）；
- `--trigger FILE` 或 `SIGUSR1`：两种触发源，文件方式供 camd 后续接入；
- `MPP_ENC_SET_HEADER_MODE = EACH_IDR`：**每个 IDR 自带 SPS/PPS**，保证任意切片自包含。

### 3. 两个真 bug（都已修）

| 现象 | 根因 | 修法 |
|---|---|---|
| 码流解出 0 帧 | 录到的片段里**没有 SPS/PPS**（MPP 默认只在首帧输出头） | `SET_HEADER_MODE=EACH_IDR` |
| 2 个 IDR 却有 2 组重复参数集 | 早期手工注入头 + 编码器自带头，重复 | 关闭手工注入 |

`ev1.h264`（坏）：`NAL {1:62, 5:2, 6:4}`，首字节是 SEI。
`ev6.h264`（好）：`NAL {1:40, 5:2, 6:4, 7:2, 8:2}`，`first_nal = 7`。

### 4. 判据：解码帧数 = JSON 帧数 **− 1**

实测对照（关键）：

| 码流 | 编码帧数 | 解码帧数 |
|---|---|---|
| `ref30.h264`（`mpp_enc_probe` 生成，已知 30 帧） | 30 | **29** |
| `ev6.h264`（evrec 切片） | 42 | **41** |

**`mpp_dec_probe` 固定少解一帧**，与本项目录像逻辑无关（已知帧数的对照流同样少一帧）。
因此判据写成 `decoded == frames - 1`；`41/42` 属**通过**。

早期误判为“末帧未 flush”，加空包 EOS 后仍是 41 —— 假设被推翻，记在此处避免重复走。

### 5. 实测数据

```
>>> 触发 seq=71 ts=5015.6ms -> pre_i=44 (丢弃到 IDR)
>>> 写出 /root/ev/ev6.h264 (42 帧) + ev6.json
FILE ev6.h264 bytes 1528472
NAL 50 {1:40, 5:2, 6:4, 7:2, 8:2} first_nal 7
解出 41 帧
```

JSON 逐帧记录 `seq / ts_ms / abs_ms / bytes / key`，可反查每一帧。

### 6. 未完成

- **接检测触发**：camd 的 `cls==0` 检出写触发文件，evrec 监听（接口已留 `--trigger`）；
- **MP4 封装**：先不做，`.h264 + .json` 已能证明切片正确，封装 bug 会掩盖切片问题；
- **长时间运行**：目前一次触发即退出，需改成循环触发并落多份文件。

## 5. 合并进 evrec 与三个真 bug（第二轮）

把 RGA + RKNN 检测搬进 `evrec` 后，事件录像从"手动触发"变成"检测自动触发"，也让三个此前看不见的 bug 暴露出来。

### 5.1 移植过程中的三个真 bug

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | 无法用 `MPP_ENC_GET_HEADER` 取头 | 该宏在本版头文件里叫 `MPP_ENC_SET_HEADER_MODE` + `MPP_ENC_HEADER_MODE_EACH_IDR` | 改用 `control(MPP_ENC_SET_HEADER_MODE)` |
| 2 | `score_max` 恒为 `0.000`，偶发进程直接消失 | **`rknn_query(RKNN_QUERY_OUTPUT_ATTR)` 前没设 `attr.index`**，9 次查询全返回 0 号张量的属性 | 循环里 `memset` + `attr[i].index = i`；输出个数用 `RKNN_QUERY_IN_OUT_NUM`（类型 `rknn_input_output_num`） |
| 3 | 触发后只写出 6 帧，随机 6~87 帧 | `pre_i` 存的是**环形下标**，触发到 dump 之间 `ring_head` 前移，下标记已经指向别的帧 | 存 `seq`，dump 前按 `seq` 回查下标 |

第 2 条的诊断过程值得记：`score_max` 精确等于 `0.000` 不是"没检测到"（那会是 0.28~0.39 的噪声底），而是网络看到了全零输入 / 输出元数据读错。加了三处探针后一次定位：`[npu] in: sz=1228800 mean=139 rgb0=4/10/3 int8_0=-124`（输入正确）→ `[npu] out0 size=409600 b0=5`（输出也正确）→ 差别只在 `index`。

### 5.2 两个时序问题

- **启动即触发**：人已经在画面里，第 3 帧就满足 `连续 3 帧`，此时环里只有 3 帧，`pre` 窗口为空。加**预热闸门**：`ring_cnt < pre_sec * 15` 时忽略触发（不清 `g_streak`，攒够后立即触发）。
  - 注意：第一版闸门用 `(ts - t_start) < pre_sec*1000` 判断，**没生效**——`ts` 与 `t_start` 的作用域不一致。改用环内帧数后立刻正确（触发时刻从 542 ms 推迟到 2956 ms）。
- **pre 窗口偏短**：回退到时间点后取"往后第一个 IDR"，会跳到下一个 GOP 的 IDR，把中间一段丢掉（6 帧）。改成**往前找最近 IDR**，前置帧从 6 帧变成 40 帧（≈2.7 s）。

### 5.3 多事件与命名

- dump 完后复位环与触发状态，**同一进程继续等下一个事件**，输出 `-00`、`-01` 编号；`--max-events N` 控制退出。
- 输出名加时间戳前缀，长跑不覆盖。
  - **限制**：本板无 RTC，未联网时文件名时间不可信（实测 `20240618`）。

### 5.4 验收

```
>>> 触发 seq=260 ts=25400.9ms -> pre_i=220 pre_seq=220 (ring_cnt=260 head=0 pushed=260)
>>> 事件 1 完成, 继续等待下一个事件
>>> 触发 seq=301 ts=29397.3ms -> pre_i=15 pre_seq=286 (ring_cnt=30 head=0 pushed=30)
>>> 事件 2 完成, 继续等待下一个事件
```

| 项 | 结果 |
|---|---|
| 检测触发（连续 3 帧 + 分数 0.45 + 类别 0） | ✅ |
| 预热闸门 | ✅ 攒够 pre 才触发 |
| pre 窗口 | ✅ 40 帧 ≈ 2.7 s |
| 多事件 | ✅ 同进程连录 2 个，`-00/-01` |
| 码流可解码 | ✅ `42 → 41`（`mpp_dec_probe` 判据） |

### 5.5 架构收敛：evrec 是唯一产品形态

`/dev/video5` 只能被一个进程独占，所以"camd 写触发文件、evrec 监听"的**跨进程方案根本不成立**——两者会抢同一个设备，后者 `S_FMT` 直接 `EBUSY`。

因此 `camd` 里的 `--ev-trigger` 已删除。定位改为：

- **`evrec`**：唯一的产品形态（采 → 编 → 判 → 触发 → 落盘 → 循环）；
- **`camd`**：纯验证工具（队列/消费者/故障注入/RGA vs CPU 对比），不再承担产品职责。

这条边界写在这里，是为了避免后来的人再去尝试跨进程触发。

## 6. 视频 OSD（烧进码流）

`--osd` 把 `#<源帧序号>` 和相对时间烧进编码前的 NV12 帧：左上角 174×42 黑底，5×7 点阵放大 2 倍，两行（`#22` / `t 00:01.816`）。看录像时不用再对着 `.json` 数帧。

### 6.1 只写 Y 平面

NV12 的 UV 是 **2×2 共享**：给一个字形像素写 UV，等于同时给相邻 4 个亮度像素上色。白字描边上会出现彩色毛边，色度块还会被编码器反复重用、白耗码率。纯灰阶字只需要 Y，改 Y 在视觉上就是"白色字 + 黑底"。

### 6.2 stride 取回填值，不假设等于 width

行可能有 padding，`stride` 不一定等于 `width`。拿 width 当步长，每行都会错位，字会斜着拉花。`S_FMT` 回填的 `plane_fmt[0].bytesperline` 存在 `cap.stride`（evrec.c:131）。这个值必须三处一致：写 Y、`memcpy` 进编码缓冲、`prep:hor_stride`（evrec.c:963 / 968 / 975）。本板 1920×1080 实测 `bytesperline = 1920`，但代码不依赖这一点。

### 6.3 seq 语义：源帧序号，不是编码包序号（第一版是错的）

第一版的 `#` 直接用主循环的 `seq`，而 `seq++` 当时写在 **`encode_get_packet` 的包循环里** —— 那是编码包计数，不是源帧计数。1 源帧 = 1 包时两者恰好相等，所以 48 帧的录像没暴露问题；一旦某帧吐出 2 个包（SPS/PPS 单独成包、码控拆包），OSD 编号就会 +2，和 `.json` 错开。

现在改成：帧序号只在 `DQBUF` 成功后自增一次——

```c
/* evrec.c:947-950 */
/* 帧序号在这里 +1: 一次 DQBUF = 一个源帧。编码器一帧可能吐出
 * 多个包(SPS/PPS 单独成包等), 但包循环里只读 frame_seq, 所以
 * OSD 的 # 与 .json 的 seq 永远按源帧递增, 不会被包数带偏。 */
frame_seq = seq++;
```

包循环里 `seq` 只读，同一帧的所有包共用 `frame_seq`（evrec.c:999-1001），OSD 在 `encode_put_frame` 之前取同一变量（evrec.c:966）。`.json` 从"每帧一条"改成"每包一条"，并加两个字段：

| 字段 | 含义 |
|---|---|
| `seq` / `frame_seq` | 源帧序号，两者同值；`seq` 保留只为不破坏已有解析脚本 |
| `pkt` | 帧内包序号（从 0 起）。本次实测 49 条记录全是 `pkt=0`，即 1 包/帧 |

### 6.4 时间基准是"本进程第一帧"，不是切片首帧

`g_osd_ms = ts - t_start`，与 `.json` 的 `ts_ms` 同基准（`t_start = t0_ms`，进程第一帧）。**不是**事件切片首帧，这是有意的取舍：烧字发生在采集侧，那一刻还不知道这一帧会不会被触发、`pre` 窗口会回退到哪里（`pre_i` 要等触发、再往前找 IDR 才确定）。要做"切片内相对时间"，只能在 `dump` 时把整段重编一遍 —— 为几行字付一次二次编码的代价，不成比例。

代价是看录像时 `t 00:01.8` 读作"进程起来后 1.8 s"，不是"事件前 0.2 s"。要知道切片起点，用 `#` 号对 `.json` 的 `first_idr_ts_ms` 即可（下节）。

### 6.5 逐帧核对：OSD 读回 vs .json

把录像解码后，用同一套 5×7 字模反读左上角（`/root/osd_probe`，临时工具未入库），48 帧逐帧比对：

| 解码帧 | OSD 读回 | `.json` |
|---|---|---|
| `f000` | `#22` `t 00:01.816` | `list[0].seq=22` `ts_ms=1834.4` |
| `f022` | `#44` `t 00:03.282` | `list[22].seq=44` `ts_ms=3302.9` |
| `f047` | `#69` `t 00:04.949` | `list[47].seq=69` `ts_ms=4967.0` |

**48 帧全部一致**（48/48），`seq` 22..69 连续；`.json` 多出的第 49 条 `seq=70` 正好是解码器丢掉的末帧（见第 4 节判据：解码帧数 = JSON 条数 − 1）。

OSD 时间恒比 `ts_ms` **小 18.0 ms**（14.0~20.9）。不是误差，是打点时刻不同：OSD 取 `DQBUF` 时刻（evrec.c:967），`ts_ms` 在 `ring_push` 里打点（evrec.c:740），中间隔着 RGA/NPU/编码的流水线延迟。同样的差也出现在 `first_idr_ts_ms` 上（1834.4 vs 1816）。

### 6.6 码率影响：+0.35%，不显著

先按"同场景、同参数、只切 `--osd`"录了三对现场片段（1920×1080、gop=22、4000 kbps、pre=2/post=1、ring=64 MB、各 49 帧）：

| 对照 | 关 OSD | 开 OSD | Δ |
|---|---|---|---|
| 第 1 对 | 1,036,086 B | 1,040,468 B | +0.42% |
| 第 2 对 | 1,061,822 B | 1,042,473 B | −1.82% |
| 第 3 对 | 955,507 B | 934,096 B | −2.24% |

靠不住：同一状态的两段之间就差 **−10.0%**（关 vs 关）和 **−10.4%**（开 vs 开），差一个量级。现场比对的分辨率不足以判定 OSD 的效应。

所以做确定性对照：把同一段 48 帧 `.h264` 解码出来，用**完全相同的编码器配置**重编两遍，唯一变量就是"是否烧字"（临时工具 `reenc.c`，未入库）：

| 项 | 关 OSD | 开 OSD | Δ |
|---|---|---|---|
| 总字节 | 825,705 | 828,568 | **+2,863（+0.35%）** |
| 字节/帧 | 17,202.2 | 17,261.8 | +0.35% |
| 折算码率 @15 fps | 2,064.3 kbps | 2,071.4 kbps | +7.1 kbps |
| 3 个 IDR | 303,622 | 305,608 | +0.65% |
| 45 个 P | 522,083 | 522,960 | +0.17% |

绝对值比现场的 21,670 字节/帧低约 22%：重编是离线灌帧、喂的是解码后的画面，传感器噪声已被解码器滤掉一层，码控也没有实时抖动。两个 pass 条件完全相同，所以只看 Δ。

画质（两段现场片段解码对比）：Y 均值 30.98 → 31.03；去掉顶部 48 行的 PSNR **47.07 dB**（41.35~49.97），全画面 34.65 dB —— 差异全部来自 OSD 自己画的那些像素。

**结论：OSD 让码率涨 0.35%，远低于 5% 的显著线。** 成本集中在 IDR（+0.65%，文字边缘首次出现），P 帧几乎不变（+0.17%）。码率不构成拒绝 OSD 的理由。
