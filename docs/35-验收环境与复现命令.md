## 4. 从零复现

### 4.1 准备（每次重启后都要做）

**2026-10-26 修订**：旧版这里写"必须 stop+disable 3A 并重启"——与 docs/31 §8 及
2026-10-26 的生命周期矩阵实测（docs/29 §10）矛盾，已作废。现行规则：

```bash
# 常规复现:什么都不用做。3A 开机自启(active),采集程序直接开 /dev/video5 即可,
# AE/AWB 生效(实测检测分数比固定曝光还高,见 docs/29 §10.1 A1 格)
systemctl is-active rkaiq_3A    # 确认 active 即可

# 需要独占压测时:干净停 3A 后直接采,不必重启(实测 A4 格)
systemctl stop rkaiq_3A

# ★ 唯一红线:不要在采流中 stop/kill 3A —— 之后任何一次 STREAMOFF 都会
#   rkisp_stream_stop timeout,ISP wedge,新打开者全灭,唯一恢复=重启(A2/A5 格)
```

> 旧版"3A 独占 video5/S_FMT EBUSY 是 3A 造成"的归因是错的:EBUSY 的真凶是
> 其他采流进程残留(用 `ls -l /proc/*/fd | grep video5` 找),3A active 不阻止
> 采集(docs/31 §8、docs/29 §10)。

> ~~**这是最大的坑**：`systemctl stop rkaiq_3A` 之后**不重启直接开流**，`/dev/video5` 会 `DQBUF timeout`；反过来 3A 运行中直接开流会 `S_FMT: Device or resource busy`。~~
> **2026-10-26 勘误**：上面这条旧认知两个半句都被证伪——干净停 3A 后直接开流实测正常（A4 格）；3A 运行中直接开流也正常（A1 格）。真实的坑只剩一个：**采流中 stop/kill 3A**（A2/A5 格，见 docs/29 §10）。

### 4.2 编译

```bash
cd /root
gcc -O2 -pthread -DHAVE_RGA -DHAVE_RKNN \
    -I/usr/include/rga -I/root/npu/3rdparty/rknpu2/include \
    -o evrec evrec.c -lrockchip_mpp -lrga -lrknnrt -lm

gcc -O2 -o mpp_dec_dump mpp_dec_dump.c -lrockchip_mpp
```

**【已实测】** 两条命令在板上 `0 error` 通过（`evrec.c` 有一条 `-Wformat-truncation` 警告，不影响运行）。

### 4.3 跑一次最小事件（文件触发）

```bash
rm -f /tmp/t /root/demo*
./evrec -d /dev/video5 -w 1920 -h 1080 --pre 2 --post 1 \
        --ring-mb 64 --kbps 4000 --trigger /tmp/t -o /root/demo -n 1 &
sleep 7; touch /tmp/t; sleep 5
head -c 230 /root/demo_*.json
```

**【已实测】** 预期输出（节选，字段含义见 `docs/32`）：

```json
{"file":"/root/p6_20240618-072226-00.h264","trigger_seq":100,
 "trigger_frame_index":34,"trigger_ts_ms":7009.6,
 "first_idr_seq":66,"first_idr_ts_ms":4747.5,"frames":51,"frame_count":51,
 "span_ms":3330.4,"width":1920,"height":1080,"fps":15.31,...}
```

判据三条：`fps ≈ 采集帧率`（1080p 约 15）；`trigger_frame_index ≥ 0`；`span_ms / frames ≈ 33 ms`。

### 4.4 校验录像可解码

```bash
./mpp_dec_dump /root/demo_*00.h264 /tmp/shot; echo "EXIT=$?"
```

**【已实测】** 判据是 `解出帧数 == frames - 1`（`mpp_dec_dump` 恒少解一帧，已用固定 30 帧码流对照确认）：

```
p6_...-00.h264 EXIT=0 >>> 解出 50 帧     # frames=51
```

【已实测】异常输入（截断文件）应 `EXIT=1` 且打印「未收到 EOS」，**不得 SIGSEGV**。

### 4.5 检测 + 事件（需人入镜）

```bash
./evrec -d /dev/video5 -w 1920 -h 1080 --pre 2 --post 1 --ring-mb 64 \
        --kbps 4000 --detect --det-score 0.45 --det-frames 3 \
        -o /root/det -n 3
```

**【条件依赖】** 需要 `cls=0`（person）连续 3 帧 `score ≥ 0.45` 才会触发；无人入镜时不会产生事件，属正常。

判据：日志出现 `检测触发 streak≥3 score≈0.5~0.8`；每 60 帧打印一次阶段耗时。**【已实测】** 本机 258 帧均值：

```
阶段耗时(均值, 258 帧): RGA 5.92 + RKNN 74.20 + 编码 15.36 = 95.49 ms/帧 -> 10.5 fps
```

### 4.6 推流与拉流校验

```bash
./evrec ... --rtsp 8554 --max-events 0 &
python3 /root/rtsp_check.py 127.0.0.1 8554 5
```

**【条件依赖】** 需要 `rtsp_check.py`（已入库 `tools/`）。**【引用 `docs/34`】** 判据 `gaps=0` 且 `fps ≈ 15`（1080p）；验收记录为 `pkts=1347 gaps=0 fps=14.85`。

> 推流**必须等参数集到达**才能握手：修复后 `t=202 ms` 即可 200；若你的分支仍返回 503，说明缺 `fix(evrec): 首个事件的 IDR 补齐 SPS/PPS`（`8b8b219`）。

## 5. 前置条件与坑（按撞墙顺序）

1. **3A 与采集互斥**：要么 3A 不启动，要么 camd/evrec 不开设备。没有第三条路——`/dev/video5` 不能被两个进程同时打开。
2. **停 3A 后要重启**才出流（见 4.1）。
3. **相机必须固定**：`det_samples.sh` 的所有样本都在同一机位、固定 `exposure=300`、`gain=64`、不加白平衡。机位一动，检出率数据全部作废。
4. **无 3A 时画面偏绿/偏暗是预期**：那是缺少 AWB/AE，不是驱动 bug。检测在此条件下仍可用于 1~2 m 顺光。
5. **不要 `pkill -f`**：会杀掉自己那条 ssh 会话。停进程用 `pidof evrec | xargs -r kill`。
6. **长命令写脚本再 `scp`**：直接 `ssh host '...'` 传含 `|`、`;`、`$()` 的命令会被本地 shell 解析掉。脚本必须是 LF 换行。
7. **`scp` 失败要显式检查**：曾有 `scp 2>$null` 吞掉错误、跑了旧二进制，导致"改完没生效"。**编译返回码不证明代码生效，只有输出字段能证明。**
