# 37 · 事件治理设计:evrec 从 ring-dump 走向流式事件写入

> 状态:**S1→S5 全部实施并板测 PASS(2026-10-28)**。S5 终验:10.3 分钟持续目标 = 同 event_id 3 段(301.6s+301.2s+14.0s),bytes/duration=0.207MB/s,触发 1 次,cooldown 零误伤,dmesg 零错误。满长 300s 段实测 62MB → disk_min_mb 默认上调 1000。对应 issue #4(持续目标 2h 产生 834 个事件文件)。
> V1(止血抑制)不立项为最终方案,仅作为运营层参数(cooldown 60s 等)在需要时配置;
> 四处边界修正已并入(事件周期对账/体积对账/ring 与 seq 去重/writer 背压)。

## 1. 现状:为什么不能"改几个变量"

当前 `evrec.c` 的事件模型是 **ring-based 一次性 dump**:

```text
trigger → 等 post_sec → 从 ring dump pre+post → ring_clear → 等下一次 trigger
```

三个硬限制(见 `evrec.c:2740-2820`):

1. 事件结束即 `ring_clear()` —— 环只有 `--ring-mb 64`,装不下一个 300 s 的 4K 事件;
2. `dump()` 一次性把 pre+post 写成文件 —— 事件进行中没有任何数据落盘;
3. `g_streak` 是"连续命中帧数",检测**偶尔漏一帧就归零** —— 用它判断"目标是否持续在场"会把长事件拆碎。

所以"持续目标合并为一个事件"**不是状态机加变量,而是写入架构的变化**。

## 2. 产品语义(先回答两个问题)

| 问题 | 决定 |
|---|---|
| 持续目标要一条长事件,还是允许分段? | **允许分段,但必须有意为之**:达到 `--max-event-sec` 时在 IDR 边界切段,`event_id` 不变、`segment_index++`。段与段之间无缝(都在实时写,不存在 ring 装不下的丢失)。 |
| 事件期间实时写,还是继续 ring dump? | **实时写(流式)**。pre-roll 部分仍从 ring 取(从最近 IDR 起),trigger 之后的每个编码包直接 append 到当前事件文件。 |

## 3. 目标架构:流式事件写入(streaming event writer)

```text
                    ┌─ 无事件: 每 frame → ring(滚动)
编码器出包 ──┬──────┤
             │      └─ 事件中: append 到 event.h264(同时 ring 照滚,供下一个 pre)
             │
检测触发 ────┴─→ 无事件时: 开临时文件 → 从 ring 取 pre-roll(自最近 IDR)→
                  逐包 append; last_detect_ms 持续刷新
                  事件结束判定: now - last_detect_ms > post_sec
                  → close → rename → 写 JSON → (进 cooldown)
```

### 3.1 事件延长判定:用 `last_detect_ms`,不用 `streak`

- 每次检测命中刷新 `last_detect_ms`(单调时钟);
- `now - last_detect_ms > post_sec` 才算"目标离开";
- streak 只保留给**触发门限**(连击 N 帧才开始一个事件),不参与延长判定。
  这样检测单帧丢失不会把 10 分钟目标切成碎文件。

### 3.2 分段(segment)与冷却(cooldown)语义分离

**切段门控(本节唯一的产品决定)**:切段 = close 当前段 → **目标仍在场才续段**。
判据是"最近一次命中/触发落在 post 窗口内"(`event_alive()`),不是"到点就续"。
到点且目标已离场 → 直接收尾,`close_reason=target_left`(文件结束的真实原因是目标走了,
上限只是同时撞上);`max_duration` 只在**确实发生了续段**时出现。这条门同时保证:
没有目标时不会出现"切段链自我续命 → 无限录 → 磁盘写满"。

| 情形 | 行为 | 事件计数 |
|---|---|---|
| 目标持续,达到 `--max-event-sec` | 在 **IDR 边界**切段:close 当前段,立刻开新段文件(段首仍为该 IDR) | `event_id` 不变,`segment_index++`;**不进 cooldown** |
| 目标离开超过 post_sec | 事件关闭 → **进 cooldown** | `cooldown_until = now + cooldown_sec` |
| cooldown 内再次触发 | 记 `cooldown_skipped`,不开新文件(检测与采集照常) | 不计入事件 |
| cooldown 结束后再触发 | 新 `event_id` | 正常 |

JSON 字段(每段一份):`event_id`、`segment_index`、`close_reason`(`target_left` / `max_duration` / `disk_low` / `sigterm`)、
`coalesced`(本事件吞掉的后续触发数)、`cooldown_skipped`、`disk_free_mb`(关闭时刻)。

### 3.3 磁盘水位:两阈值 + 滞回

- **开新事件前**:`statvfs` 检查 `free < disk_min_mb` → 不开,检测计数照走,记 `disk_low`;
- **事件进行中**:每 10 s 查一次;低于水位 → **先收尾当前文件**(close+rename+JSON,`close_reason: disk_low`),之后不再开新事件;
- **滞回**:低于 `disk_min_mb` 进入"停录"态后,须回升到 `disk_min_mb + hysteresis`(默认 +1 GB)才允许开新事件——避免 500 MB 边界反复启停;
- 水位计算必须把**当前事件已写体积**算进去;体积按实测对账:
  - 117 个样本平均 **1.48 MB/事件**(短事件,pre+post 窗口);
  - 连续满长段按 `--kbps 4000`(4 Mbps ≈ 0.49 MB/s,满帧)≈ **147 MB / 300 s**;
  - **S3 实测(检测模式,7.3 fps)**:1.13 MB / 8.1 s ≈ **0.14 MB/s**,
    300 s ≈ **42 MB** —— 与 147 MB 的差别来自 MPP 的 RC 按帧发预算(帧率低则实际码率低),
    两者是同一份配置在不同帧率下的真实表现, 不能互相替代;
  - 故 `disk_min_mb` 默认 **500 MB** 覆盖满帧 300 s 的 3.5 倍余量, 检测模式更宽松。

### 3.4 ring 语义与 seq 去重(writer 的两个暗坑)

- **事件结束路径移除 `ring_clear()`**:ring 必须照滚,否则下一个事件的 pre-roll 无从取起;
  复位集合收窄为 `g_trigger=0 / g_pre_seq=0 / trigger_i=pre_i=end_i=-1`(`g_streak` 归零保留——
  它只是触发门限的状态,不是事件状态);
- **pre-roll 与实时 append 按 `seq` 去重**:trigger 帧本身已在 ring 里,writer 打开文件后
  先写 ring 中 `seq < trigger_seq` 的部分,实时路径只 append `seq >= trigger_seq` 的新包,
  否则首帧重复;

### 3.5 writer 背压(必须有,否则磁盘慢会拖死采集主循环)

- 用户态 4 MB 写缓冲,攒批发写(`fwrite` 批量),**绝不逐包 fsync**;
- 写路径全部非阻塞语义:flush 超时(>200 ms)或写失败 → **立即收尾当前文件**
  (`close_reason: write_error`),进入与 `disk_low` 相同的停录态,检测与采集照常;
- 任何情况下 writer 不得阻塞采集/编码线程——"fps 不下降"优先于事件完整性;
- 缓冲满且 flush 失败:丢当前事件剩余数据(已在 ring 里的仍可事后人工分析),记 `write_error`。

### 3.6 各场景下的完整落盘

| 场景 | 保证 |
|---|---|
| SIGTERM / USR1 退出 | 当前事件 close+rename+JSON(`close_reason: sigterm`) |
| 链路故障恢复(link_recover) | 事件中断处继续(编码器不动),段内标注 gap;若编码器重建则按 `max_duration` 同款切段 |
| max-duration 切段 | 新段从 IDR 起(编码器 gop 边界自然满足;切段点即 IDR) |

## 4. V1 止血方案(可选,与流式方案独立)

若时间不允许做流式写入,先做**事件抑制**(不冒充事件合并,文档/面试表述必须区分):

- `--cooldown SEC`(默认 10):事件关闭后的冷却窗;
- `--max-events N`:已有;
- `--disk-min-mb`:事件**之间**检查,低水位停录。

止血版预期(按实测事件周期 8.6 s/个对账):cooldown 10s → 周期 ~18.6s → **约 390 个/2h(约减半,不是降一个量级)**;
cooldown 60s(运营参数)→ ~113 个/2h。**持续目标仍是一个目标多个文件**——这解释了为何 V1 只能算止血,
也是选 A 不选 B 的量化依据。

## 5. 验收矩阵(流式版)

持续目标 10 分钟(镜头前持续有人):

- [ ] 事件数 = 1,或按 `--max-event-sec 300` 分段 **≤3 段**;
- [ ] 段间 IDR 边界衔接,pre/post 无丢失(逐段 ffprobe 帧数连续);
- [ ] JSON 每段含 `event_id/segment_index/close_reason/coalesced/cooldown_skipped/disk_free_mb`;
- [ ] 目标离开 ≥ post_sec → 事件关闭;冷却窗内再触发 → `cooldown_skipped` 不新建;
- [ ] 磁盘低水位:当前文件完整收尾,后续不开新事件;回升越过滞回带才恢复;
- [ ] SIGTERM:当前事件完整落盘;
- [ ] 全程无 D 状态、无 fd 增长、采集 fps 不下降。

止血版验收:cooldown/max-events/disk-min 三参数生效,2h 持续目标场景事件数 ≤120 且磁盘占用有上限。

## 8. S3 收尾记录(板测后复审,2026-10-28)

S3 首版在板上跑通分段(5 段 × 8.09s,`max_duration` 正确、IDR 衔接、SIGTERM 段完整),
但复审确认三个缺陷,其中两个被"分段能跑"掩盖。全部按 **A 方案(事件=目标在场)** 修复:

1. **"无触发也在录"不是产品语义问题,是幽灵事件 bug**。S3 首版基于 cfbc855 的
   `if (evw_open(pre_i) != 0)`(每帧无条件调用):事件不存在时带 `pre_i=-1` 开幽灵事件
   (`trigger_seq=0` 的来源),之后切段链每 8s 续命一条,只有 SIGTERM 能停。
   该缺陷在 S2 复审的 `1df53e6` 已修,但 S3 分支未包含该提交,故在板上重现。
   修复:触发+开启块以 `g_ev_fp == NULL` 为门,幽灵事件无路径。
2. **续段 pre-roll 从 ring 头写**(`pre_i < 0` 被当成 0):每段开头塞进整个环(最多
   `--ring-mb`)的历史,段体积逐段递增(板上 2.07 / 4.01 / 6.09 / 8.05MB 正是此因),
   且新段首包不是 IDR。修复:新增 `ring_last_idr()`,`pre_i < 0` = 从 ring 内最新 IDR 起;
   与上一段末尾的同一 IDR 包重叠 1 个,保证两段都独立可解码。
3. **`event_id` / `segment_index` 失效**:`evw_open()` 每次调用都 `g_ev_segment = 0` 并重新
   生成 `event_id`,续段因此退化为"新事件"(板上 event_id 2987/2995/3003/3011、段号恒 0)。
   修复:拆成 `evw_open_at()`(公共) + `evw_open_new()`(序号/event_id 提交、段 0) +
   `evw_open_next()`(序号与 event_id 不变、段 +1);`evw_close()` 不再自增 `g_events`
   (分段落盘 ≠ 事件完成),事件计数改由 `evw_event_finish()` 在事件真正结束时 +1。

命名随之改为 `<前缀>-NN` (段 0) / `<前缀>-NN-sN` (续段),`NN` 只随事件递增;
`event_id` 与文件名同源(进程内事件序号),便于对账。

**待板测验收**(替换 §5 中对应项):持续目标 10 分钟 + `--max-event-sec 30` →
- 段数 ≤ 21,且 `duration_ms` 集中在 30~34s(不超 1 个 GOP);
- 同一事件内 `event_id` 恒定、`segment_index` 从 0 连续递增;
- 每段 `bytes` 量级一致(不再逐段递增),首包为 IDR;
- 目标离开 ≥ post_sec → 最后一段 `close_reason=target_left`,事件计数 +1;
- 无目标静置 60s → 不产生任何新事件文件(幽灵事件回归项)。

### 8.2 T3 复测(2026-10-28):先分清"误检"与"目标真的在画面里"

观测行上线后(编译 md5 双端一致), 镜头静置 30 s 实测:

| 指标 | 实测 |
|---|---|
| 5 s 窗命中率 | **95~100%**(57~62 / 61 帧) |
| 窗内峰值 score | **0.798** |
| streak | 峰值 193(近乎逐帧命中) |
| 连击结束 | 3 次(偶发丢帧断连) |

**第一层结论**:`alive` 恒真、40 s 永不 `target_left` 由此完全解释, 状态机三件套
(切段 / 幽灵事件门 / alive 门控)在真实复杂画面下行为正确 —— 它忠实跟随一个
"持续在场的目标", 逻辑没错。

**但"系统性误检"这个定性站不住, 有一处混淆**:

1. 遮住镜头对照做的是 **J11(OV8858)**, 而采集/检测链是 **`/dev/video5` = IMX415(J10)**
   —— 遮 J11 对检测输入零影响, 命中率不变是必然结果, 不能作为"误检"证据
   (证据边界见 `docs/35` §1.1);
2. 抓帧内容显示 J10 对着的是**整个办公区, 画面右侧有一个人(操作者本人)**。
   峰值 0.798 的 person 框更可能是**真阳性**, 而不是无目标的幻觉。

因此当前状态是:**"目标是否真的离开了 J10 视野"未受控**, 不是"检测器失效"。

**受控复测三步(替代"人离开房间")** —— 每步都看 `检测统计` 行, 不看"我觉得没人":

| 步 | 操作 | 期望 | 若不满足说明 |
|---|---|---|---|
| S0 对照 | **遮住 J10**(不是 J11) | 命中率 → 0%, NPU 输入均值骤降 | 检测输入与当帧不同源(RGA/NPU 读了陈旧缓冲), 属代码缺陷, 立刻停测排查 |
| S1 触发 | 放开 J10, 人入镜 10 s | 命中率高、`检测触发` 出现、事件开启 | — |
| S2 离场 | 人离开 **J10 视野**(或重新遮住 J10) | 命中率 → 0%, `post` 秒后 `close_reason=target_left`, 且不再续段 | 若命中率不归零: 场景本身在出 person 框, 属触发源/阈值问题, 不属状态机 |

S0 是最便宜也最有信息量的一步:它一次性分开"场景里有真目标"与"检测输入通路错"两种可能,
且不动任何参数。

**风险登记(不进代码, 进运维)**:触发源 = 业务镜头本身时, 复杂场景的 person 误报会
让事件系统退化为常开录像, 此时唯一兜底是 `--max-event-sec` 分段 + S4 磁盘水位。
若业务要求"只在真有人时录", 触发源应改为 ROI 限定 / 更高阈值 / 专用检测镜头, 属
产品侧决定(issue #5 候选)。
