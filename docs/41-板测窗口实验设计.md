## 1. 排期原则、隔离与共同证据

1. **准备先于窗口**:PC/VM 上实现并评审注入库、固定输入回放、板端记录器与客户端监测器,自测故障开关和退出码;核对交叉编译器、目标 sysroot、头文件/库版本和测试介质。本文不假装这些辅助程序已经存在。准备未完成的实验标记阻塞,不把临时手工操作当替代验收。
2. **建议拆窗口**:W0 只读盘点及 VM 编译;W1 低风险 evrec/camd、双路 NPU、四客户端;W2 用户在场进行 HDR/GPIO/潜在需重启实验;W3 单独审批 compliance 与 suspend 高风险实验;W4 在前置通过、环境稳定且用户批准后启动 24h soak。顺序可因状态调整,**高风险实验不与 24h 并行**。T1 是两次长对照,不与 T4 混成同一个结果。
3. **共同前提**:核对串口未被其他程序占用;只读记录 `boot_id`、内核、DTB、服务、时间、网络、空闲空间、现役进程与节点、拓扑、3A 状态、配置/模型/库/待测二进制的 SHA-256 与 MD5。识别 sensor 与节点后才选设备;不要把历史 `/dev/videoN` 当固定身份。现役文件、系统库和服务配置不覆盖。待测源码/二进制使用唯一目录,scp 后两端 MD5 一致才运行。共享硬件的状态变更及采集需窗口授权。
4. **3A 红线**:默认保持现役 3A 常驻;**采流中不 stop/kill 3A**。本次 boot 启动过 3A 后,停止它不能直接再采;需要无 3A 对照时,由用户批准 disable、重启,核验本 boot 从未启动,再测;结束后按批准方案恢复启用并重启。不能把 disable+reboot 写成已发生 wedge 的恢复捷径。
5. **储存与记录**:以板端持久文件系统上的独立目录 `<P>/camera-window/<run-id>/` 为待测根,下文简称 `<run>`;`run-id` 含 UTC 时间和随机后缀,禁止复用;先确认 `<P>` 不是 `/tmp`/tmpfs、不是 `/boot`,核对可用空间、inode、写入权限及介质耐久性。每项有独立子目录、参数/二进制哈希、启动命令、环境、stdout/stderr、退出码、单调时钟+墙钟、异常与操作员记录。产物不覆盖现役数据;故障注入只命中测试进程与测试目录。测试后人工复核脱敏,新增至 `evidence/YYYY-MM-DD-板测窗口/<run-id>/`,大视频保留清单/哈希及代表性片段,按仓库规定审查后入库;原始证据只增不改。
6. **中止/恢复**:出现新 Oops/panic、D 状态、节点失联、温度或存储接近事先约定上限、输出意外触及现役目录时立即停止发起下一步,保全现场;记录器不得用 kill -9 声称解除 D 状态。需要重启/断电由用户决定并在场;刷写/覆盖 `/boot`、分区、bootloader、eMMC 等逐次单独批准。故障路径可能留下 `.part`,不自动清理。
7. **有效性分类**:PASS=全部前提、判据和证据完整;FAIL=有效实验中任一明确判据不符;BLOCKED/INCONCLUSIVE=缺设备、未获批准、采样不完整或控制变量不能保持。不得用进程 exit 0 单独代替文件、帧或设备检查。

## 2. 必做验收 A

### A1 evrec 真实设备故障传播(批 A)

- **假设**:真实采集/编码进行中,事件收尾遇到 JSON 创建、写入或关闭失败,以及视频写入失败,会向退出码和事件完成状态传播;正常 SIGTERM 收尾保持原行为。主机替身覆盖见 [测试](../tools/tests/test_evrec_host.py),不能代替板测。
- **准备与方法**:VM 构建独立 evrec 副本及故障注入包装器。文件错误夹具 [evrec_fault_preload](../tools/evrec_fault_preload.md) 已实现,主机提取代码测试通过、AArch64 交叉编译通过;**尚待代码评审、板端 libc 兼容性及真实设备验证**。它针对独立进程和指定目录/前缀注入 JSON 打开、格式化写入、关闭、视频写入及 rename 故障,记录命中与返回,不能覆盖 QBUF/RGA。板测前先验证实际目标二进制的动态链接/符号可拦截性与私有目录,确认命中;失败则用隔离测试构建的等价包装,**不声称 LD_PRELOAD 一定可拦截内部 libc 写入**。在隔离输出目录同条件进行正常对照,分别覆盖 target_left 收尾和事件活跃时 SIGTERM;QBUF 恢复仍需测试构建或 ioctl 包装器,RGA 失败仍需测试构建并计数推理调用,均不触及其他进程。
- **判据**:正常对照事件完整、退出 0;每个被确认命中的收尾故障返回非零,失败事件不计成功,核对 stderr、完成数、`.part`/`.h264`/`.json` 的存在及事件 ID/segment,JSON 若存在应按实际状态解析而不要求失败场景必有完整 JSON。QBUF 失败进入恢复/非零退出;RGA 失败帧不调用 NPU、后续成功帧恢复。未命中注入=无效,不能算通过;意外成功或错误事件被计成功=失败。视频 rename 后 JSON 失败允许留下已生成视频,按实际实现记录,不预设原子回滚。
- **风险/批准/到场/时间/证据**:占用摄像头、磁盘写入与故障注入需窗口批准;不动 3A,无需断电,用户可不持续在场;准备另计,执行约 90–120 分钟。`<run>/A1-evrec/{manifest,inject,stdout,stderr,exit,files}/`。若注入点或事件计数不可观测,先补测试辅助并评审,不以日志猜测。

### A2 camd 真实运行与输出字节一致性(批 B)

- **假设**:批 B/C 后真实设备采集、正常收尾和有界恢复可运行;相同输入及配置下,可比较的输出字节与旧版一致。真实不同采集帧不构成逐字节相等证据。
- **方法**:隔离准备基线版(批 B 前)、待测版及依赖,分别记录源码/二进制哈希和同一配置。先逐版独占同一节点跑固定帧数,记录帧/丢弃/队列/回收/fd/RSS、返回值、dmesg 与恢复过程;按现有 `--fault`/`--fault-once` 能覆盖的场景核实实际路径。**确定性字节对照需新建测试夹具**:抓取并冻结相同原始帧及其元信息,以同一适配层向两版输入同一字节序列、序号和时间戳,固定像素格式、stride、参数、模型、随机性与输出口径;分别保存实际被测图像/推理张量字节和哈希。先证明夹具输入哈希与参数完全相同,再逐字节比较可确定的输出;JSON 中实时耗时/时间戳、硬件编码器码流除非已证明确定性,只按字段语义单独比较,不能删字段后宣称整个输出相同。若程序没有注入入口,先独立评审测试夹具,不可假装现有 CLI 支持回放。
- **判据**:设备运行无新 Oops/卡死,线程和 buffer 归还与计数守恒,退出符合设计;同输入可确定输出逐字节一致、长度和哈希一致,统计口径按同输入同顺序核对。任一不同需定位字段/字节与原因,不能归咎于不同场景;不能固定时序/硬件输入则字节一致性为 INCONCLUSIVE,真实运行通过也不能代替。恢复场景前后记录最大并发采样线程数及资源数,沿用 [主机测试](../tools/tests/camd_host_test.c)。
- **风险/批准/到场/时间/证据**:共享视频节点需批准,测试二进制和数据隔离,无需断电;用户不必持续在场;夹具准备另计,板上约 90–150 分钟。`<run>/A2-camd/{versions,input,baseline,candidate,diff,resource}/`。

### A3 camd 双宏完整编译(VM)

- **假设**:批 C 后完整 `camd.c` 在目标 ABI、RGA/RKNN 双宏及相应头库组合下能编译链接。
- **方法**:VM 隔离构建目录取待测源码及依赖,记录 commit/哈希、目标架构、交叉编译器、sysroot、RGA/RKNN 头库版本;用 `-DHAVE_RGA -DHAVE_RKNN -Wall` 完整编译并链接目标二进制,保存命令、完整 stdout/stderr、退出码和 `file`/架构。若 sysroot 没有目标库,先记录完整源文件对象编译,**链接待补**;不能把 x86 主机对象冒充板端二进制。必要时另排板端隔离编译,不覆盖现役文件。
- **判据**:目标架构编译及链接 0 error,逐条记录 warning;缺库/未链接为 BLOCKED,不是完成。与后续运行哈希相符才能关联验收。
- **风险/批准/到场/时间/证据**:只用 VM,不碰板子,不需用户在场,30–60 分钟(补 sysroot 另计)。`<run>/A3-build/{command,versions,build.log,exit,hashes}/`;VM 暂存,窗口后与其余证据归档。

### A4 T2 四客户端满载至少 10 分钟

- **假设**:四个真实 RTSP/TCP 客户端同时接收时,采集、解码和事件录像可持续工作。上限配置为 4 不等于满载已验证。
- **方法**:先用相同分辨率、码率、模型、3A 和客户端工具做单客户端基线;优先在板端启动四个独立 RTSP/TCP 回环客户端,独立保存各路流、帧/包时间戳、退出码和服务端指标,运行期间用低开销码流拷贝而非假定板上有能力并行软件解码。窗口结束后用 VM 对每路完整解码并保存错误和帧时间戳,算入结果;先核算四份码流空间,记录客户端 CPU/内存,不能把客户端过载当服务端结论。以服务端确认 `clients=4` 且四路均收到首个可解码帧作为 t0,持续至少 600 个单调秒;周期触发事件并记录文件关闭/JSON/可解码性,采样服务端采集帧率、sent/drop、温度、fd、D 状态与内核日志。若板端缺客户端工具、容量或本机负载改变被测条件,记录原因并改用 VM 上四个独立有线客户端,同时记录 VM/网络负载,不可因此称板端自包含;均不依赖 Windows PC 唤醒。第五路拒绝、慢客户端/重连可作为单独附加用例,不混入四路稳态统计。
- **判据**:四路在 t0–t0+600s 同时存活并持续成功解码,没有非预期重连或服务端丢客户端;按预先固定的逐分钟口径,各路及采集帧率不低于同条件基线的 95%(容差为本计划测试阈值,不是历史测量),无连续 5s 无帧,错误/丢帧计数按可观测字段不增长;事件按触发完成并可解析/解码,无新 Oops、D 状态、录像中断。任何关键指标不可观测或客户端自身瓶颈未排除=INCONCLUSIVE;实际 drop/断流/录像失败=FAIL。单次结果不外推 WiFi 或其他分辨率。
- **风险/批准/到场/时间/证据**:占用采集与网络、写盘需批准,不碰 3A 生命周期;无需持续在场,基线+执行+回收约 45–60 分钟。`<run>/A4-rtsp4/{server,client1,client2,client3,client4,events,network}/`。这项不是 24h soak 的四客户端长期验证。

### A5 T4 24h 服务级 soak:板端自包含

- **假设**:固定配置的服务、事件录像及资源占用可连续运行 24h,不依赖 PC/VM 连接。对象、码率、输入、事件频率、日志级别和温度阈值需在运行前冻结,与历史 2h 服务级结果区分。
- **板端记录器设计**:在独立目录运行独立 supervisor/collector(待实现),启动前记录进程 PID+启动时间、boot_id、配置和哈希;每 60s 用单调时钟记录进程存活/重启次数、RSS/PSS(可用则记录 smaps_rollup)、fd/线程、磁盘剩余与 inode、温度、采集/编码/事件/RTSP 计数、dmesg 序号或时间戳。持久化日志、采样 CSV、事件结果、start/heartbeat/end 和退出码,写入失败立即标记无效并安全停止测试;每次持久化时检查实际剩余空间。记录器自行产生固定周期触发,不可依赖 SSH、终端、PC 定时器或 PC 保持唤醒;用后台服务/独立会话并验证断开管理连接后持续。定时器用单调时间,墙钟漂移只记录不修时。
- **容量/安全**:按预定码率×最长事件写入时长×次数计算录像上界,加日志及安全余量,须在开始前证明空间足够并记录计算;按现有 `--disk-min-mb` 和独立文件系统保留水位,不自动删除现役或证据。空间或温度到预设中止阈值、安全文件创建失败、设备异常时留下停止原因;不可用循环删除来伪造完整录像。若介质/空间不够则 BLOCKED,不缩成短测冒充 24h。
- **判据**:同一 boot_id、目标进程身份连续(除非设计明确允许并单独计次,本验收默认不允许重启)覆盖 ≥86400s;采样时间戳连续、缺样为 0、开始/结束及退出记录完整;新增内核 error/Oops/panic 0,无 D 状态;每次计划触发与事件落盘/JSON/可解码抽检一一对应,无失败。每小时报告 RSS/PSS/线程/fd 和事件成功数;预设资源门限:排除启动后首 30min,末小时 RSS 中位数相对其后的首小时增加不超过 10 MiB,fd 末小时中位数较首小时不超过 2 个,且不存在连续四个逐小时增量均 ≥1 MiB。超过门限或出现该连续增长则资源稳定性 FAIL 并保留曲线,不直接断言内存泄漏;缺样/无法测量则 INCONCLUSIVE。阈值为方案提议,正式运行前可由用户裁定,不得测后改阈值。网络观察若没有独立板端客户端,只验服务和录像,不宣称客户端 24h 接收通过。
- **风险/批准/到场/时间/证据**:持久写入和长时间占用需用户批准及供电/存储保障,无需人员守 PC;启动和收尾需要用户在场,中途异常通知由已准备的本地机制处理,无网络通知不影响数据保留。执行 ≥24h 加准备/核验约 1–2h。`<run>/A5-soak24/{manifest,samples.csv,service.log,kernel.log,events,heartbeat,summary}/`。断电/重启/数据缺失=未完成,保留已采样数据。

### A6 T1 RSS 归因(可选,独立于 T4)

- **假设**:固定负载下 RSS 增长与 allocator arena 相关;`ARENA_MAX` 限制可能降低增长,但不能由 RSS 波动单独证明泄漏或碎片。
- **方法**:同一板端记录器、相同二进制/模型/配置/事件触发及环境,分别运行默认 allocator 与 `MALLOC_ARENA_MAX=2`,每组预热后连续 ≥4h,顺序 A→B→B→A 更有说服力但需更多窗口;每组记录启动环境、进程重启、RSS/PSS、匿名映射、线程、fd、分配器统计(可用时)、事件/帧吞吐及 CPU。优先连续固定负载,不与其他测试并跑;变量不能一致则无效。历史使用的二进制及环境先核对,`ARENA_MAX=2` 的实际生效方式须通过进程环境和运行库确认。
- **判据**:两条件各自 ≥4h 完整记录;对预热后的每分钟样本按单调时间做 RSS 线性斜率拟合,同时报告 PSS、峰值及首末小时中位数差。预设负载等价为每组完成帧/事件速率相差不超过 5%;在 ABBA 重复中,两次默认组斜率均为正、两次限制组斜率均不超过相邻默认组的 50%,且 PSS/映射变化方向不矛盾,才支持 arena 相关;差异不足、重复方向不一致或内存映射不支持时不支持/未定。只有单次 AB 的结果只能作为探索,不能声称重复成立。阈值为待审方案,执行前冻结;采样丢失、重启、运行库不支持变量、负载不一致=INCONCLUSIVE;不单凭相关性证明根因。
- **风险/批准/到场/时间/证据**:占用设备和存储需批准,板端自记录、不依赖 PC;用户只需启停时在场。至少 2×4h 加预热,ABBA 为 ≥16h。`<run>/A6-rss/{A-default,B-arena2,comparison}/`。

## 3. 待检验悬案 B

### B1 输出 native 差异的根因

- **假设**:差异可能来自 layout/stride/padding、量化/反量化、缓存同步、输入不一致或运行时转换;“runtime requant”仅为候选。历史输出 native 尝试代码未入库,[两次原始 JSON](../evidence/2026-10-25-质量保障线/fv_ab2.json) 只能证明当时字节对照有差异,不能单独证明原因。
- **方法**:先用固定输入和模型哈希重建独立 harness,锁定板端 RKNN 版本、输出个数、普通与 native 的 tensor 属性(index、dims、fmt、type、qnt、zp/scale、stride、size_with_stride)、API 返回码与缓冲生命周期;官方 [RKNN API 头文件](https://github.com/rockchip-linux/rknpu2/blob/master/runtime/RK356X/Android/librknn_api/include/rknn_api.h) 是接口背景,以板上实际版本为准。同帧交替或双 context 确认输入字节一致,采集普通 `outputs_get` 的原始/请求浮点结果与 native 原始 buffer;保存完整 bytes、属性和数据长度。按真实 layout/stride 剔除 padding、明确 NC1HWC2→逻辑布局后比较,再以相同 scale/zp、类型和舍入规则转换并对比逐元素误差/差值分布;分别做 sync 有/无与重复运行,保证每组同一输入、无时间错位。若 API/版本不支持同一 context 两种输出,使用固定输入双 context 并先做同路径重复性对照。
- **判据**:布局还原后全等支持布局/填充解释;再按已记录量化规则转换才全等支持表示转换解释,**仍不能仅据此断言 runtime 内部确切实现**。只切 sync 消除差异支持同步相关;控制输入/布局/量化/sync 后同路径稳定而跨路径仍差异则反驳上述充分解释,保留原样待进一步仪器/官方资料。转换定义不完整、版本不支持、重复结果自身不稳定=INCONCLUSIVE。检测框一致不等于张量字节一致。
- **风险/批准/到场/时间/证据**:需独占 NPU 与隔离实验程序,不替换 runtime/model,需用户批准;无需断电,准备另计,板上 2–4h。`<run>/B1-native/{input,attrs,raw,normalized,diffs,versions}/`。

### B2 双路 NPU 争用复现

- **假设**:同一运行环境下两路并行推理的每路等待/吞吐相对各自单路发生变化;变化原因需通过控制实验区分,不能仅凭墙钟认定调度机制。
- **方法**:使用 [zc_dual 源码](../zerocopy/zc_dual.cpp),检查其线程/计时点/两路真实输入与是否支持单路;缺单路切换或逐次日志时,先在独立实验副本加可审查的计时与开关,记录补丁和哈希。固定模型、分辨率、前处理、时钟/温度、CPU 亲和性(如可控),分别运行 A-only、B-only、A+B;预热后每组至少 60s、至少 3 次,交错顺序,保存每次 `rknn_run` 的开始/结束单调时间、线程、序号、返回值、每路 fps 和汇总,以及采集帧率/RGA耗时/CPU/温度。先核对这两个“单路”只关闭对侧推理,其他输入链/负载一致;另做同一固定张量双 context 控制组,隔离采集差异。
- **判据**:重复组中双路与各自单路在每路推理墙钟/吞吐的变化方向一致且时间区间重叠的对照满足预设方法,支持存在并发争用;若各路无可重复变化则不支持该现象。输入不同、发热降频、前处理瓶颈或样本不完整则不能归因于 NPU。结论只描述观测的墙钟与吞吐,不宣称已证明内部时间片调度。新数据只在归档原始日志后用于 README,不能把历史报告数字补写成新结果。
- **风险/批准/到场/时间/证据**:双摄及 NPU 同时占用需批准,无需断电;准备另计,板上 60–90 分钟。`<run>/B2-dual-npu/{A-only,B-only,dual,fixed-input,summary}/`。

### B3 compliance Oops 与替代内存后端

- **假设**:旧 Oops 可能与特定 rkcif 参数校验及 DMA 后端有关;更换用户态内存方式或后端可能绕过该触发,但不等于根治或证明整个 compliance 通过。
- **现有源码考证(仅 VM)**:`drivers/media/platform/rockchip/cif/capture.c:3238–3244` 的队列支持 `VB2_MMAP | VB2_DMABUF`,`hw_dev->iommu_en` 为真选 `vb2_dma_sg_memops`,否则选 `vb2_dma_contig_memops`;`hw.c:799` 根据 DT `iommus` 引用及节点可用性判断。**MMAP/DMABUF 是用户 API,不是直接切换 sg/contig 的开关**。该 VM 源码与现役内核/DTB 尚未核对,不能认定板端当前选择。
- **方法**:先不触发危险 ioctl,只读核对已运行 Image/DTB 的构建来源、IOMMU 拓扑、队列选择和版本;在 VM 审计 `queue_setup`、plane/size 校验、两后端异常分配路径与支持的 io_modes。然后在明确批准、用户在场并保留串口的破坏性窗口,先以独立最小复现器复核**完全相同非法参数**与基线签名,固定重启恢复方案;有界子进程超时只用于记录,**不能解除内核 D 状态**。可选分别测合法 MMAP/DMABUF、非法参数的模式支持及错误码;若理论上切到 contig 需修改设备树/IOMMU 或隔离测试内核,先构建候选和回滚镜像、列出 DMA 地址/连续内存约束,每次覆盖/刷写单独请批,不得直接修改现役。在候选内核下先做最小复现、正常采集回归,再单独批准完整 compliance。
- **判据**:相同参数在原配置重现且候选配置重复返回规定错误、无 Oops 且正常采集可用,支持**该组合绕过**,不证明厂商缺陷已修;两者均 Oops/同错误则不支持绕过。若原基线未重现、候选不支持该模式、测试没有到达同一内核路径、回归失败或日志缺失=INCONCLUSIVE。完整 compliance 必须保存完整命令、逐项输出、总计和系统存活状态,有 fail/warning 原样报告,不能只因未崩溃说全通过。
- **风险/批准/到场/时间/证据**:高风险,可导致 Oops、设备 D 状态、强制断电;须逐项批准、用户现场、串口和已验证恢复介质。VM 审计 1–2h;破坏性实验单独 2–4h+恢复,不占 24h 窗口。`<run>/B3-compliance/{baseline,candidate,ioctl,kernel,recovery}/`。

### B4 suspend 唤醒源是否存在

- **假设**:历史“无唤醒源”来自当时 `/dev/rtc*` 不存在、无电源键的现场记录([docs/20](20-L4电源管理.md)),不是当前硬件永久事实;存在可用 RTC/GPIO 唤醒也不自动等于 suspend 已修复。
- **VM 只读考证**:当前 VM `.config` 含 RTC class、sysfs/dev 接口及若干 RTC 驱动,也启用 PM sleep/debug;这是编译配置,**不证明实际板有 RTC、供电、设备树节点或唤醒连线**。板级 wakeup 节点和 bootloader/固件配置需继续按实际 DTB/源码核对。
- **方法**:窗口先只读盘点 `/sys/class/rtc`、`/dev/rtc*`、`/sys/power/state`、`/sys/power/mem_sleep`、设备 `power/wakeup`、`wakeup_sources`、中断与实际运行 DTB/原理图,确认 GPIO 是否接至可由外部安全操作的按键/中断和供电域,不扫描或切换未知引脚。RTC 候选须确认硬件/驱动支持 alarm 和 wake,预设短时报警并记录 alarm 注册;GPIO 候选须确认 pinmux/极性/IRQ/供电和按键物理路径。缺硬件但有可安全接入外置 RTC/按键时单独形成接线及 DT 方案,硬件改线/DTB 刷写另批。真实 suspend 仅在验证唤醒源、串口、断电恢复及用户到场后单独批准;先空闲停流,不对 3A 做危险操作,先执行一次并记录入睡、唤醒原因与时钟,再验证设备恢复;带流保护仅按现有保护路径单独测试,禁止绕过。
- **判据**:RTC alarm/GPIO 事件实际使系统从真实目标 sleep state 恢复且 boot_id 不变、唤醒原因可关联=该源在该状态可用;仅设备存在/`pm_test=devices` 通过不算唤醒。已验证接线配置下触发无恢复=该候选不成立,但不排除其他源;无法核实供电/连接或需断电恢复=INCONCLUSIVE。真实唤醒成功与带流 suspend 修复分别报告。
- **风险/批准/到场/时间/证据**:真实 suspend 可能无法唤醒,硬件改线/DTB/断电另批,用户必须到场;只读盘点 30–60 分钟,候选测试另 1–2h。`<run>/B4-wake/{inventory,rtc,gpio,suspend,recovery}/`。

### B5 IMX415 1080p 线性基线的 0x3034 定点对照

- **假设**:1080p 表写入后读回为零可能是寄存器读语义/自清零,也可能是初始化或模式相关;单个回读值不足以区分“只读”和“自清零”。先验证线性基线,不启用 HDR 派生表。来源 [issue #3](https://github.com/Ericsunny/rk3568-camera-driver/issues/3) 与 [冻结分支 E0 记录](https://github.com/Ericsunny/rk3568-camera-driver/blob/af19dff/evidence/2026-10-27-HDR线性基线/README.md):该 E0 文件/实验补丁在历史分支,**不在当前 main**,不得假定已部署。当前 VM `imx415.c` 含 1080p 表及 `{0x3034,0x05}`、`{0x301C,0x04}`,但 VM 树未证明对应板端镜像。
- **30 分钟时间盒(仅准备已齐全时)**:预备好已验证的 sensor/ISP 节点、模式表、只读寄存器工具、串口与输出日志,在已批准的无 3A 干净 boot 中进行:0–5min 核对 3A 本 boot 从未启动、镜像/DTB 哈希、基线 media 拓扑;5–12min 设正常 720p 并确认确实出帧/IRQ 增长,流式及停流后读取 0x3034 与 0x301c/模式位;12–19min 同法测正常 4K;19–27min 仅在现场已有可用的 1080p 测试模式、已批准且恢复路径可用时,完整配置 sensor→CSI→ISP sink/crop/source→video 节点,启动受控采集并在流式阶段读取同组寄存器及 IRQ/帧计数,含超时;27–30min 记录与停流、判定是否需恢复。I2C 只读访问与驱动并发及 `-f` 强制访问有风险,须确认地址/总线/数据宽度、获批准并严格只读;工具阻塞、0 帧或 STREAMOFF timeout 立即停止推进,不能依赖 timeout 杀掉内核 D 状态。
- **判据**:正常模式和 1080p 的表项、流式/待机读回、帧及 IRQ 均有时间对应记录,才能判断“零读回是否仅发生在 1080p”;若正常模式同值也读零,反驳其为 1080p 特有现象,**不证明自清零机制**;若正常模式可回读而 1080p 不能,支持模式相关异常,仍不能定位根因。模式未真正生效、4K/720p 本身无帧、读失败、1080p 不存在或缺可比表项=INCONCLUSIVE。要证实自清零还需寄存器资料或受控写后时序实验,后者另批。
- **风险/批准/到场/时间/证据**:模式切换会占用 ISP、可能 wedge;需要用户在场、批准无 3A 配置及重启。若需要 #53 或修改/覆盖 Image、DTB,先停在 BLOCKED,每次刷写单独批准且回滚介质就绪;**30min 不含无 3A 切换、重启、刷写和故障恢复**,前置未满足就不启动计时。`<run>/B5-imx415-3034/{preflight,720p,4k,1080p,irq,comparison}/`。

### B6 GPIOD_ASIS 与方向来源

- **假设**:`GPIOD_ASIS` 不主动设方向,reset/pwdn 输出方向可能由 bootloader、pinctrl/GPIO hog、其他消费者或先前状态建立;运行时方向为输出并不能证明是谁建立的。
- **已完成的 VM 源码只读考证**:VM 的 `include/linux/gpio/consumer.h` 将 `GPIOD_ASIS` 定义为 0;`drivers/gpio/gpiolib.c:3898–3940` 在无 `GPIOD_FLAGS_BIT_DIR_SET` 时返回,不调用方向设置;普通 push-pull 路径 `gpiod_set_value_cansleep` 经 `gpiod_set_value_nocheck` 写值,开放漏极/源极有特殊分支,不能一概而论。VM `drivers/media/i2c/ov8858_sm.c` 申请时用 ASIS,后续调用 `gpiod_set_value_cansleep`;搜索该文件未见显式 `gpiod_direction_output`。VM DTS 的 `cam1_ov8858` 对应 GPIO1_B1/B2、active-high;这些是源码线索,非板端 DTB 现状。VM 该驱动文件 SHA-256 `b2b08a1a7cca73b23814b45fd58999e938afdf0edcd04e3702e50f528b77ab01`,并非已证与板端运行 Image 一致。
- **方法**:继续只读核查实际 DTB 反编译结果、GPIO hog/pinctrl、启动固件代码和运行 Image 的来源;窗口记录 GPIO controller 节点的物理基址、版本、pinmux、debugfs GPIO 描述及方向。按 VM `drivers/gpio/gpio-rockchip.c` 的版本判断方向寄存器:V1 的 `port_ddr` 偏移 `0x04`,V2 为 `0x08`,V2 分半字读取;仅在核实板端映射/寄存器版本且获批准后使用**只读**寄存器工具记录 GPIO1_B1/B2 对应位,不使用写寄存器、不 export 已占用 GPIO。若 debugfs 已能提供方向,先用它;寄存器读取在相机正常状态做,不主动切换电平。追踪方向建立时点需要 bootloader 输出或不同启动阶段的只读观测,准备独立隔离镜像/trace 后另批,不能通过无证据推断。
- **判据**:驱动源码 ASIS 分支不设方向是源码层证据;同 boot 的 GPIO 方向位为 1 且 pinmux 为 GPIO,只支持“读取时已配置输出”,为 0 则反驳该时刻输出假设。只有建立时点/调用者可追溯且与读数一致,才可归因给具体阶段;读不到、pinctrl 未核准、源码与镜像不匹配=INCONCLUSIVE。避免把 `/sys/class/gpio` 序号当物理位或以读数证明电压。
- **风险/批准/到场/时间/证据**:只读 MMIO 可能受权限、映射与时钟影响,须获批准;不触碰 GPIO 输出/DTB,无需断电但建议用户在场;VM 1–2h,板端 20–40min。`<run>/B6-gpio/{source,dtb,pinmux,ddr,provenance}/`。

## 4. 改动与待批准清单

### W1 附加:当前 CIF 标签与内存布局复核(目标 10 分钟)

无板核证及历史厂商 `BG10`/compact 不一致见 [docs/40 P2-14](40-全仓体检报告.md);下列是**当前设备复核**,不是预填的板测结果。前置为 W0 已核对节点、3A、独占窗口、隔离目录及采集工具,不含设备准备/异常恢复时间。

1. 只读保存 CIF 节点 `G_FMT` 的 FourCC、width/height、plane `bytesperline` 和 `sizeimage`,确认当前 sensor/拓扑及模式;采集一帧时保存 `QUERYBUF` length、`DQBUF bytesused` 和原始帧哈希,不要把三者当作同一字段,不修改原始帧。
2. 若实际为历史 1632×1224、stride 2048、文件恰含 2,506,752 字节,以 `raw10_stats.py --packing raw10p --bayer <实际相位> --width 1632 --height 1224 --stride 2048` 读取。再以 `u16le-lsb`、相同宽高及 stride 验证:由于 16 位容器每行至少 3264 字节,工具应拒绝该 stride,这是几何不相容的否证;完整 16 位帧至少 3,995,136 字节。用户给出的 `2048×1224=2,509,056` 是算术笔误,正确结果为 2,506,752。
3. 可选对同一帧以 `u16le-lsb --width 1024 --height 1224 --stride 2048` 仅做**逐行字节对重解释的高位检查**:若出现大于 1023 的字,该候选被拒;若没有,**不能证明**其为 16 位容器。此诊断的 1024 宽不是实际图像宽度,包含行尾 padding,其统计不作画质结果。`raw10p` 解包值必然不大于 1023,也不能仅凭范围证明低两位顺序;应结合受控 test pattern/已知输入或驱动资料验证低位。
4. 若 FourCC、stride、文件长度或节点与历史不同,记录实际值并重新判断,不强制套用上述数字。正常完成即保留命令、返回码、格式输出与哈希于 `<run>/W1-cif-format/`;不符合预设条件、读不到或输出截断标 INCONCLUSIVE。占用采集节点须窗口批准,不停止或 kill 3A;不涉及刷写。单帧无板前置及读数准备好后目标 10 分钟,故障恢复另计。

### 汇总与批准

- **不删 A/B**:所有必做项保留;T1 是可选独立对照而不是 T4 的替代。加 A3 构建可追溯性、共同存储/重启保护和 A/B 的无效实验判据,避免“跑了但不能下结论”。B5 只承诺前置就绪后的 30 分钟定点观察,不承诺需要刷写/恢复时也能完成。
- **需提前研发/评审**:A1 文件错误夹具已有主机测试,仍需评审及板端兼容性验证,QBUF/RGA 注入工具尚需准备;A2 固定帧及元信息回放夹具、A5/A6 板端持久记录器/空间管理/单调时钟校验、B1 tensor 原始抓取/归一化工具、B2 按需单路开关和逐次计时工具仍待准备。准备完成并做无设备自测后再安排相关板测。
- **逐次单独批准**:任何覆盖 `/boot` 或 Image/DTB、分区/bootloader/eMMC 写入;B3 候选内核/IOMMU/DT 修改和危险 compliance;B4 接线/唤醒配置/真实 suspend;B5 无 3A 的 disable 与重启、#53/其他镜像切换;任何可能需冷启动断电的恢复。其他独占设备、长时负载和测试文件写入也须窗口授权。
- **证据回收**:每项先核对 start/end、exit、时间线、哈希与完整性;生成 SHA-256 清单,保留失败及无效记录,脱敏审查通过后仅新增 `evidence/`。执行结果和开放问题更新 docs/39、docs/40/README 时区分“设计 / 实际执行 / 板测通过”;任何未执行项保持待验证。
