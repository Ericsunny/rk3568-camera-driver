### 0.2 建两个文件

`hello.c`(路径按 0.3 选的方式:方式 A 就在 VM 的 `~/work/hello/`,方式 B 就在 PC 的 `D:\vm\work\hello\`):

```c
#include <linux/module.h>
#include <linux/init.h>

static int __init h_init(void) { pr_info("m4probe: hello init\n"); return 0; }
static void __exit h_exit(void) { pr_info("m4probe: bye\n"); }

module_init(h_init);
module_exit(h_exit);
MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("module-4 toolchain probe");
```

`Makefile`(与 `hello.c` 同目录;**`all:`/`clean:` 下面的命令行必须用 Tab 缩进,不能用空格**):

```makefile
obj-m += hello.o

# Absolute toolchain path + kernel tree: no PATH setup needed.
# Build files are kept ASCII-only on purpose.
TOOLCHAIN := $(HOME)/rk3568/RK_SDK/prebuilts/gcc/linux-x86/aarch64/gcc-buildroot-9.3.0-2020.03-x86_64_aarch64-rockchip-linux-gnu
KDIR := $(HOME)/rk3568/RK_SDK/kernel
ARCH := arm64
CROSS_COMPILE := $(TOOLCHAIN)/bin/aarch64-rockchip-linux-gnu-
export LD_LIBRARY_PATH := $(TOOLCHAIN)/lib

all:
	$(MAKE) ARCH=$(ARCH) CROSS_COMPILE=$(CROSS_COMPILE) -C $(KDIR) M=$(PWD) modules
clean:
	$(MAKE) ARCH=$(ARCH) CROSS_COMPILE=$(CROSS_COMPILE) -C $(KDIR) M=$(PWD) clean
```

> **这份 Makefile 是"自给自足"的**:工具链写**绝对路径** → 不需要 `export PATH`;`LD_LIBRARY_PATH` 在 Makefile 里导出 → 不需要手工设。所以只敲 `make` 就行。
> 实测(2026-10-15):在一个全新终端、**什么都没 export** 的情况下,`make` 直接成功,vermagic 正确。
> ⚠️ **Makefile 里不要写中文**(实测踩坑):中文注释行会和下一行**并成一行**,`TOOLCHAIN ?= ...` 于是变成注释的一部分、变量为空,而报错却是 `aarch64-...-gcc: No such file or directory` —— 看着像 PATH 问题,实际是变量没被赋值。Makefile 注释一律用英文。

### 0.5 什么叫"做对了"

| 检查点 | 期望看到 |
|---|---|
| `modinfo` 的 vermagic | **`4.19.232 SMP mod_unload aarch64`**(和板上内核逐字符一致,所以能加载) |

> 这一步真正学到的东西:**内核模块 = 一个能被内核"挂上去/摘下来"的对象**;`module_init` 是挂上去时执行、`module_exit` 是摘下来时执行。等写 `ov8858_sm.c` 时,probe/remove 就是**被"某个设备"触发的** init/exit——本质同一件事。

### 0.6 为什么这份 Makefile 这么写(原理,值得懂)

1. **`CROSS_COMPILE := $(TOOLCHAIN)/bin/aarch64-rockchip-linux-gnu-`(绝对路径前缀)**:内核构建系统最终拼出的是 `$(CROSS_COMPILE)gcc`,前缀给绝对路径就**不依赖 PATH**。好处:不用每次开终端都 export,也不会再撞 `aarch64-...-gcc: No such file or directory / Is your PATH set correctly?`(2026-10-15 你踩的就是这个)。
2. **`export LD_LIBRARY_PATH := $(TOOLCHAIN)/lib`**:交叉编译器的 `cc1` 依赖工具链自带的 `libisl.so.15`。不在 Makefile 里导出,就得手工 export,否则报 `cc1: error while loading shared libraries: libisl.so.15`(你在编 rkaiq 时踩过同一个坑)。
3. **`KDIR := $(HOME)/rk3568/RK_SDK/kernel`**:这是**你板上正在运行的那颗内核的源码树**(板上 `uname -a` 里写着 `rk3568@rk3568-vm` —— 出厂镜像就是你在 VM 里编的)。用同一棵树编,vermagic 与符号表天然一致。
4. **别把这个工具链目录塞进 `PATH` 开头**:它自带一个坏掉的 `python2`(缺 `libpython2.7.so`),放开头会让内核构建脚本调用它而报错。这也是"用绝对路径前缀"比"改 PATH"更稳的原因。

## 第 1 步:看懂"驱动到底是什么"(读,约 15 分钟)

### 1.1 原理(人话版,务必先读懂这五句)

1. **设备树是硬件自我介绍**。`cam1_ov8858@36` 这个节点写着 `compatible = "ovti,ov8858"`、三路电源、时钟、复位脚——它就是在说"i2c5 上 0x36 地址有个 OV8858,它需要这些资源"。
2. **驱动里有一张表声明"我能驱动谁"**。就是 `of_match_table` 里的 `.compatible = "ovti,ov8858"`。
3. **内核把两者对一遍,匹配上就调用你驱动的 `probe()`**,并把那个设备(`struct i2c_client *`)交给你。**这就是"驱动被加载"的真正含义**——模块插进内核只是"我来了",probe 被调用才是"我干活了"。
4. **所以"写驱动" = 写一堆"在特定时刻被内核调用"的函数**。最重要的三个:`probe()`(设备出现时)、`remove()`(设备消失时)、`s_stream()`(应用要开流时)。你模块四要做的,只是把 probe/remove 写出来。
5. **"五件套"就是 probe 里必须做的五件事**:
   - ① **开电源**(regulator):芯片要三路电,按顺序上电(顺序错了芯片不工作)
   - ② **给时钟**(clk):给芯片 24MHz 参考时钟,它内部 PLL 才能起振
   - ③ **登记可调项**(ctrl handler):把"曝光、增益、link_freq"登记成标准控制项,应用层才能用 `v4l2-ctl` 调
   - ④ **挂进 V4L2 拓扑**(subdev + media entity + pad):让内核知道"这颗 sensor 的输出接到谁"(dphy → ISP)
   - ⑤ **注册给内核**(`v4l2_async_register_subdev`):把自己登记进"待匹配设备池",让 ISP 那侧能找到它

### 1.2 为什么要写"骨架"而不是直接写完整驱动

- 框架不对,寄存器填对了也白填(probe 都不知道该干什么);
- 寄存器序列必须从 OV8858 datasheet 一条条查出来,那是 L1-B 的活,现在写等于抄厂商代码(违反你自己定的纪律);
- **骨架本身就是交付物**:一份"从零写出的内核驱动"是简历上"我写过内核代码"的实物证据。

### 1.3 现在读什么(只读这些,别通读)

| 读什么 | 在哪 | 读到什么程度 |
|---|---|---|
| `ov5695.c` 的 **probe 函数** | VM `~/rk3568/RK_SDK/kernel/drivers/media/i2c/ov5695.c`(搜 `static int ov5695_probe`) | 只看它**按什么顺序做什么事**(取 regulator → 取 clk → 建 ctrl → 初始化 pad → 注册)。**寄存器表一律不看** |
| `ov5695.c` 的 **remove** | 同一个文件 | 看它撤销的顺序,体会"对称性" |
| 中文框架文档 | VM `~/rk3568/RK_SDK/kernel/Documentation/translations/zh_CN/video4linux/v4l2-framework.txt` | 只看 v4l2_device / v4l2_subdev 两节 |
| 你的设备树节点长什么样 | 板上 `ls /proc/device-tree/i2c@fe5e0000/cam1_ov8858@36/` | 看属性名,和你 probe 里要取的资源对得上 |

> 对照物:你 IMX6ULL 写过的 platform 驱动。`probe/remove/of_match_table/module_xxx_driver` 四件套完全一样,只有三处不同:①总线类型 `platform_driver → i2c_driver`;②probe 参数 `pdev → client`;③注册宏 `module_platform_driver → module_i2c_driver`。

## 第 2 步:整份代码长什么样(先有地图再走路)

你之前"看不懂"的一个主要原因,是 12 个手术点是**平铺的清单**,看不到它们在同一个文件里怎么拼起来。真实文件从上到下就是这样:

```
ov8858_sm.c
├── ① 头文件                       ~10 行   module.h / i2c.h / v4l2-subdev.h / v4l2-ctrls.h / clk.h / regulator/consumer.h / pm_runtime.h / gpio/consumer.h
├── ② struct ov8858_sm { ... }     私有数据  subdev、ctrl_handler、xvclk、supplies[3]、pwdn/reset、client   ← 手术点 1
├── ③ 两张静态表 id[] / of_match[]  声明支持谁                                                          ← 手术点 2
│       + MODULE_DEVICE_TABLE(i2c, ...)
├── ④ power_on() / power_off()      开/关电源与时钟(五件套①②)                                        ← 手术点 3
├── ⑤ probe(client)                 ★ 内核发现设备时调用,下面 8 步是它的骨架
│       ① devm_kzalloc 私有结构体
│       ② v4l2_i2c_subdev_init()    把 subdev 和 i2c client 互相绑定
│       ③ 取资源 regulator / clk / gpio                                                          ← 手术点 5、6
│       ④ ctrl handler 建曝光/增益/link_freq                                                     ← 手术点 8
│       ⑤ media_entity_pads_init()  登记 pad                                                     ← 手术点 10
│       ⑥ 填 v4l2_subdev_ops 表(.core/.pad/.video)                                              ← 手术点 9
│       ⑦ pm_runtime_enable + SET_RUNTIME_PM_OPS                                                 ← 手术点 7
│       ⑧ v4l2_async_register_subdev() + dev_info 打印                                            ← 手术点 11
├── ⑥ remove(client)                按 ⑧⑦⑤④ 逆序撤销                                              ← 手术点 12
├── ⑦ s_stream() / set_fmt() / log_status()   应用层触发时才调用,本阶段先占位                          ← 手术点 9
└── ⑧ module_i2c_driver(ov8858_sm_driver)   把整个驱动交给内核
```

**记住一句话**:probe 是"入场流程",remove 是"退场流程",五件套是入场时必须办的五件事,①~⑧ 是它们的代码位置。

### 3.5 起手骨架(阶段 A 的全部内容)

下面这份就是 08 任务书里"手术点 1、2 + 空 probe/remove + 注册"的落地版,**已在你的 VM 上编译验证 0 error 0 warning**。

> **这块是脚手架,不是学习目标**——直接整份覆盖文件,别手敲。真正体现你理解的是阶段 B/C 往 probe 里加的东西。
> **但文件里各块的顺序不能乱**(2026-10-21 实测踩过):
>
> ```
> ① include 段        ← 用到的类型/原型必须先出现
> ② 私有 struct        ← 依赖 ①
> ③ 两张匹配表         ← 依赖 ①
> ④ probe / remove    ← ★ 必须在 ⑤ 之前定义!
> ⑤ struct i2c_driver  ← 引用 ③ 和 ④
> ⑥ module_i2c_driver  ← 引用 ⑤
> ```
> 顺序错了会报两类错:`field 'xxx' has incomplete type`(漏 include)和 `'xxx_probe' undeclared here`(函数定义在使用之后)。

```c
// SPDX-License-Identifier: GPL-2.0
/*
 * ov8858_sm.c - OV8858 sensor driver skeleton (module 4)
 * 只搭框架,不填寄存器;寄存器序列属于 L1-B(datasheet)。
 */
#include <linux/clk.h>
#include <linux/gpio/consumer.h>
#include <linux/i2c.h>
#include <linux/module.h>
#include <linux/of.h>
#include <linux/pm_runtime.h>
#include <linux/regulator/consumer.h>
#include <linux/slab.h>
#include <media/media-entity.h>
#include <media/v4l2-async.h>
#include <media/v4l2-ctrls.h>
#include <media/v4l2-fwnode.h>
#include <media/v4l2-subdev.h>

#define OV8858_SM_NAME "ov8858_sm"

/* 手术点 1:私有结构体。模块二那张"对象组成图"上每个框 = 这里一个成员 */
struct ov8858_sm {
	struct v4l2_subdev          subdev;
	struct v4l2_ctrl_handler    ctrl_handler;
	struct media_pad            pad;
	struct clk                 *xvclk;
	struct regulator_bulk_data  supplies[3];
	struct gpio_desc           *pwdn;
	struct gpio_desc           *reset;
	struct i2c_client          *client;
};

/* 手术点 2:两张静态表 —— "我支持谁" */
#if IS_ENABLED(CONFIG_OF)
static const struct of_device_id ov8858_sm_of_match[] = {
	{ .compatible = "ovti,ov8858-sm" },   /* 用独特 compatible,见手册第 4 步 */
```

## 第 4 步:阶段 B —— 让它真的被内核调用(第一次看到自己的 probe 打印)

**这一关是模块四最容易卡死的地方**,先读懂原理再动手。

### 4.1 原理:为什么你的 probe 可能永远不打印

内核匹配"设备 ↔ 驱动"靠 compatible,而且**先注册的先赢**。你板上的实际情况(我实测):

| 事实 | 值 |
|---|---|
| ov8858 的驱动 | **内建在内核里**(不是模块):`/lib/modules/4.19.232/modules.builtin` 里有 `kernel/drivers/media/i2c/ov8858_camera.ko` |
| 设备树节点 | `cam1_ov8858@36` 存在,`compatible = "ovti,ov8858"`,但 **`status = "disabled"`** |

于是有三种现象,**全都不是 bug**:

| 你的做法 | 现象 | 原因 |
|---|---|---|
| 驱动写 `ovti,ov8858`,节点还 disabled | insmod 成功,毫无打印 | 设备不存在 → probe 根本不会被调用 |
| 驱动写 `ovti,ov8858`,节点改 okay | insmod 成功,**还是没有你的打印** | 内建驱动先注册,把这个设备抢走了 |
| 驱动写**独特** compatible(如 `ovti,ov8858-sm`)+ 节点改成同一个 | **你的 probe 打印出现了** | 只有你匹配 |

### 4.2 做什么(顺序很重要,这是一次很好的对照实验)

1. **先做对照**:只把设备树节点的 `status` 改成 `okay`,compatible 不动 → 编 dtb → 部署 → 重启 → `dmesg | grep -i ov8858`,你会看到**内建驱动**的日志(它会去读芯片 ID,而 J11 上现在插的是 IMX415,所以它会失败——这正好证明"设备确实存在、但被别的驱动认领了")。
2. **再做正解**:把节点 compatible 改成 `"ovti,ov8858-sm"`,同时你驱动的 `of_match_table` 用同一个字符串 → 编 dtb → 部署 → 重启 → `insmod` → **看你的 `ov8858_sm probe done`**。

> **要让你的 sensor 进 media 图,下一步是启用 `csi2-dphy2`**(dts 改动)。注意 dphy 有模式互斥约束(见 09 文档),别把 dphy1 弄挂了。

### 5.1 ctrl handler 的标准四步(2026-10-21 已编译 + 板上验证)

**初始化函数**:

```c
static int ov8858_sm_initialize_controls(struct ov8858_sm *ov8858)
{
	struct v4l2_ctrl_handler *handler = &ov8858->ctrl_handler;
	struct v4l2_ctrl *ctrl;
	int ret;

	/* ① 初始化:第二个参数是"预计几个 ctrl",只是容量提示 */
	ret = v4l2_ctrl_handler_init(handler, 8);
	if (ret)
		return ret;

	/* ② 逐个登记。只读的可以传 NULL ops;可写的必须给自己的 ctrl_ops */
	ctrl = v4l2_ctrl_new_int_menu(handler, NULL, V4L2_CID_LINK_FREQ,
				      0, 0, ov8858_sm_link_freq_menu);
	if (ctrl)
		ctrl->flags |= V4L2_CTRL_FLAG_READ_ONLY;

	v4l2_ctrl_new_std(handler, NULL, V4L2_CID_PIXEL_RATE,
			  0, OV8858_SM_PIXEL_RATE, 1, OV8858_SM_PIXEL_RATE);

	ov8858->exposure = v4l2_ctrl_new_std(handler, &ov8858_sm_ctrl_ops,
					     V4L2_CID_EXPOSURE,
					     OV8858_SM_EXPOSURE_MIN,
					     OV8858_SM_EXPOSURE_MAX, 1,
					     OV8858_SM_EXPOSURE_DEF);

	ov8858->anal_gain = v4l2_ctrl_new_std(handler, &ov8858_sm_ctrl_ops,
					      V4L2_CID_ANALOGUE_GAIN,
					      OV8858_SM_GAIN_MIN,
					      OV8858_SM_GAIN_MAX, 1,
					      OV8858_SM_GAIN_DEF);

	/* ③ ★关键:单个 ctrl 创建失败不会立刻返回,而是累加到 handler->error */
	if (handler->error) {
		ret = handler->error;
		dev_err(&ov8858->client->dev, "failed to init controls: %d\n", ret);
		v4l2_ctrl_handler_free(handler);
		return ret;
	}

	/* ④ 挂到 subdev 上,用户态才看得见 */
	ov8858->subdev.ctrl_handler = handler;
	return 0;
}
```

> - `implicit declaration of function`:函数名**拼错**(如把 `v4l2_ctrl_new_int_menu` 写成 `new_init_menu`),编译器会猜你想用哪个

### 5.3 五件套 + subdev ops 落地(2026-10-21 实测通过)

**资源与 dts 的对应关系**(你板上的真实值):

| 代码里 | dts 里 | 实测结果 |
|---|---|---|
| `supply_names = {"dovdd","avdd","dvdd"}` | `dovdd-supply` / `avdd-supply` / `dvdd-supply` → 三个 `regulator-fixed`(always-on,1.8/2.8/1.2V) | `Linked as a consumer to regulator.8/9/10` |
| `devm_clk_get(dev, "xvclk")` | `clocks = <&ext_cam1_clk>` + `clock-names = "xvclk"`,fixed-clock **24 MHz** | `xvclk=24000000 Hz` |
| `devm_gpiod_get_optional(dev, "pwdn")` | `pwdn-gpios` | `pwdn=ok` |
| `devm_gpiod_get_optional(dev, "reset")` | `reset-gpios` | `reset=ok` |

**四条设计要点**(每条都在板上有对应现象):

1. **`-EPROBE_DEFER` 原样返回**:regulator 提供者可能后注册,吞掉这个错误 = 永不重试。板上现象:如果拿不到,probe 反复重试而**不报致命错误**。
2. **GPIO 用 `devm_gpiod_get_optional`**:`pwdn`/`reset` 不是所有模组都有;用 optional 版本,拿不到返回 NULL 而不是错误,代码里 `if (ov8858->pwdn)` 才安全。
3. **`power_on/off` 放在 `s_stream`,不放 probe**:probe 一次、stream N 次。放 probe 里 = 只上电一次、也永远不会真正关电,而且和 runtime PM 冲突。
4. **`devm_*` 自动释放看得见**:rmmod 后 dmesg 出现 `Dropping the link to regulator.8/9/10` —— 这就是 devm 在替你回收,remove 里不用手写 disable。

**subdev ops 占位**(四条回调,签名必须与 `v4l2-subdev.h` 一致):

| 回调 | 4.19 签名 | 本阶段实现 |
|---|---|---|
| `.video.s_stream` | `int (*)(struct v4l2_subdev *sd, int enable)` | 打日志 + 调 `power_on/off`,寄存器序列留 `TODO(L1-B)` |
| `.core.log_status` | `int (*)(struct v4l2_subdev *sd)` | 打日志 |
| `.pad.get_fmt` / `.set_fmt` | `int (*)(sd, struct v4l2_subdev_pad_config *cfg, struct v4l2_subdev_format *f)` | 先返回 `-ENOTTY` |

**验收记录**:编译 0 warning;`insmod` → `resources: xvclk=24000000 Hz, pwdn=ok, reset=ok` + `probed`;`rmmod` 干净且出现三条 `Dropping the link`;连续 3 次 insmod/rmmod 循环全部 OK;`dmesg` 里 oops / call trace 计数均为 0。

### 5.4 ★ 为什么 sensor 驱动通常"编进内核"而不是做成模块(2026-10-21 实测踩坑)

**现象**:把 CAM1 链路(`csi2_dphy2` / `mipi_csi2` / `rkcif_mipi_lvds`)在 dts 里打开后,链路本身 probe 正常(6 个 subdev、多出 `/dev/media1`),但 `insmod` 我们的 sensor 模块后:

- `dmesg` 只有 `probe done`,**没有** `dphy2 matches ov8858-sm`;
- `/dev/v4l-subdev*` 数量不变(6 → 6),`media-ctl` 里找不到 sensor;
- 伴随 `rockchip-csi2-dphy2: No link between dphy and sensor` 告警。

**根因**:4.19 的 async 匹配是**单向链式触发**的(`drivers/media/v4l2-core/v4l2-async.c`):

```c
/* v4l2_async_register_subdev() 第 601 行:只遍历 notifier_list */
list_for_each_entry(notifier, &notifier_list, list) {
	struct v4l2_device *v4l2_dev = v4l2_async_notifier_find_v4l2_dev(notifier);
	if (!v4l2_dev)
		continue;            /* ← 还没挂到 v4l2_device 的通知器被跳过 */
	asd = v4l2_async_find_match(notifier, sd);
	...
}
/* 没匹配上 → 挂进 subdev_list 等热插拔(第 625 行) */
list_add(&sd->async_list, &subdev_list);
```

而 dphy 这类"桥"的通知器要通过**上层**(rkcif/mipi-csi2)先绑定它、把它的通知器挂到父链上,`v4l2_async_notifier_find_v4l2_dev()` 才找得到 v4l2_device,然后才会回头扫描 `subdev_list` 认领 sensor。

**结论**:
- **sensor 与桥在开机阶段一起 probe**(都是内建驱动)→ 无论谁先谁后,链式触发能把 sensor 认领进来 → IMX415 就是这样工作的;
- **桥开机 probe 完、sensor 事后 insmod** → 反向不触发 → sensor 永远挂在等待队列里;
- 所以生产环境的 sensor 驱动**一律编进内核**(`CONFIG_VIDEO_xxx=y`),而不是做成 `.ko` 事后加载。

**试过但无效的办法**(别浪费时间):
- `echo csi2-dphy2 > .../rockchip-csi2-dphy/unbind` + `bind`:重跑 probe,但 dphy 自己的通知器依旧没有 v4l2_device → 不认领;
- `echo rkcif_mipi_lvds > .../rkcif/unbind` + `bind`:不但没修好,还触发了 vendor 驱动在 unbind 时的一个 trace(内核没死,重启即恢复),而且链路会掉。

**正确做法**:把驱动放进内核树 `drivers/media/i2c/`,`Kconfig` + `Makefile` 加进去,defconfig 里开成 `=y`,重编 Image + dtb 部署。

### 5.5 L1-B 第一步:让驱动第一次和芯片说话(读 ID,2026-10-21 实测)

**硬件前提**:OV8858 模组接到 **J11(CAM1 / i2c5)**。验证:`i2cdetect -y 5` 应看到 `36`(同总线上 `0c` 是镜头 VCM dv9714,属正常)。

**ID 寄存器**(必须来自 datasheet,别套别的型号):`0x300B` = 高字节 `0x88`,`0x300C` = 低字节 `0x58` → 合起来 `0x8858`。⚠️ `0x300A` 读出来是 `0x00`,别被它骗了。

**16 位寄存器读法**(OV 系列是 16 位地址 + 8 位数据,`i2c_smbus_*` 是 8 位地址,用不了):

```c
static int ov8858_sm_read_reg(struct i2c_client *client, u16 reg, u8 *val)
{
	u8 buf[2] = { reg >> 8, reg & 0xff };
	struct i2c_msg msgs[2] = {
		{ .addr = client->addr, .flags = 0,        .len = 2, .buf = buf },
		{ .addr = client->addr, .flags = I2C_M_RD, .len = 1, .buf = val },
	};
	int ret = i2c_transfer(client->adapter, msgs, ARRAY_SIZE(msgs));

	if (ret < 0)
		return ret;
	return ret == ARRAY_SIZE(msgs) ? 0 : -EIO;
}
```

**两条消息的含义**:第一条把 16 位寄存器地址写给芯片(写方向),中间是**重复起始(repeated START)**,第二条读回 1 字节。这就是传感器驱动里最常见的读寄存器写法。

**ID 校验 + probe 里调用**:

```c
	/* probe 里,subdev_init 之后 */
	ret = ov8858_sm_check_sensor_id(ov8858);   /* 读 0x300B/0x300C,不等于 0x8858 就 -ENODEV */
	if (ret)
		return ret;
```

**实测日志**:
```
ov8858-sm 5-0036: Detected OV8858 id 0x8858
ov8858-sm 5-0036: OV8858 SM camera driver probed
```

> 为什么产品驱动都要做这一步:防止**接错模组**(比如板上插的是 IMX415)或**驱动/模组型号对不上**。没有 ID 校验,驱动会对着错误的芯片写寄存器,现象千奇百怪。
> 注意:现在能读通是因为 cam1 三路电源在 dts 里是 `regulator-always-on`。等按 datasheet 2.6 章实现了上电时序,就要**先上电、再读 ID**(真实驱动都是 `power_on → 读 ID → power_off` 或走 runtime PM)。

### 5.6 L1-B 第二步:按 datasheet 写上电时序(2026-10-21 实测通过)

**从 datasheet 2.6 章(p25~32,figure 2-3 / table 2-3、2-4)抄到的约束**:

| 约束 | 值 | 影响代码 |
|---|---|---|
| DOVDD / AVDD 先后 | **可颠倒**(t0/t1 = 0~∞) | 三路一起 `regulator_bulk_enable` 即可 |
| DVDD | 需在另两路稳定后(t7 = 0) | 同上,同时使能没问题 |
| XSHUTDN(= 引脚名,不是 XCLR) | DVDD 稳定后即可**拉高**(t9 = 0);**高 = 运行** | `gpiod_set_value(reset, 1)` 释放复位 |
| 首次 SCCB 前时钟已运行 | **8192 个 XVCLK**(t3) | 24 MHz → 341 µs,取 1 ms 余量 |
| 到可访问 I2C | 再来 8192 个 XVCLK(t2) | 同上 |

**实现要点**:

```c
	ret = regulator_bulk_enable(3, supplies);      /* 三路一起,顺序不敏感 */
	ret = clk_prepare_enable(xvclk);               /* 24 MHz */
	usleep_range(1000, 2000);                      /* t3: 8192 cycles ≈ 341us */
	gpiod_set_value_cansleep(reset, 1);            /* t9: 高电平 = 运行 */
	usleep_range(1000, 2000);                      /* t2: 再来 8192 cycles */
	/* 之后才能读 ID / 写寄存器 */
```

**两个容易写错的点**:

1. **`reset` 极性**:本器件引脚是 XSHUTDN(低有效关断),所以 **拉高才是运行**。dts 里 `GPIO_ACTIVE_HIGH` + `gpiod_set_value(desc, 1)` = 物理高 = 运行。写反了的现象是:ID 读回 `0x00` 或 `-EIO`。
2. **GPIO 用 `GPIOD_ASIS` 申请**:只拿句柄、不改引脚状态,避免 `GPIOD_OUT_LOW/HIGH` 在申请瞬间把芯片意外复位/关断。

**实测日志**(上电时序执行后读 ID 成功,证明极性判断正确):

```
resources: xvclk=24000000 Hz, pwdn=ok, reset=ok
Detected OV8858 id 0x8858
OV8858 SM camera driver probed
```

**错误路径也要关电**:probe 里后续步骤失败时走 `goto err_power → ov8858_sm_power_off()`,否则半初始化失败会留下"电一直开着"的状态。

### 5.7 L1-B 第三步:写入完整初始化序列,芯片真的开始出流(2026-10-21 实测)

**先定版本**(用错 r1a/r2a 的表会完全不出图):

### 5.10 踩坑:`open("/dev/video0")` 报 `Unknown error 515`

**现象**:驱动 probe 成功、media 链路全 ENABLED,但一打开 video 节点就失败,errno 515(`-ENOIOCTLCMD`),dmesg:

```
stream_cif_mipi_id0: update sensor info failed -515
```

**根因**(`drivers/media/platform/rockchip/cif/capture.c:2769 rkcif_update_sensor_info`):

```c
ret = v4l2_subdev_call(sensor->sd, video, g_mbus_config, &sensor->mbus);
if (ret && ret != -ENOIOCTLCMD) { ...; return ret; }   /* -515 被"容忍" */
...
return ret;                                            /* 但 ret 没清零! */
```

我们驱动**没实现 `.video.g_mbus_config`** → 这次 subdev 调用返回 `-ENOIOCTLCMD(-515)` → 内核虽然"容忍"了,却把这个陈旧的 `ret` 当成自己的返回值 → 上层判失败。

**注意**:`g_mbus_config` 在 **`v4l2_subdev_video_ops`** 里,不在 `pad_ops` 里,所以按五件套想象时特别容易漏。

**修法**(2 lane / CSI-2):

```c
static int ov8858_sm_g_mbus_config(struct v4l2_subdev *sd,
				   struct v4l2_mbus_config *cfg)
{
	cfg->type  = V4L2_MBUS_CSI2;
	cfg->flags = V4L2_MBUS_CSI2_2_LANE |
		     V4L2_MBUS_CSI2_CHANNEL_0 |
		     V4L2_MBUS_CSI2_CONTINUOUS_CLOCK;
	return 0;
}

static const struct v4l2_subdev_video_ops ov8858_sm_video_ops = {
	.s_stream      = ov8858_sm_s_stream,
	.g_mbus_config = ov8858_sm_g_mbus_config,   /* ← 少这一行就打不开 video 节点 */
};
```

顺带:`ov8858->subdev.flags |= V4L2_SUBDEV_FL_HAS_DEVNODE;` 加上才会有 `/dev/v4l-subdevN`,方便 `v4l2-ctl -d /dev/v4l-subdev2 --list-ctrls` 单独调 sensor。

### 5.11 第一帧怎么"看懂":compact RAW10 的真实内存布局

抓下来的 7.5 MB 文件不是"每像素 2 字节",直接按 16bit 看会得到"只有左边一半有数据"的假象。真相是:

**rkcif 在 RK3568 上默认 `is_compact = 1`,10bit RAW 按 MIPI 打包写内存:每 5 字节 = 4 个像素。**

| 量 | 值 | 怎么算 |
|---|---|---|
| 每行有效字节 | **2040** | 宽 1632 × 10bit / 8 |
| 每行 stride | **2048** | 2040 向 256 对齐(`ALIGN(x,256)`) |
| 每帧字节 | 2048 × 1224 = 2,506,752 | 抓 1 帧的大小 |
| 像素值范围 | 0 … 1023 | 真 10bit |

**解包公式**(5 字节 `b0 b1 b2 b3 b4` → 4 个像素):

```
p0 = (b0 << 2) | (b4 & 0x03)
p1 = (b1 << 2) | ((b4 >> 2) & 0x03)
p2 = (b2 << 2) | ((b4 >> 4) & 0x03)
p3 = (b3 << 2) | ((b4 >> 6) & 0x03)
```

**三步校验数据对不对**:

1. **字节数**:每行非零字节必须正好 2040(多一个少一个都说明 stride/格式不匹配)
2. **5 字节周期**:同一行里 `b0..b3` 是相邻像素的高 8 位(量级接近),`b4` 是低位字节(0~255 满量程乱跳)
3. **图像结构**:解出来做 4×4 平均后应该能看出场景轮廓;如果 4×4 平均后仍是均匀噪声,说明拿到的是垃圾帧(见 §5.12)

**一条命令看对不对**(在 VM/PC 上用 python3 + numpy):

```python
import numpy as np
BPL, H, W = 2048, 1224, 1632
```

### 5.12 偶发"整帧垃圾":probe 上电后没有断电

**现象**:同一套代码、同一个模式,有时候抓到清晰图,有时候抓到整帧噪声(均值从 546 掉到 288),重启/重开流之后又好了。

**根因**:probe 为了读 ID 调了 `power_on()`,**成功路径没有 `power_off()`**。于是:

- probe:`clk_prepare_enable` +1、`regulator_bulk_enable` +1,之后一直挂着
- 第一次 `s_stream(1)`:再 `power_on()` → 计数变 2
- `s_stream(0)`:只 `power_off()` 一次 → **传感器一直带电、clk 一直开**
- 两次开流之间传感器没有真正掉电复位,状态机残留 → 偶发垃圾帧

**修法**:加一个 `bool powered;` 把上电/断电做成幂等,并在 probe 读完成 ID 后主动断电。

```c
struct ov8858_sm {
	...
	bool is_1080p;
	bool powered;		/* 电源/时钟是否已打开,保证上电断电严格配对 */
};

static int ov8858_sm_power_on(struct ov8858_sm *ov8858)
{
	if (ov8858->powered)		/* 已经在电上就别重复加计数 */
		return 0;
	...
	ov8858->powered = true;
	return 0;
}

static void ov8858_sm_power_off(struct ov8858_sm *ov8858)
{
	if (!ov8858->powered)		/* 没开过就别重复减计数 */
		return;
	ov8858->powered = false;
	...
}

/* probe 里,读完 ID / 跑完 test_stream 之后: */
	ov8858_sm_power_off(ov8858);
	ret = ov8858_sm_initialize_controls(ov8858);
```

**验证**:

```bash
# 空闲时(没有在抓帧)时钟计数必须是 0
ssh rkboard 'grep clk_cam1_out /sys/kernel/debug/clk/clk_summary'
# →  ext_cam1... clk_cam1_out   0  0  0  24000000   ...   (enable=0 prepare=0)

# 连开 5 次流,每次都要一致
for i in 1 2 3 4 5; do
  v4l2-ctl -d /dev/video0 --stream-mmap --stream-count=1 --stream-to=/tmp/s$i.raw
done
```

实测结果(修完):5 次全部 `mean 545.0~545.5`,4×4 平均后的行间相关 `0.899~0.900`,完全稳定,无 clk/regulator 告警。

### 5.14 L1-B 第六步:1080p 模式(2026-10-21 自推 + 修掉 anchor 越界,已转正)

**先说结论**:1920×1080 是"**全阵列读出 + 裁窗**",不是 binning。最终可用的参数:

| 寄存器 | 值 | 含义 |
|---|---|---|
| `0x3808/09` | `0x0780` | 输出宽 1920 |
| `0x380A/0B` | `0x0438` | 输出高 1080 |
| `0x380C/0D` | `0x0794` | HTS = 1940(**和全分辨率模式一模一样**) |
| `0x380E/0F` | `0x04D4` | VTS = 1236 → ≈30 fps |
| `0x3501/02` | `0x4CA0` | 曝光 1226 行 = VTS−10 |
| `0x3814` / `0x382A` | `0x01` / `0x01` | 关掉 subsample(不是 binning) |
| `0x3821` | `0x46` | 关 binning |
| `0x3841` | `0x00` | 关 auto-size(全局表给的是 `0xFF`) |
| `0x3800~0x3807` | `0x02B0/0x0A2F`、`0x02BC/0x06F3` | 手写居中窗口:H 688..2607,V 700..1779 |
| `0x4020~0x4027` | 见下方"anchor" | **BLC anchor 必须按窗口重算**,这是缺行的真凶 |
| `0x402B` / `0x402F` | `0x08` / `0x08` | 顶/底黑行数(沿用全分辨率) |

实测:**29.3 fps,30 帧连跑每帧 1080 行零空行,1632×1224 回归同样零空行**。

> 这一档不是一次做对的:第一版帧结构是坏的(1080 行只有 901 行有数据,肉眼却看不出来),查下去才发现是 **BLC anchor 寄存器在裁剪窗口里越界**——详见本节末尾的"排查过程与结论"。

**坑 1:全局表里 `0x3841 = 0xFF` 已经把 auto-size 打开了**

datasheet §4.2 原话:

> Windowing is achieved by masking off the pixels outside of the window; **thus, the original timing is not affected.**
> The OV8858 also supports auto size mode which is controlled by 0x3841[5:0]. Setting it to 0x3F will enable the auto size function and **will output the center of the image by default**. The user only has to configure the H/V output size (0x3808~0x380B) ...

所以 1080p 有**两条路,只能选一条**:

- **A. 交给 auto-size**:只写 `0x3808~0x380B`(`0x3841` 保持全局表的 `0xFF`),芯片自动输出居中窗口。最简单,但实测帧结构仍有缺行(263/1080)。
- **B. 关 auto-size + 手写窗口(最终采用)**:`0x3841 = 0x00`,再写 `0x3800~0x3807`。**必须配套重算 `0x4020~0x4027` 的 anchor**,否则会出现"隔行有数据、隔行全 0"。

**两边同时用**(auto-size 开着又手写窗口)会打架,现象是:

```
rockchip-mipi-csi2: ERR1: error matching frame start with frame end, reg: 0x10
rkcif_mipi_lvds: ERR1: multi fs in oneframe, bak_int:0x0, fs_num:2
```

抓到的 buffer 会变成"**隔行有数据、隔行全 0**",看起来像半个画面。

**坑 2:HTS 不能按裁剪后的宽度缩小**

一开始我按"1920 输出 → HTS = 1066"算,行时序直接被压坏(FS/FE mismatch)。原因是 datasheet 明确说裁窗**不改变原有时序**,整行的列时间还是全阵列那一份。HTS 必须保持 `0x0794`(1940)。

竖直方向则**可以**缩短(`0x380E` 按 VTS 走):auto-size 模式下实际只读 1080+blanking 行,所以 VTS=1236 就能跑 30 fps。这点和"水平不变、垂直可变"的不对称是实测出来的,记下来。

**坑 3:曝光要跟着 VTS 重新算,否则整帧过曝**

全分辨率表的曝光是 `0x9A20`(=2466 行,接近 VTS 2474)。直接搬到 VTS=1236 的 1080p 上,曝光被钳到整帧 → 抓到一片全白(4×4 均值 1022/1023)。改成 `0x4CA0`(1226 行)后图像正常。

**坑 4:写表循环遇到 `REG_NULL` 就退出,`0x0100=0x01` 必须写在它前面**

厂商全分辨率表里**没有** `0x0100=0x01`(它是在 `__ov8858_start_stream` 里单独写的),照抄过来就忘了开流,现象是回读 `stream=0x00`、抓 0 字节。补的时候又踩了一次:插到 `{OV8858_SM_REG_NULL}` **后面**等于没写。正确顺序:

```c
	{0x382d, 0xff},
	{0x0100, 0x01},        /* ← 必须在 REG_NULL 之前 */
	{OV8858_SM_REG_NULL, 0x00},
```

**用起来注意:切 1080p 要先把 sensor 的 pad 格式设好**

```bash
# 1) 先设 sensor 子设备(否则 rkcif 会把宽夹回 1632)
media-ctl -d /dev/media0 --set-v4l2 '"ov8858-sm 5-0036":0[fmt:SBGGR10_1X10/1920x1080]'
# 2) 再设视频节点
v4l2-ctl -d /dev/video0 --set-fmt-video=width=1920,height=1080,pixelformat=BG10
# 3) 抓帧
v4l2-ctl -d /dev/video0 --stream-mmap --stream-count=30 --stream-to=/tmp/f30.raw
```

只做第 2 步的话,`--get-fmt-video` 会显示 `1920x1080` 但 `media-ctl -p` 里 sensor 还是 1632,抓出来是垃圾——因为 **rkcif 在问 sensor 之前就先按 sensor 当前尺寸把宽夹住了**。

**遗留问题的排查过程与结论(2026-10-21 深挖 + 当天解决)**

一开始这一档是**坏的**:把抓到的 buffer 按行统计"非零字节数"就能看出来:

| 配置 | 全零行 | 有效行占比 |
|---|---|---|
| 厂商驱动 3264×2448 | 0 / 2448 | 100% |
| 我们 1632×1224 | 0 / 1224 | 100% |
| 我们 1920×1080(**修复前**) | **179~263 / 1080** | 75.6%~83.4% |
| 我们 1920×1080(**修复后**) | **0 / 1080** | **100%** |

空行集中在**前 353 行、每隔一行空一行**,之后连续正常——肉眼几乎看不出来(那一片只是显得更暗更脏),所以一开始误判成"图像正常"。

**根因:BLC 的 anchor 寄存器在裁剪窗口里越界了。**

`0x4020/21`、`0x4022/23`、`0x4024/25`、`0x4026/27` 是 **ANCHOR LEFT/RIGHT START/END**(datasheet 6.12),单位是**输出像素坐标**:

| 模式 | 内部读出宽 | 厂商给的 ANCHOR LEFT END | 是否越界 |
|---|---|---|---|
| 3264×2448 | 3264 | `0x0C60` = 3168 | 否 ✓ |
| 1632×1224 | 内部仍读 3264(2×2 binning) | `0x0600` = 1536 | 否 ✓ |
| 1920×1080(我们裁剪) | **真的只读 1920 列** | 照抄来的 **3168** | **是 ✗** |

厂商那两档之所以能一直用大数值,是因为它们内部都读满 3264 列;我们做的是真裁剪,anchor 必须按窗口重算。按 `1920/3264 = 0.588` 缩放:

```c
	{0x4020, 0x01}, {0x4021, 0x53},   /* LEFT  START = 339  (576*0.588) */
	{0x4022, 0x07}, {0x4023, 0x47},   /* LEFT  END   = 1863 (3168*0.588) */
	{0x4024, 0x04}, {0x4025, 0x3e},   /* RIGHT START = 1086 (1846*0.588) */
	{0x4026, 0x04}, {0x4027, 0xd5},   /* RIGHT END   = 1237 (2103*0.588) */
```

改完立刻:**30 帧连跑,每帧 1080 行零空行;1632×1224 回归也零空行;帧率 29.3 fps**。

**排除过的其他假设(都是单变量实验,记下来避免重走)**

| 假设 | 实验 | 结果 |
|---|---|---|
| 垂直消隐太大 | 1632×1224 把 VTS 1244 → 2000 | 0 次边界错误 → 无关 |
| 内存 stride 有 160 字节对齐填充 | 1080p 换 `BYR2`(stride 恰好 3840=1920×2) | 空行数完全相同 → 无关 |
| 手写窗口与 auto-size 冲突 | 两种配置各测 | 都坏(263 / 179),只是程度不同 |
| HTS 太小 | 改成全分辨率同值 1940 | 错误依旧 |
| 曝光越界 | 改成 VTS−10 | 只影响亮度 |

**仍存在(不影响数据,已列入诚实清单)**:1080p 下每帧仍打一条

```
rockchip-mipi-csi2: ERR1: error matching frame start with frame end, reg: 0x10
```

它来自 **Synopsys DW CSI-2 主控**的 `ERR1(0x20)` 寄存器 `err_bndry_match` 字段(bits 7:4);`mipi-csi2.c` 只在 DSI-RX 路径才屏蔽这一位(`&= 0xe00000f0`),CSI-2 路径 `MSK1=0` 全开。CIF 侧统计 `all err count: 0`、`frame dma end: 30/30`,数据通路无影响,属主控边界检查的误报。
