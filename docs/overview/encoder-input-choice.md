# 编码输入路径的选择

当前默认使用 V4L2 采集后复制到 MPP 输入缓冲；MPP 分配缓冲、V4L2 导入的 DMA-BUF 路径保留为显式选择。共享路径消除的是采集帧到编码输入的一次整帧 CPU 复制，ISP、RGA、编码器的内存访问以及编码包分发仍然存在，不称为全链路零拷贝。

## 比较依据

- 两路同一输入帧的隔离编码对照各验证 120 帧，复制与共享输出经软件解码后逐帧一致；这是有限帧数，不代表所有运行状态。[对照结果](../../evidence/2026-11-14-dmabuf-allocation/README.md#画面及业务验证)
- 在开启 OSD 和检测的短时测试中，录像进程 CPU 时间中位数分别为：IMX415 复制 27.98、共享 26.17 ms/处理帧；OV8858 复制 24.96、共享 24.37 ms/处理帧。每种模式仅三次、每次约 8–9 秒，包含启动开销；这不是整机 CPU、端到端延迟或双路吞吐的对照，OV8858 组的样本波动较大。未开启检测时相对收益更明显。[测量与原始结果](../../evidence/2026-11-14-dmabuf-allocation/README.md#cpu-结果)
- 共享输入需要在 MPP 返回并核对任务、帧、PTS 与 buffer 后才能 QBUF，CPU 叠字还需执行 DMA-BUF 同步。复制模式在完成复制后即可归还采集 buffer。两者的缓冲占用时间和故障处理不同；当前没有充分的端到端延迟、丢帧和运行余量对照。
- 最终候选的 OV8858 故障注入恢复测试中出现 CSI-2 CRC 并中止；复制路径也曾出现同类日志，不能据此认定共享路径造成了 CRC，也不能将该次恢复记为通过。[记录](../../evidence/2026-11-14-dmabuf-allocation/board/final-v3-ov-recover-term/result.json)
- 双路带检测的并发短测使用的是 v2 候选；后续 v3 增加了检查。提交快照已在板端编译，但未运行该编译产物。[编译记录](../../evidence/2026-11-14-dmabuf-allocation/final-commit-build.md)

因此，目前能确认共享输入具有局部 CPU 收益，**尚不能证明它在本系统的双路业务、可靠性和整体资源使用方面优于复制方案**。保留复制作为默认，是基于现有证据作出的选择；不是认定共享输入不可用，也不是认定 CRC 由它造成。

## 重新选择默认路径的条件

在同一板卡、内核、3A、模型、分辨率和应用版本下，分别以复制和共享模式进行两路业务对照：检查录像和 RTSP 解码、帧数与丢帧，记录进程及整机 CPU、处理吞吐和采集到编码的延迟；重复测试并保留每次结果。对缓冲导入失败、任务归还异常和采集恢复进行隔离验证，出现新的内核错误即停止并保留日志。OV8858 CRC 应先独立定位或用受控对照缩小范围，不能当作已解决。

如果共享路径在实际业务下有可重复的系统收益，并完成相应功能及恢复验证，再将它设为默认。是否删除复制路径应另看目标 BSP 的 DMA-BUF 支持和回退需求；减少一套实现能降低维护负担，但也会失去兼容性对照和明确的回退方式。
