# 原生录像回收验收 · 2026-11-20

## 环境与复现

父版本 585ba2d，单 IMX415、RK3568 #62、eMMC 文件系统。最终源码包在工作站和板端核对 SHA-256 后于新目录构建。板钟未校准，文件名日期仅用于关联。运行顺序采用独立编号。环境、产物和主要输入见[指纹](fingerprints.txt)。现有 3A 全程保持运行。

```sh
# Linux 主机，包含 g++、ffmpeg、ffprobe
python3 tools/tests/test_camera_retention.py
python3 tools/tests/test_camera_cpp_service.py

# RK3568，预先确认镜头空闲、录像卷有余量，CASE 必须为尚不存在的绝对目录
make -j2 entrance
python3 evidence/2026-11-20-native-retention/board_check.py "$PWD" "$CASE"
```

测试夹具先在受管模式用真实摄像头和手动触发生成一段视频。随后重启到正式 entrance 管线并锁定第一段所属运行，使用 1 MiB 占用上限、0 MiB 回收目标、2 s 巡检触发在线回收。观看端为板上回环 FFmpeg RTSP/TCP，带 -xerror。确认已解码且回收报告受保护后解锁，要求旧组消失时同一观看进程仍在解码，主路采集及交付监督正常收尾。测试用零目标故意低于登记及运行文件占用，用于观察超额告警。未填满 eMMC。

## 最终结果

| 判据 | 结果 |
|---|---|
| 真实视频经交付后才进入回收 | 手动模式采集/完成 153/153 帧，独立观看端解码 90 帧，MP4 回执 complete，含 88 帧。|
| 跨服务启动识别旧片段和锁定状态 | next 创建 run-00000002；加锁时旧组保留，解锁后按回执核对并删除旧运行的五文件组，记账 5,640,192 分配字节。|
| 在线回收时采流和观看连续 | 解锁与确认删除时观看端最新进度是第 11、27 帧；同一连接最终严格解码 150 帧。主路完成 153/153 帧，V4L2 序号断点 0，副路接受 150 条结果。监督器退出码 0，内核日志连续，新增 CRC/Oops/panic 匹配项 0。|
| 短窗口资源观察 | 监督器前后均为 4 个 fd、3272 KiB RSS；录像进程从 22 个 fd、21884 KiB 变为 23 个 fd、32328 KiB。第二个采样点在播放器结束后，含预录环预热等工作，两个点无法判定泄漏。|

第 11/27 帧来自 FFmpeg 最近一次输出的进度，不能相减作为回收耗时。分配字节按普通文件占用统计；空闲空间差值还受同时写入的相机及系统影响。[结果 JSON](board-result.json) · [监督器原始回收日志节选](board-retention.log)

板上另用相同源码编译并运行合成文件策略用例，正常续清及损坏保护均通过。日志中的 invalid retention watermarks 是故意传入冲突配置的拒绝用例。[板端文件夹具输出](board-fixture.log)

- 首轮构建提示 nice 返回值未检查，改为显式处理错误。原生方案首轮真板已观察到边解码边回收。[首轮](iteration-b.json)

- 最终将已交付路径提前从监督器扫描候选排除，再做空目录构建及上述复测。Linux 主机的原生策略回归和原 C++ 交付/监督/配置回归均通过。策略用例包含运行编号与独占锁、受保护运行、片段锁定、临时文件、无回执、失败、内容损坏、额外附件、符号链接、未登记目录、构造的部分回收现场和重复巡检。[可执行判据](../../tools/tests/test_camera_retention.py)
